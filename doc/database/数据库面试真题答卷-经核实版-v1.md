## 一、基础（Q1-Q3）

### Q1 · 一行 SELECT 的执行过程（⭐⭐⭐⭐⭐）

**【一句话答】** 客户端 → 连接器（鉴权） → 查询缓存（8.0 已删除） → 分析器（词法/语法） → 优化器（选索引/join 顺序） → 执行器（调存储引擎 API） → 存储引擎（InnoDB 走索引取数据）。

**【标准答】**
- **连接器**：验证账号密码 + 权限，8.0 后 `caching_sha2_password` 是默认认证插件
- **查询缓存**：MySQL **8.0 已彻底删除**（5.7 是默认关闭，命中率极低，因为任何写都会失效）
- **分析器**：把 SQL 解析成解析树（AST），生成 `token` 序列，检查表/列是否存在
- **优化器**：选索引（基于成本估算）、决定 JOIN 顺序、`SELECT *` 改写成具体列
- **执行器**：调存储引擎接口按条件取行，权限校验（连接器只校验连接级权限，行级权限靠 SQL 自己 where）
- **存储引擎**：InnoDB 默认，可换 MyISAM/Memory（接口一致）

**【易错点】**
- ❌ "查询缓存能加速读" → ✅ 8.0 已删，5.7 也几乎没用（写多场景命中率 < 5%）
- ❌ "权限校验只在连接器" → ✅ 行级 / 列级权限校验在执行器（FSM）

---

### Q2 · MyISAM vs InnoDB（⭐⭐⭐⭐）

**【一句话答】** InnoDB 支持事务/行锁/外键/MVCC，是 MySQL 5.5+ 默认引擎；MyISAM 只支持表锁、不支持事务，读取比索更快但**已不推荐新项目使用**。

**【标准答】**
| 维度 | InnoDB | MyISAM |
|---|---|---|
| 事务 | ✅ ACID | ❌ |
| 锁粒度 | 行锁 + 表锁（默认行锁） | 表锁 |
| 外键 | ✅ | ❌ |
| MVCC | ✅ | ❌ |
| 索引 | 聚簇索引（数据即主键索引） | 非聚簇（数据文件分离） |
| 全文索引 | 5.6+ 支持 | ✅ 原生支持 |
| 崩溃恢复 | ✅（redo/undo log） | ❌ 易损坏 |
| COUNT(*) | 需要扫表或维护计数表 | 直接读元数据，O(1) |
| 适用场景 | 写多读多、事务要求 | 读多写少、无事务（已淘汰） |

**【易错点】**
- ❌ "MyISAM 比 InnoDB 快" → ✅ 仅在 **读多写少、无事务** 场景成立；现代硬件 + SSD 下 InnoDB 反而快
- ❌ "InnoDB 不支持全文索引" → ✅ 5.6+ 原生支持

### Q3 · CHAR vs VARCHAR / VARCHAR(100) vs VARCHAR(10)（⭐⭐⭐）

**【一句话答】** CHAR 是定长（`CHAR(10)` 永远占 10 字符，不足补空格）、VARCHAR 是变长（按实际长度 + 1-2 字节长度前缀）；`VARCHAR(N)` 的 N 是**字符数不是字节数**，存"abc"和存 100 个字符都合法。

**【标准答】**
- **CHAR**：定长，磁盘占用固定，适合等长字段（MD5、手机号、身份证号），尾部空格会被 trim
- **VARCHAR**：变长，需要 1-2 字节存长度（≤255 用 1 字节，>255 用 2 字节），节省空间但更新可能引起行迁移
- **VARCHAR(100) vs VARCHAR(10)**：存 `"hello"` 时两者磁盘占用相同（都是 5+1=6 字节）；**但** `VARCHAR(100)` 在排序 / 内存临时表时按 100 长度分配，浪费内存
- **选 CHAR**：等长、变更少、字段短（如性别 `CHAR(1)`）
- **选 VARCHAR**：长度差异大、变更频繁（如用户名、文章内容）
- **TEXT/BLOB**：超过 VARCHAR 上限（65535 字节）才用；会有独立存储 + 指针，效率差

**【易错点】**
- ❌ "VARCHAR(N) 占 N 字节" → ✅ 只占实际字符数 + 1-2 字节
- ❌ "VARCHAR 越长越好预留" → ✅ 太长会浪费内存临时表空间 + 索引长度限制

## 二、索引（Q4-Q8）

### Q4 · B+ 树 vs B 树 vs Hash（⭐⭐⭐⭐⭐）

**【一句话答】** InnoDB 默认 **B+ 树**（多路平衡搜索树，叶子节点链表相连）；B 树非叶子也存数据 → 范围查询慢；Hash 索引只支持等值查询、不支持范围/排序。

**【标准答】**
- **B+ 树**（InnoDB 索引）：
  - 非叶子节点**只存键 + 指针**，叶子节点存数据（或主键）
  - 叶子节点**双向链表**相连 → 范围查询 O(log N + range)
  - 高度通常 3-4 层 → 千万级数据只需 3-4 次 IO
  - **聚簇索引**叶子节点就是数据本身；**二级索引**叶子存主键 → 回表
- **B 树**：非叶子也存数据 → 单点查询稍快，但范围查询要中序遍历整棵树
- **Hash 索引**：
  - 等值查询 O(1)，**不支持范围 / 排序 / LIKE**
  - InnoDB 自适应 Hash 索引（内存里自动建，不可见）
  - Memory 引擎默认 Hash
- **红黑树**：树高 O(log N) 但**太高**（百万级 20+ 层 → 20+ 次 IO），**不适合磁盘**

**【易错点】**
- ❌ "B+ 树和 B 树差不多" → ✅ B+ 树非叶子不存数据 → 单节点能挂更多子节点 → 更"矮胖"，磁盘 IO 少
- ❌ "Hash 索引比 B+ 树快" → ✅ 仅等值查询快；范围查询直接报废

---

### Q5 · 聚簇索引 vs 非聚簇索引（⭐⭐⭐⭐⭐）

**【一句话答】** InnoDB **聚簇索引** = 数据文件本身（按主键组织，叶子节点存完整行）；**二级索引**（非聚簇）叶子存**主键**，不存行数据 → 查询要"回表"。

**【标准答】**
- **聚簇索引（clustered）**：InnoDB 主键索引，叶子节点 = 完整行数据；一张表**只能有一个**（数据物理顺序只能一种）
- **二级索引（secondary）**：其他索引，叶子节点 = 主键值；查询时先走二级索引拿到主键，再回聚簇索引取行（**回表**）
- **覆盖索引**：查询列全在二级索引里 → 不回表，EXPLAIN Extra = `Using index`
- **MyISAM 全是非聚簇**：数据文件和索引文件分离（`.MYD` / `.MYI`）
- **InnoDB 必建主键**：如果没有显式主键，会选第一个非空唯一列，否则隐藏 `row_id`（6 字节）

**【易错点】**
- ❌ "InnoDB 主键索引也是非聚簇" → ✅ InnoDB 主键索引**就是聚簇**，数据和索引一体
- ❌ "二级索引存的就是行数据" → ✅ 只存主键值，必须回表

---

### Q6 · 覆盖索引与最左前缀原则（⭐⭐⭐⭐⭐）

**【一句话答】** 覆盖索引 = 索引里包含查询所需全部列，不回表；最左前缀 = 联合索引 `(a,b,c)` 按 `a → b → c` 排序，跳过 `a` 就失效。

**【标准答】**
- **覆盖索引**：
  ```sql
  -- 索引 (name, age)
  SELECT name, age FROM user WHERE name='张三';  -- ✅ 不回表
  SELECT *   FROM user WHERE name='张三';        -- ❌ 需回表取其他列
  ```
  EXPLAIN Extra = `Using index` 即覆盖索引
- **最左前缀**：
  ```sql
  -- 索引 (a, b, c)
  WHERE a=1                       -- ✅ 用 a
  WHERE a=1 AND b=2               -- ✅ 用 a, b
  WHERE a=1 AND b=2 AND c=3       -- ✅ 用 a, b, c
  WHERE b=2                       -- ❌ 跳过 a，全失效
  WHERE a=1 AND c=3               -- ⚠️ 只用 a（c 不能跳过 b）
  WHERE a=1 AND b>2 AND c=3       -- ⚠️ 用 a, b，c 不走索引（b 是范围）
  ```
- **列顺序选择**：区分度高的列放前面（如 user_id 比 gender 强）；常用等值查询列放前，范围列放最后

**【易错点】**
- ❌ "覆盖索引 = 主键索引" → ✅ 任意索引能包含查询列就算
- ❌ "跳过中间列 c 也能用索引" → ✅ 只用 a，b 和 c 都失效

---

### Q7 · 索引失效的 7 大场景（⭐⭐⭐⭐⭐）

**【一句话答】** 函数/表达式/类型转换/左模糊/OR/不等号/NULL 统计——本质是 **破坏索引有序性**。

**【标准答】**
| # | 失效场景 | 示例 | 修复 |
|---|---|---|---|
| 1 | 索引列用函数 | `WHERE YEAR(create_time)=2026` | 改范围 `create_time BETWEEN '2026-01-01' AND '2026-12-31'` |
| 2 | 索引列计算 | `WHERE price+10>100` | 改 `price>90` |
| 3 | 隐式类型转换 | `WHERE phone=13800001000` (phone 是 varchar) | 加引号 `phone='13800001000'` |
| 4 | 左模糊 | `WHERE name LIKE '%张%'` | 改右模糊 `'张%'`，或用全文索引 |
| 5 | OR 两侧非索引 | `WHERE id=1 OR name='x'` | name 加索引，或 UNION 改写 |
| 6 | 不等号 | `WHERE age<>20`（有时仍走） | 拆成两个范围 `age<20 OR age>20` |
| 7 | IS NULL / NOT NULL 统计 | `WHERE name IS NULL`（取决于优化器） | 建 `idx_name` 让优化器选 |

- **其他**：列字符集/校对集不一致、索引列用 `!=`、数据量小（优化器认为全表扫更快）

**【易错点】**
- ❌ "OR 一定失效" → ✅ OR 两侧**都走索引**才不失效；只有 name 不在索引才失效
- ❌ "!= 一定不走索引" → ✅ 高基数列（如 status）可能走，要 EXPLAIN 看

### Q8 · 为什么推荐自增主键（⭐⭐⭐）

**【一句话答】** 自增主键插入是**顺序追加**到页尾，避免页分裂；UUID/字符串主键随机插入引发页分裂 + 空间浪费。

**【标准答】**
- **页（page）**：InnoDB 存储基本单位 16KB，一页存多行
- **页分裂**：插入位置在页中间 → 后半页复制到新页 → 性能损耗 + 空间浪费（约半页空闲）
- **自增主键**：总是追加到末尾，避免分裂；叶子节点物理顺序 = 逻辑顺序 → 范围查询连续 IO
- **UUID 主键**：随机 → 频繁页分裂 + 写入性能差 + 主键长度大（二级索引叶子都存，浪费空间）
- **业务主键（如身份证号）**：可能变化 → 主键更新成本高（聚簇索引行物理位置要变）

**【易错点】**
- ❌ "主键必须自增" → ✅ 不强制；**有序**就行（雪花 ID 也行，避免 UUID 即可）
- ❌ "UUID 比自增安全" → ✅ 分布式场景可用雪花/Leaf 段，不要用 UUID v4

## 三、事务（Q9-Q12）

### Q9 · 事务 ACID（⭐⭐⭐⭐⭐）

**【一句话答】** A 原子性（要么全成要么全败，Undo Log）、C 一致性（业务约束 + 触发器）、I 隔离性（并发互不干扰，锁 + MVCC）、D 持久性（提交后不丢，Redo Log）。

**【标准答】**
- **A 原子性（Atomicity）**：事务内 SQL 全成功或全回滚；靠 **Undo Log** 实现（记录 SQL 反向操作）
- **C 一致性（Consistency）**：事务前后业务约束不变（如转账 A-100 / B+100 总和不变）；不是单一机制，是 A/I/D 共同保证
- **I 隔离性（Isolation）**：并发事务互不干扰；靠 **锁 + MVCC** 实现
- **D 持久性（Durability）**：事务提交后即使宕机也不丢；靠 **Redo Log + binlog 两阶段提交** 实现
- **MySQL 自动提交**：默认 `autocommit=1`，每条 SQL 一个事务；`START TRANSACTION` / `BEGIN` 开启显式事务

**【易错点】**
- ❌ "一致性靠单一机制" → ✅ A/I/D 协同 + 业务约束 + 触发器
- ❌ "Undo Log 用来恢复已提交数据" → ✅ Undo 是回滚未提交 + MVCC 版本链；**崩溃恢复靠 Redo**

---

### Q10 · 脏读/不可重复读/幻读（⭐⭐⭐⭐⭐）

**【一句话答】** 脏读（读到未提交）、不可重复读（同条记录两次读值不同，UPDATE 引起）、幻读（同一范围两次读行数不同，INSERT/DELETE 引起）。

**【标准答】**
| 现象 | 本质 | 触发 |
|---|---|---|
| **脏读** | 读到其他事务**未提交**的数据 | 隔离级别 RU |
| **不可重复读** | 同一条记录两次读值不同 | 同事务内 UPDATE |
| **幻读** | 同一范围两次读**行数**不同 | 同事务内 INSERT / DELETE |
- **脏写**：两个事务同时改同一行，后提交覆盖前提交（任何隔离级别都会，写锁解决）
- **不可重复读 vs 幻读**：前者针对**已存在行的内容**变化，后者针对**行集合**变化

**【易错点】**
- ❌ "幻读就是不可重复读" → ✅ 不可重复读是 UPDATE，幻读是 INSERT/DELETE
- ❌ "RR 完全没幻读" → ✅ InnoDB RR 通过 **MVCC + Next-Key Lock** 几乎完全避免；⚠️ 但 `UPDATE … WHERE` 当前读仍可能触发边界幻读

---

### Q11 · 4 个隔离级别 + MySQL 默认 RR（⭐⭐⭐⭐⭐）

**【一句话答】** SQL 标准：RU（读未提交）/ RC（读已提交）/ RR（可重复读）/ Serializable（串行化）；MySQL InnoDB 默认 **RR**，但已用 MVCC+Next-Key 几乎消除幻读 → 实际效果类似 Serializable。

**【标准答】**
| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现 |
|---|---|---|---|---|
| **RU 读未提交** | ❌ | ❌ | ❌ | 直接读最新值 |
| **RC 读已提交** | ✅ 避免 | ❌ 可能 | ❌ 可能 | MVCC（每次 SELECT 新 Read View） |
| **RR 可重复读**（InnoDB 默认） | ✅ | ✅ | ✅（几乎）| MVCC（事务内一个 Read View）+ Next-Key |
| **Serializable 串行化** | ✅ | ✅ | ✅ | 全表锁 / 所有 SELECT 转 SELECT ... LOCK IN SHARE MODE |

- **查看/修改**：`SELECT @@tx_isolation;` `SET SESSION G/GLOBAL TRANSACTION ISOLATION LEVEL ...`
- **生产建议**：读多写少用 RC（减少间隙锁、降低死锁）；强一致用 RR（默认）

**【易错点】**
- ❌ "MySQL 默认 Serializable" → ✅ 是 **RR**，不是 Serializable
- ❌ "RC 比 RR 性能差" → ✅ **反过来**——RC 没有间隙锁，并发写入更高

---

### Q12 · MVCC 实现原理（⭐⭐⭐⭐⭐）

**【一句话答】** InnoDB 每行有 `DB_TRX_ID`（最后改事务 ID）+ `DB_ROLL_PTR`（Undo 链指针）；RR 下事务开启时生成 Read View，按可见性算法遍历 Undo 版本链 → 读快照。

**【标准答】**
- **3 个隐藏字段**（InnoDB 每行）：
  - `DB_TRX_ID`：最近修改的事务 ID（6 字节）
  - `DB_ROLL_PTR`：回滚指针，指向 Undo Log 中该行上一版本
  - `DB_ROW_ID`：隐藏主键（无显式主键时启用）
- **Undo Log 版本链**：每次 UPDATE 生成反向日志，新行 `DB_ROLL_PTR` 指旧行 → 链表
- **Read View**（事务第一次 SELECT 时生成）：
  - `m_ids`：生成时刻活跃事务 ID 列表
  - `min_trx_id` / `max_trx_id`：活跃事务最小/最大 ID
  - `creator_trx_id`：创建 Read View 的事务 ID
- **可见性算法**：行 `DB_TRX_ID` < `min_trx_id` → 已提交可见；`> max_trx_id` → 不可见；在 `m_ids` 中 → 未提交不可见；否则已提交可见
- **RC vs RR 差异**：
  - **RC**：每次 SELECT 都生成**新 Read View** → 看到其他事务最新提交
  - **RR**：事务内**共享一个 Read View** → 整个事务同一快照

**【易错点】**
- ❌ "MVCC 是行锁" → ✅ MVCC 是**无锁读**，快照读不阻塞写
- ❌ "MVCC = 乐观锁" → ✅ 是乐观并发控制；但当前读（UPDATE/SELECT FOR UPDATE）仍要加锁

## 四、锁（Q13-Q15）

### Q13 · 行锁 vs 表锁 vs 意向锁（⭐⭐⭐⭐⭐）

**【一句话答】** InnoDB 默认行锁（基于索引）；表锁是 `LOCK TABLES` 显式加；意向锁（IS/IX）是表级标记，**表示事务有意在某些行加共享/排他锁**，避免逐行检查锁状态。

**【标准答】**
- **行锁（record lock）**：锁住索引对应记录；不基于索引的 UPDATE 会**升级为表锁**
- **表锁**：
  - 显式：`LOCK TABLES t WRITE;`
  - 隐式：DDL、ALTER TABLE 会隐式加
  - 意向：IS（意向共享）/ IX（意向排他）
- **意向锁作用**：事务 A 加 `IX`（表级）→ 事务 B 想加表级 X 锁时立即冲突；不需要逐行扫
  - 加行 X 锁 → 自动加表 IX
  - 加行 S 锁 → 自动加表 IS
- **锁兼容性**：IS+IS ✅、IS+IX ✅、X 与其他全部 ❌
- **InnoDB 不支持 `LOCK TABLES ... READ` 的细粒度读锁**（会升级）

**【易错点】**
- ❌ "意向锁是给行加的" → ✅ 是**表级**锁，是"标记"
- ❌ "加了 WHERE 条件就是行锁" → ✅ 必须**走索引**才是行锁；不走索引 = 表锁

---

### Q14 · 共享锁 vs 排他锁 + 当前读 vs 快照读（⭐⭐⭐⭐⭐）

**【一句话答】** S 锁（共享读锁，多事务可同时读）+ X 锁（排他写锁，独占）；**快照读**是普通 SELECT 走 MVCC 无锁；**当前读**（UPDATE / DELETE / SELECT FOR UPDATE）走最新数据 + 加锁。

**【标准答】**
- **共享锁（S）**：`SELECT ... LOCK IN SHARE MODE`（8.0 仍可用，但建议 `FOR SHARE`）；其他事务可读不可改
- **排他锁（X）**：`SELECT ... FOR UPDATE`；其他事务不可读（X 阻塞 S）也不可改
- **当前读**（current read）：读最新已提交版本 + 加 X 锁
  - `SELECT ... FOR UPDATE`
  - `UPDATE / DELETE`（本质就是先查后改）
  - `INSERT`（加插入意向锁）
- **快照读**（consistent read）：普通 `SELECT`，读 Read View 决定的快照
  - RR 下：事务首次 SELECT 生成 Read View
  - RC 下：每次 SELECT 新 Read View
- **MVCC 只管快照读**：当前读仍走锁

**【易错点】**
- ❌ "普通 SELECT 加 S 锁" → ✅ 普通 SELECT 是**快照读**，无锁
- ❌ "FOR UPDATE 比 UPDATE 安全" → ✅ 一样；FOR UPDATE 只是显式控制锁范围

---

### Q15 · 间隙锁 / 临键锁（⭐⭐⭐⭐⭐）

**【一句话答】** 间隙锁 = 锁住索引记录之间的"空隙"，防 INSERT；临键锁 = 行锁 + 间隙锁（左开右闭）；InnoDB **RR 级别默认加临键锁**，RC 级别无间隙锁。

**【标准答】**
- **间隙锁（Gap Lock）**：锁 `(5, 10)` 这段区间 → 其他事务不能在区间内 INSERT
- **临键锁（Next-Key Lock）**：`行锁 + 间隙锁`，区间 `(前一个值, 当前行]`，左开右闭
  - InnoDB RR 当前读默认走 Next-Key
- **插入意向锁**：INSERT 前申请的特殊间隙锁，与已有间隙锁冲突 → 阻塞等待
- **唯一索引等值查询**：精准命中 → 退化为**记录锁**（无间隙锁），并发更高
- **范围查询**：如 `WHERE id BETWEEN 5 AND 10` → 锁 (5, 10] + (10, +∞)
- **RC 下不存在间隙锁** → 可能幻读 → 但并发写入高、减少死锁

**【易错点】**
- ❌ "间隙锁也锁行" → ✅ 只锁**区间空档**，不锁行
- ❌ "RR 一定加间隙锁" → ✅ 唯一索引等值 + 当前读 → **退化为记录锁**

## 五、日志（Q16-Q17）

### Q16 · binlog / redo log / undo log 三件套（⭐⭐⭐⭐⭐）

**【一句话答】** binlog（Server 层，逻辑日志，主从同步用）/ redo log（InnoDB 层，物理日志，崩溃恢复用）/ undo log（InnoDB 层，回滚 + MVCC 版本链）。

**【标准答】**
| 维度 | binlog | redo log | undo log |
|---|---|---|---|
| 层级 | Server 层 | InnoDB 引擎层 | InnoDB 引擎层 |
| 内容 | 逻辑 SQL（ROW 模式是行镜像） | 物理：哪个页哪个偏移改了什么 | 逻辑反向 SQL |
| 用途 | 主从同步 / 数据归档 / 误删恢复 | 崩溃恢复（已提交但没刷盘） | 事务回滚 + MVCC |
| 写入时机 | 事务提交时（两阶段提交） | 事务执行中不断写 | UPDATE / DELETE 时 |
| 文件大小 | 可配置（默认无限追加） | 固定大小（默认 48MB × 4 文件，循环写） | 在系统表空间或独立 undo tablespace |

- **binlog 模式**：
  - STATEMENT（记 SQL，体积小但不安全）
  - ROW（记行镜像，推荐，体积大）
  - MIXED（混合，默认 5.7+ 用 ROW）

**【易错点】**
- ❌ "redo log 是逻辑日志" → ✅ 是**物理**（页级）
- ❌ "undo log 用来恢复数据" → ✅ 用来**回滚 + MVCC**；崩溃恢复靠 **redo**

---

### Q17 · 两阶段提交 (2PC)（⭐⭐⭐⭐⭐）

**【一句话答】** redo log 写 → binlog 写 → redo log 标记 commit；保证 redo 和 binlog 一致性，避免崩溃时 redo 已提交但 binlog 没写导致主从不一致。

**【标准答】**
- **阶段 1**：InnoDB prepare → 写 redo log，状态标记 `prepare`
- **阶段 2**：Server 写 binlog → 调引擎提交 → redo log 状态改 `commit`
- **崩溃恢复**：
  - redo 是 `prepare`，binlog 完整 → 重做提交
  - redo 是 `prepare`，binlog 不完整 → 回滚
  - redo 是 `commit` → 直接提交
- **为什么需要**：redo 是物理 + binlog 是逻辑，两者粒度不同，必须保证"两边都对"才一致
- **group commit**：8.0 后多个事务合并刷盘，提升性能

**【易错点】**
- ❌ "两阶段提交是分布式事务" → ✅ 是**单机** MySQL 内部 binlog ↔ redo 一致性协议；XAG 分布式事务另说
- ❌ "可以关闭 2PC" → ✅ **不能关**，关了就崩后可能 redo 已写但 binlog 没写 → 主从不一致

## 六、SQL 优化（Q18-Q20）

### Q18 · EXPLAIN 12 字段解读（⭐⭐⭐⭐⭐）

**【一句话答】** 看 type（至少 range，最好 ref/const）、key（实际用到的索引）、rows（预估扫描行数，越少越好）、Extra（重要提示）。

**【标准答】**（重点字段）
- **id**：SELECT 序号，相同则同层；越大越先执行
- **select_type**：SIMPLE / PRIMARY / SUBQUERY / DERIVED / UNION
- **type**（**重要**）：
  - `system`（系统表）>`const`（主键/唯一等值）>`eq_ref`（唯一索引 join）>`ref`（非唯一索引）>`range`（范围）>`index`（全索引扫）>`ALL`（全表扫）
  - **至少 range，最好 ref**
- **possible_keys**：可能用到的索引
- **key**：实际用到的索引（**NULL = 没走索引**）
- **key_len**：索引使用字节数（联合索引里算到哪一列）
- **rows**：预估扫描行数
- **Extra**（**重要**）：
  - `Using filesort`：需额外排序（避免 SELECT *, ORDER BY 非索引列）
  - `Using temporary`：用临时表（GROUP BY 非索引列）
  - `Using index`：**覆盖索引**，好
  - `Using where`：server 层过滤
  - `Using join buffer`：JOIN 缓冲（NLJ 算法优化）

**【易错点】**
- ❌ "type=ALL 就是坏" → ✅ 看 rows + 表大小；百万行 ALL 比 range(1000行) 还慢
- ❌ "key 不为 NULL 就是走索引" → ✅ 还要看 type 是不是 index/ALL（**走了索引但全索引扫描**也算"走"）

---

### Q19 · 常见 SQL 优化 10 条（⭐⭐⭐⭐）

**【一句话答】** 避 SELECT */ 命中索引 / 避免函数 / 索引下推 / 小表驱动大表 / LIMIT 优化 / 批量写 / 索引不超 5 个。

**【标准答】**
1. **不用 SELECT ***：只查需要的列，避免回表 + 节省网络
2. **命中索引**：避免索引失效 7 大场景（Q7）
3. **避免函数/运算**：索引列 `WHERE YEAR(create_time)=2026` → 改范围
4. **小表驱动大表**：JOIN 时小表做驱动（EXPLAIN 看执行顺序）
6. **覆盖索引**：经常查 `(a, b)` → 建联合索引避免回表
7. **LIMIT 深分页优化**：`LIMIT 1000000, 10` → 先用主键定位 `WHERE id > 1000000 LIMIT 10`
8. **批量写**：`INSERT INTO ... VALUES (...), (...), (...);` 一次插多行
9. **索引不超 5-6 个**：写慢、空间大、维护成本
10. **长事务拆小**：避免持锁过久

**【易错点】**
- ❌ "索引越多越快" → ✅ 写慢 + 空间 + 优化器选错索引概率↑
- ❌ "JOIN 一定慢" → ✅ 索引到位 + 小表驱动大表，3-4 表 JOIN 也能 ms 级

---

### Q20 · 慢查询分析与深度分页优化（⭐⭐⭐⭐）

**【一句话答】** 慢查询日志定位 + EXPLAIN 分析 + 索引优化；深分页用 **"延迟关联"**——先按主键定位 id 再回表。

**【标准答】**
- **开启慢查询**：
  ```sql
  SET GLOBAL slow_query_log = ON;
  SET GLOBAL long_query_time = 1;  -- 1 秒
  SET GLOBAL log_queries_not_using_indexes = ON;
  -- my.cnf
  slow_query_log_file = /var/log/mysql/slow.log
  ```
- **mysqldumpsa 工具**分析：`mysqldumpslow -s t slow.log` 按时间排序
- **深度分页优化**：
  ```sql
  -- ❌ 慢：扫前 100 万 + 排序
  SELECT * FROM orders ORDER BY id LIMIT 1000000, 10;

  -- ✅ 子查询延迟关联
  SELECT * FROM orders o
  JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 10) t
  ON o.id = t.id;
  -- 子查询只查 id（覆盖索引），回表只 10 次
  ```

**【易错点】**
- ❌ "深分页必须用搜索引擎" → ✅ 百万级延迟关联就够；千万级才考虑 ES

## 七、架构与高可用（Q21-Q23）

### Q21 · 主从同步原理（⭐⭐⭐⭐）

**【一句话答】** 主库写 binlog → 从库 IO 线程拉 binlog 存 relay log → SQL 线程重放 relay log；5.6+ 改 **多线程**（按库并行）。

**【标准答】**
- **三线程模型**（传统）：
  - 主库 binlog dump 线程
  - 从库 IO 线程（拉 → 写 relay log）
  - 从库 SQL 线程（读 relay log → 重放）
- **5.6+ 多线程复制**：基于 `slave_parallel_workers` + `slave_parallel_type=LOGICAL_CLOCK`（按库并行）
- **8.0 增强**：writeset-based 并行（按事务冲突检测）
- **同步模式**：
  - 异步（默认）：主库不等从库 → 可能丢数据
  - 半同步（`rpl_semi_sync`）：主库等至少一个从库 ack → 性能损失 10-30%
  - 全同步：所有从库 ack（很少用）
- **主从延迟**：`SHOW SLAVE STATUS` 看 `Seconds_Behind_Master`

**【易错点】**
- ❌ "MySQL 默认半同步" → ✅ 默认**异步**
- ❌ "读写分离能解决延迟" → ✅ 延迟不可避免，只能"接受 + 监控"

---

### Q22 · 分库分表策略 + ShardingKey（⭐⭐⭐⭐）

**【一句话答】** 垂直拆分（按业务 / 列）+ 水平拆分（按行 / 数据量）；ShardingKey 选择查询最频繁的列（如 user_id），避免跨库 join / 分布式事务。

**【标准答】**
- **垂直拆分**：
  - 垂直分库：按业务（用户库 / 订单库 / 商品库）
  - 垂直分表：大表拆小表（冷热列分离）
- **水平拆分**：
  - 水平分库：同一业务按行分散到多库（user_id % 4 → 4 个库）
  - 水平分表：同一库内按行分散到多表（user_id % 16 → 16 张表）
- **拆分策略**：
  - 哈希：`HASH(user_id) % N`（均匀，但扩缩容要 rehash）
  - 范围：`0-1kw → APP/1`，`1kw-2kw → APP/2`（范围查询友好）
  - 一致性哈希：扩缩容只影响相邻节点
- **ShardingKey 选择**：高频查询字段（user_id）、区分度高、不会变化
- **带来的问题**：跨库 JOIN / 分布式事务 / 全局 ID / 跨库聚合 → 用中间件（Sharding-JDBC / MyCat / DRDS）

**【易错点】**
- ❌ "分表后性能自动提升" → ✅ 错误 ShardingKey → 跨节点扫描 → 反而更慢
- ❌ "分库分表能解决一切" → ✅ 优先考虑：读写分离、缓存、SQL 优化；分库分表是最后手段

---

### Q23 · 读写分离 + 分布式全局 ID（⭐⭐⭐⭐）

**【一句话答】** 读写分离 = 主写从读（缓解主库压力）；分布式全局 ID = 雪花算法 / Leaf 段 / 号段模式，保证分布式唯一且趋势递增。

**【标准答】**
- **读写分离**：
  - 主库承担写，从库承担读（多个从库可水平扩展读）
  - 实现：MyBatis 拦截 / Sharding-JDBC / 自研中间件 / ProxySQL
  - 延迟：主从同步延迟（ms~s）→ 写后立即读可走主库
- **分布式 ID 方案**：
  - **UUID**：简单但无序、占空间（不推荐）
  - **数据库自增**：单点、瓶颈
  - **雪花算法**（Snowflake）：1 bit 符号 + 41 bit 时间戳 + 10 bit 机器 + 12 bit 序列；趋势递增、分布式唯一
  - **Leaf 段**（美团）：号段模式，每次取一段；性能极高（一次 DB 取一批）
  - **Redis INCR**：原子自增，依赖 Redis
  - **业务拼接**：时间戳 + 业务前缀 + 随机

**【易错点】**
- ❌ "雪花算法有 64 位永远不重复" → ✅ 12 bit 序列号限制**单节点单毫秒 4096 个**，超出会等下毫秒或回拨
- ❌ "读写分离能解决写瓶颈" → ✅ **写仍是单点主库**；写瓶颈要分库分表

## 八、实战题（Q24-Q25）

### Q24 · 行转列 + TopN（⭐⭐⭐⭐）

**【一句话答】** 行转列用 `CASE WHEN / IF / GROUP_CONCAT` 或 `PIVOT`；TopN 用窗口函数 `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)` 取 rn=1。

**【标准答】**
- **行转列**（学生成绩）：
  ```sql
  SELECT name,
    MAX(CASE WHEN subject='语文' THEN score END) AS 语文,
    MAX(CASE WHEN subject='数学' THEN score END) AS 数学,
    MAX(CASE WHEN subject='英语' THEN score END) AS 英语
  FROM scores GROUP BY name;
  ```
- **TopN**（每个部门工资前 3）：
  ```sql
  SELECT * FROM (
    SELECT  *, ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rn
    FROM employee
    ) t WHERE rn <= 3;
  ```
- **RANK vs DENSE_RANK vs ROW_NUMBER**：
  - ROW_NUMBER：1, 2, 3（无并列）
  - RANK：1, 1, 3（并列后跳号）
  - DENSE_RANK：1, 1, 2（并列不跳号）

**【易错点】**
- ❌ "TopN 只能用 LIMIT" → ✅ LIMIT 不能 PARTITION；窗口函数才行
- ❌ "GROUP_CONCAT 能行转列" → ✅ 可以，但只是字符串拼接，不便后续聚合

---

### Q25 · 连续 N 天登录（⭐⭐⭐⭐⭐）

**【一句话答】** 用窗口函数 `ROW_NUMBER()` 算登录日期差 → 减去 rn 得到**组标识** → 按组 `COUNT(DISTINCT date) >= N`。

**【标准答】**
```sql
-- 找连续登录 ≥ 7 天的用户
WITH ranked AS (
  SELECT user_id, login_date,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date) AS rn
  FROM login_logs
),
grouped AS (
  SELECT user_id, login_date,
    DATE_SUB(login_date, INTERVAL rn DAY) AS grp  -- 同组的 grp 相同
  FROM ranked
)
SELECT user_id, MIN(login_date) AS start_date, MAX(login_date) AS end_date,
       COUNT(*) AS continuous_days
FROM grouped
GROUP BY user_id, grp
HAVING COUNT(*) >= 7;
```
- **核心技巧**：`date - rn` 把连续日期映射到同一常量 → 同一组
- **变种**：留存率（同一天再次登录）→ 用 JOIN + DATEDIFF

**【易错点】**
- ❌ "连续登录要用 LEAD/LAG" → ✅ 那算"两次登录间隔"，不是连续 N 天
- ❌ "grp 要类型转换" → ✅ DATE_SUB 出来还是 date，能直接 GROUP BY
