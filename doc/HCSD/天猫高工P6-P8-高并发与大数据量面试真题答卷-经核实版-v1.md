### Q1 · 高并发系统怎么设计（⭐⭐⭐⭐⭐）

> 🎯 **30 秒脚本**：先问量化目标——多高 QPS、多少 RT、可用性几个九，没数字的设计都是堆技术。然后分层作答：**流量往下压一层一层削**——接入层 CDN + 动静分离 + 负载均衡；应用层无状态横向扩 + 多级缓存 + 异步化；数据层读写分离、分库分表。最后补一句：**缓存、限流熔断、全链路压测**是三道护城河，大促前必须真刀真枪压过。

**🔧 弹药库**

| 层 | 手段 | 一句话原理 |
|---|---|---|
| 接入层 | CDN、动静分离、LVS/Nginx 负载均衡 | 静态内容推到离用户最近的地方；流量均摊到多台机器 |
| 应用层 | 无状态 + 横向扩 | 没有本地状态才能随便加机器 |
| | 多级缓存（本地+Redis） | 读请求尽量不落 DB |
| | 异步化（MQ 削峰） | 写路径只做一次落消息，消费者按自己节奏追 |
| 数据层 | 读写分离、分库分表、热点缓存 | 单机 DB 撑不住就拆 |
| 护城河 | 限流（保命）→ 熔断降级（止损）→ 全链路压测（验真） | 流量超过容量时有序放弃，而不是雪崩 |

**⚠️ 坑位**
- ❌ 一上来堆名词（Redis、Kafka、K8s 全家桶）→ ✅ 先给数字再谈选型："先算峰值 QPS 和单机容量，除出机器数，再谈每一层用什么"
- ❌ 高并发 = 什么技术都上 → ✅ **高并发的第一原则是减少到达数据库的流量**，缓存和异步永远排在最前

**📎 口诀**：*流量层层削：CDN 挡、缓存挡、异步挡，挡不住的才到 DB；挡不住流量就限流，挂了就熔断，大促前压测验真。*

### Q2 · 缓存穿透 / 击穿 / 雪崩（⭐⭐⭐⭐⭐）

> 🎯 **30 秒脚本**：三个问题一句话区分——**穿透是查"压根不存在"的数据，击穿是"一个热 key"过期，雪崩是"一大片 key"同时过期或 Redis 整个挂了**。穿透用空值缓存 + 布隆过滤器挡；击穿用互斥锁重建或逻辑过期；雪崩靠随机 TTL、集群高可用、多级缓存兜底。

**🔧 弹药库**

| 问题 | 场景 | 药方 |
|---|---|---|
| 穿透 | 恶意请求 id=-1 / 爬虫遍历不存在的 key，每次都打穿到 DB | ① 缓存空值（短 TTL 30s~2min）② 布隆过滤器前置（说"没有"就真没有）③ 入口参数校验 + 限流 |
| 击穿 | 秒杀商品 key 正好过期，万级并发同时回源 DB | ① 互斥锁（SETNX，拿到锁的查库回填，其他等待）② 逻辑过期（物理不过期，值里带过期时间，发现过期就异步刷新）③ 热点数据干脆不过期 |
| 雪崩 | 大量 key 同一时刻过期；或 Redis 实例宕机 | ① TTL 加随机数（基础值 ±10%~30%）② 哨兵/集群保证高可用 ③ 多级缓存（本地兜一层）④ 真挂了走限流+降级，别把 DB 打死 |

**⚠️ 坑位**
- ❌ 分不清击穿和雪崩 → ✅ 记 **"一个 vs 一片"**：击穿是一个热 key，雪崩是一批 key 或整个缓存
- ❌ 布隆过滤器 100% 准 → ✅ 有**假阳性**（说有其实没有，多查一次库而已），**无假阴性**（说没有就一定没有）——所以它只能挡穿透，不能当数据库
- ❌ 空值缓存会造成数据不一致 → ✅ 空值 TTL 必须短（分钟级），且新增数据时主动删掉空值

**📎 口诀**：*穿透空值加布隆，击穿加锁逻辑过期，雪崩随机加集群，最后限流来兜命。*

### Q3 · 缓存与数据库一致性（⭐⭐⭐⭐⭐）

> 🎯 **30 秒脚本**：主流是 **Cache Aside**：读——缓存没有就查库回填；写——**先更新数据库，再删除缓存**。选"删"不选"更"是因为并发写会乱序覆盖、且懒加载省内存；选"DB 先行"是因为反过来（先删缓存）的不一致窗口更大。极端并发下的残留不一致，用**延迟双删**或**订阅 binlog（Canal）异步删**兜底；要强一致就得上分布式锁串行化，代价太大一般不干。

**🔧 弹药库**

| 方案 | 做法 | 评价 |
|---|---|---|
| Cache Aside（基本盘） | 写：更 DB → 删缓存 | 简单，最终一致；极端并发仍有毫秒级窗口 |
| 延迟双删 | 更 DB → 删缓存 → sleep 几百 ms → 再删一次 | 消掉"从库旧数据被回填"的窗口；间隔=主从延迟+buffer |
| binlog 订阅（Canal） | Canal 伪装成 MySQL 从库收 binlog → 删缓存 | 业务零侵入、不丢变更；准实时 |
| 强一致 | 读写都走分布式锁串行 | 性能倒退，一般只用于钱相关的极小范围 |

**⚠️ 坑位**
- ❌ "更新缓存"比"删除缓存"更快 → ✅ 并发写时更新会**乱序覆盖**（A 的旧值后到，把 B 的新值盖掉）；删除是无害的懒加载
- ❌ 延迟双删 = 100% 一致 → ✅ 只能极小化窗口；**缓存这层天生是最终一致**，面试敢说"100%"直接扣分
- 追问"为什么是先 DB 后缓存？"→ 先删缓存的话，"删完 → DB 还没更完"之间来的读请求会把**旧值**查出来回填，且这个窗口是普通业务节奏就能踩到的；反过来出问题需要"写 DB 极快 + 缓存恰好过期 + 读写交叉"多个巧合叠加

**📎 口诀**：*更库删缓存，DB 打头阵；双删补窗口，binlog 兜尾巴。*

### Q4 · 热 key / 大 key（⭐⭐⭐⭐）

> 🎯 **30 秒脚本**：热 key 是**一个 key 扛了极高流量**（爆款商品页），会把单个 Redis 节点的带宽和 CPU 打满；解法：本地缓存再兜一层、key 打碎成 N 份、用热点探测系统提前发现。大 key 是 **value 过大**（百万级集合），会拖慢单线程查询、阻塞主从同步和删除；解法：拆分、压缩、用 UNLINK 异步删。

**🔧 弹药库**

| | 热 key | 大 key |
|---|---|---|
| 判定 | 单 key QPS 过万 / 单节点带宽打满 | string > 10KB、集合元素 > 5000（行业惯例值） |
| 怎么发现 | `redis-cli --hotkeys`（LFU 策略）、客户端埋点统计、京东 hotkey 探测 | `redis-cli --bigkeys`、RDB 离线分析 |
| 危害 | 缓存击穿、单节点过载 | 慢查询阻塞 worker、主从同步延迟、集群迁移卡顿、删除阻塞 |
| 解法 | ① 本地缓存（Caffeine）兜底 ② key 打碎：`key#1..#N` ③ 热点探测+预热 ④ 读写分离分摊读 | ① 按业务/哈希拆成多个小 key ② 压缩 value ③ 删除用 `UNLINK`（4.0+ 异步） |

**⚠️ 坑位**
- ❌ 热 key 加机器就能救 → ✅ 热 key 天然落在一个分片上，**加 Redis 节点没用**，要靠打碎或本地缓存
- ❌ `DEL` 大 key 没事 → ✅ 同步 DEL 可能卡住主线程几百毫秒，生产用 `UNLINK`

**📎 口诀**：*热 key 打碎加本地，大 key 拆分 UNLINK。*

### Q5 · 多级缓存（Caffeine + Redis）（⭐⭐⭐⭐）

> 🎨 **30 秒脚本**：请求先查本地 Caffeine（纳秒级），miss 再查 Redis（亚毫秒），最后 DB；Redis 的 QPS 再高也有网络往返，本地缓存能把最热的那部分流量直接消化在 JVM 里。代价是**多台机器的本地缓存可能不一致**，用"MQ/Redis 订阅广播失效 + 短 TTL 兜底 + 业务容忍秒级窗口"解决。

**🔧 弹药库**

| 点 | 要点 |
|---|---|
| 为什么快 | L1 省掉网络往返；Caffeine 用 **W-TinyLFU** 淘汰算法，命中率比 LRU 高（抗偶发扫描） |
| 一致性三招 | ① 写后发 MQ/pub-sub 广播各机失效 ② 本地 TTL 设短（秒级），自然收敛 ③ 按业务评估容忍窗口（配置/字典类数据秒级不一致完全可接受） |
| 适合放 | 读多写少、可容忍短暂旧值：商品类目、配置、字典、热点活动信息 |
| 不适合放 | 库存、订单状态等要求即时的数据 |
| 实战锚点 | 长行渠道 P99 800→150ms，**第一刀就是缓存**（Redis 热点数据 + 本地字典缓存），第二刀才是异步化 |

**⚠️ 坑位**
- ❌ 全部数据都上多级缓存 → ✅ 本地缓存只给"读多写少 + 容忍旧值"的数据，不然失效风暴比查库还疼
- 追问"LRU 和 W-TinyLFU 区别"→ LRU 容易被偶发批量扫描污染（扫一遍就把真热点挤出去）；TinyLFU 用频次近似（Count-Min Sketch）淘汰，新人要先证明自己比老住户"常用"才能上位

**📎 口诀**：*本地纳秒、Redis 毫秒、DB 兜底；广播失效、短 TTL 兜住不一致。*

### Q6 · 限流：四大算法 + 分布式限流（⭐⭐⭐⭐⭐）

> 🎨 **30 秒脚本**：四个算法是逐步进化的——**固定窗口**有临界突刺问题（上一秒末尾+下一秒开头能过双倍流量）；**滑动窗口**把窗口切格子滚动统计，解决突刺（Sentinel 默认 1 秒切 2 格、每格 500ms）；**漏桶**恒定流速放行，绝对平滑但应对不了合理突发；**令牌桶**恒定速率发令牌、桶能攒令牌，**平时稳、突发能扛**，最常用。分布式限流用 Redis + Lua 原子扣减。

**🔧 弹药库**

| 算法 | 特点 | 适用 |
|---|---|---|
| 固定窗口计数 | 最简单；临界点双倍突刺 | 要求不高的接口级计数 |
| 滑动窗口 | 格子滚动，精度取决于格子数 | Sentinel 的 QPS 统计（默认 1s × 2 格 500ms，**已核实**） |
| 漏桶 | 恒定流出 | 对下游脆弱系统匀速保护（如调用三方接口） |
| 令牌桶 | 恒定流入 + 桶容量缓冲突发 | 网关/通用场景（Guava RateLimiter） |

| 层次 | 做法 |
|---|---|
| 单机 | Guava RateLimiter（令牌桶）/ Sentinel（滑窗+丰富规则+控制台） |
| 分布式 | Redis + Lua：脚本里原子地"读计数-判断-扣减"，多实例共享一个桶 |
| 部署层次 | 网关限总量 → 接口限单资源 → 用户维度（userId 分桶，配合布隆过滤器防伪造） |

**⚠️ 坑位**
- ❌ "漏桶比令牌桶先进" → ✅ 没有绝对先进，**漏桶求稳、令牌桶容突发**，看保护对象是谁
- ❌ 分布式限流 = 每个服务自己限 → ✅ 各自限的是局部，总和可能仍超；要全局总量就得上 Redis 集中计数（代价：每次请求多一跳 Redis）
- 追问"Sentinel 和 Guava 怎么选"→ Guava 是纯单机算法库；Sentinel 有规则中心、集群流控、熔断降级全家桶，微服务选它

**📎 口诀**：*固定有刺、滑动平滑、漏桶恒速、令牌容突；全局总量 Redis+Lua。*

### Q7 · 熔断、降级、隔离（⭐⭐⭐⭐）

> 🎨 **30 秒脚本**：熔断器三态循环：**关闭 →（失败率/慢调用超阈值）→ 打开（快速失败走 fallback，不再打下游）→ 熔断时长后 → 半开（放少量探测请求，成功就关闭恢复）**。降级是有损服务：非核心功能先死（推荐/评论给兜底文案）、读走旧缓存；核心靠**大促预案的人工开关**兜底。隔离分线程池隔离（重、彻底）和信号量隔离（轻、Sentinel 默认）。

**🔧 弹药库**

| 机制 | 关键点 |
|---|---|
| 熔断触发条件 | 慢调用比例 / 异常比例 / 异常数（Sentinel 三种策略） |
| 半开恢复 | 打开后等熔断时长（如 10s）自动进入半开，放探测请求，达标恢复、不达标继续熔断 |
| 降级优先级 | 保交易、砍周边：评价→静态文案、推荐→热门榜、搜索→默认结果；可自动（规则）+ 可手动（预案开关） |
| 隔离 | 线程池隔离：每个下游独立线程池，一个下游挂不影响别的（Hystrix 默认）；信号量隔离：只限并发数，轻量（Sentinel 默认） |
| 实战锚点 | 长行渠道：核心交易链路保留，外围展示类接口配 Sentinel 降级规则 + 手动预案开关 |

**⚠️ 坑位**
- ❌ 熔断就是抛异常 → ✅ 熔断期间走 **fallback（兜底逻辑）**，抛异常给用户是最后一步
- ❌ 降级全是自动的 → ✅ **大促预案靠人工开关**——自动规则管波动，人管极端场景（比如主动砍掉优惠券列表）
- 追问"Hystrix 为什么被淘汰"→ 线程池隔离太重（排队/上下文切换开销）、停止维护；Sentinel 信号量+滑窗更轻，还有流控/热点/系统自适应保护

**📎 口诀**：*关-开-半开三态转，失败超阈就跳闸；保交易砍周边，自动规则+人工开关。*

### Q8 · MQ 削峰：事务消息 / 积压 / 顺序（⭐⭐⭐⭐⭐）

> 🎨 **30 秒脚本**：异步削峰的本质是**把同步长链变成一次消息落盘**——下单接口只写一条 MQ 消息就返回，订单、积分、通知各自按自己的消费能力追。**事务消息**解决"业务库和 MQ 双写不一致"：先发 half 消息 → 执行本地事务 → commit/rollback，宕机了靠回查补偿。**积压**先看瓶颈：消费者数受队列数上限约束（Kafka 一个分区最多一个消费者），扩消费者之前可能得先扩分区。

**🔧 弹药库**

| 问题 | 要点 |
|---|---|
| 不丢消息三段 | 生产端：事务/重试；Broker：同步刷盘+多副本；消费端：手动 ack + **消费幂等**（at-least-once 是底，幂等凑出 effect-once） |
| 事务消息（RocketMQ） | half 消息（对消费者不可见）→ 本地事务 → 二次确认；宕机走**回查**（broker 反查生产者事务状态） |
| 顺序消息 | 同一业务 key（orderId）hash 到**同一队列**，队列内单线程消费 → 局部有序够用 |
| 积压处理 | ① 消费者数 < 队列数 → 加消费者 ② 到顶了 → 扩分区/队列 + 快速搬迁堆积数据 ③ 提批量 + 并发消费 ④ 旁路掉非核心订阅 ⑤ 最狠：新 topic + 临时消费者只落盘，事后离线补 |
| 选型一句话 | RocketMQ：事务/延迟/重试消息，电商业务友好；Kafka：超高吞吐、日志流处理 |

**⚠️ 坑位**
- ❌ 积压了无脑加消费者 → ✅ **消费并行度上限 = 队列/分区数**，加到上限再加是浪费；先确认瓶颈在并行度还是单条处理耗时
- ❌ "MQ 配置好了就不会丢" → ✅ 生产、存储、消费**三段各自都可能丢/重**，端到端不丢要三段一起设防
- 追问"为什么用 MQ 不用线程池异步"→ 线程池异步**机器一重启任务就没了**（内存态）；MQ 是持久化 + 可重放 + 跨服务解耦

**📎 口诀**：*同步变异步，落盘即返回；half-回查保双写，并行上限是队列数。*

### Q9 · 秒杀防超卖（⭐⭐⭐⭐⭐）

> 🎨 **30 秒脚本**：先讲流量漏斗——亿级曝光到几十万单，每层削一个数量级，**真正到达库存系统的流量很小**，这是设计前提。防超卖三层：**DB 行锁兜底**（`update stock set n=n-1 where id=? and n>0`，慢但绝对不卖超）→ **性能层 Redis+Lua 原子预扣**（check+deduct 一个脚本一次往返，比分布式锁少两次网络往返）→ **爆款库存分片**（100 件拆 10 个 key，热 key 也打散）。扣完发 MQ 异步创建订单，超时未支付用延迟消息回滚库存。

**🔧 弹药库**

| 环节 | 方案 |
|---|---|
| 前端/接入 | 按钮置灰防连点、答题/验证码削峰、CDN 静态化、网关限流 |
| 库存预扣 | Redis Lua：`if stock>0 then decr` 原子执行；为什么不用分布式锁：锁要加锁+解锁两次往返且其他线程自旋等，Lua 一次往返串行执行 |
| 库存分片 | `stock_1..stock_10`，扣完一个换下一个；前端看到"售罄"前先本地标记 |
| 异步下单 | 预扣成功 → 发 MQ → 订单服务落库 → 前端轮询/推送结果（"排队中"体验） |
| 幂等与回补 | 下单去重（唯一业务单号）；超时未支付延迟消息回滚 Redis 库存；对账 job 兜底差异 |
| DB 兜底 | 行锁 `where n>0` 是最终防线，即使 Redis 全崩也只是慢、不会超卖 |

**⚠️ 坑位**
- ❌ 只答"用分布式锁" → ✅ 面试官想听**分层**：锁是最贵的方案，能原子就原子、能异步就异步
- ❌ 忘了回滚 → ✅ 扣了库存没下单成功必须还回去（延迟消息/对账），否则"少卖"
- 追问"Redis 挂了怎么办"→ 降级 DB 行锁 + 接口限流，**宁可卖慢、不可超卖**

**📎 口诀**：*漏斗先削流，Lua 原子扣，分片散热 key，MQ 异步落，行锁兜住底。*

### Q10 · 线程池 / 连接池：池化调优（⭐⭐⭐⭐）

> 🎨 **30 秒脚本**：池化的本质是**复用昂贵资源**——线程创建、TCP 握手、DB 认证都很贵，池子把它摊平。线程池参数不背公式靠压测：参考公式是 `N×U×(1+W/C)`（线程数由 CPU 数、目标利用率、等待/计算比决定），IO 密集通常远大于核数，但**最终以压测为准**；生产要配监控（活跃/队列/拒绝数）和动态调参（配置中心推送）。连接池不是越大越好，HikariCP 默认才 10。

**🔧 弹药库**

| 池 | 关键参数 | 实践 |
|---|---|---|
| 线程池 | 7 参数 4 策略（详见飞猪篇 Q7） | ① 压测定大小 ② 监控暴露 active/queue/reject 指标 ③ 动态化：Nacos 推 core/max/queue 实时生效（美团 dynamic-tp 思路）④ 队列用有界，防 OOM |
| DB 连接池 | HikariCP：maximumPoolSize 默认 10 | 官方公式 `connections = core_count*2 + effective_spindle_count`；连接太多反而坏：MySQL 每连接耗内存、上下文切换、锁竞争加剧 |
| Redis/HTTP 连接池 | 最大连接、等待队列、超时 | 连接获取要设超时，拿不到快速失败别无限等 |

**⚠️ 坑位**
- ❌ "IO 密集设 2N"（N=核数）→ ✅ 2N 只是老经验值，正确姿势是**算 W/C + 压测**，飞猪篇审计过这条
- ❌ 线程池满了配 CallerRuns 万事大吉 → ✅ CallerRuns 是把流量推回调用者（背压），网关类服务用它会拖慢上游；要区分核心链路（Abort+告警+快速失败）和非核心（Discard）
- 追问"为什么 HikariCP 快"→ 字节码级精简、FastList/ConcurrentBag 定制数据结构（答出方向即可）

**📎 口诀**：*参数靠压测，监控加动态；连接池宁小勿大，队列必须有界。*

### Q11 · 深分页：limit 1000000,10 为什么慢（⭐⭐⭐⭐⭐）

> 🎨 **30 秒脚本**：MySQL 会**真地把前 100 万行取出来、走完回表和排序，然后扔掉**，只留最后 10 行——偏移量越大白干的越多。四招：**书签续读**（记住上一页最大 id，`where id > ? limit 10`，把翻页改成滚动加载）；**延迟关联**（先用覆盖索引把 10 个 id 捞出来，再回表拿整行）；**ES search_after**；业务上**限制跳页**。

**🔧 弹药库**

| 方案 | SQL/做法 | 适用 |
|---|---|---|
| 书签/续读 | `where id > #{lastMaxId} order by id limit 10` | 交互可改成"下一页"（信息流/导出），性能最优 O(10) |
| 延迟关联 | `select t.* from t join (select id from t where c=? order by id limit 1000000,10) x on t.id=x.id` | 必须支持跳页的 C 端列表；子查询走覆盖索引不回表，白做的部分代价骤降 |
| ES search_after / scroll | 用上一页排序值续读 | 检索类列表；scroll 给离线导出 |
| 业务限制 | 禁止跳到 N 页 / 只给前 100 页 | 大厂真实做法（淘宝订单也只给最近 3 个月） |

**⚠️ 坑位**
- ❌ "加个索引就好了" → ✅ 索引救不了 offset——优化器仍要**数过**前 100 万行才能偏移
- ❌ 延迟关联是 O(1) → ✅ 子查询还是要扫过 offset+limit 个索引条目，只是**扫的是窄索引**，快一个量级但不是免费
- 追问"ES 为什么也深分页慢"→ from+size 要在每个分片取 from+size 条汇聚，默认上限 10000；search_after 每次只取一页

**📎 口诀**：*offset 是白干：书签最优、延迟关联兜跳页、search_after 给搜索、砍跳页是正道。*

### Q12 · 百万级批量插入优化（⭐⭐⭐⭐⭐）

> 🎨 **30 秒脚本**：第一刀**加 `rewriteBatchedStatements=true`**——MySQL JDBC 驱动默认把 batch 拆成一条条发，加了这个参数才真正拼成 `multi-values` 一条 SQL，实测能快一个数量级；第二刀**每批 500~1000 条**、分批提交事务；第三刀还不够就**多线程按 id 区间并行**（各拿各的连接），再往上走 DataX / `load data`。重跑要幂等：批次号 + 临时表。

**🔧 弹药库**

| 手段 | 细节 |
|---|---|
| rewriteBatchedStatements | Connector/J 5.1.7+；把 `insert` 批量改写成 `insert values(...),(...),...`；对 `update/delete` 是改写成 multi-statement（收益小一些） |
| 批大小 | 500~1000 起步实测调优；过大撞 `max_allowed_packet`、SQL 解析内存上升 |
| 事务 | 千万别一条一提交（每次 fsync）；也别一个百万级大事务（undo 膨胀、主从延迟）：**每 N 批一提交** |
| 多线程 | 按主键区间切 20 片 × 10 线程；每线程独立连接；盯着主从延迟和磁盘 util 调速 |
| 更大规模 | DataX / load data infile / Canal 同步：**换工具别硬写代码** |
| 幂等重跑 | 作业表记批次水位；或写 staging 表校验后原子 rename/merge |

**⚠️ 坑位**
- ❌ "MyBatis-Plus 的 saveBatch 就是批量" → ✅ 不加 rewriteBatchedStatements 它还是逐条发，快不了；**参数才是开关**
- ❌ 批次越大越快 → ✅ 收益递减、风险递增（包上限/解析开销），压测找拐点
- 追问"为什么不用 insert select"→ 源头不在同一个库/要业务转换时走应用层；同库纯搬运用 SQL 最快

**📎 口诀**：*一条参数提十倍，五百一千分批喂，事务分段幂等跑。*

### Q13 · 千万级大表在线 DDL（⭐⭐⭐⭐）

> 🎨 **30 秒脚本**：先看能不能用 MySQL 自己的：**8.0 加列是 INSTANT 秒级**；5.7 加索引走 INPLACE，全程允许并发 DML，但**收尾瞬间要拿 MDL 排他锁**——这时候最怕一个长事务把 MDL 队列堵死，全表读写全卡。改不动的（改列类型等）用 **gh-ost**（影子表+binlog 追增量，无触发器、可随时暂停）或 **pt-osc**（触发器方案）。流程：低峰、留 2 倍空间、从库先试、限速切换、留回滚。

**🔧 弹药库**

| 方案 | 原理 | 优缺点 |
|---|---|---|
| Online DDL（INPLACE） | 就地重建/建索引，允许并发 DML | 原生、简单；收尾 MDL 短锁；大表耗时长、占资源 |
| INSTANT（8.0） | 只改元数据 | 加列秒级；支持场景有限 |
| gh-ost | 影子表 + **解析 binlog** 回放增量 → 增量追平后原子 rename 切换 | 无触发器、可限速/暂停/随时终止、对主库侵入小（GitHub 出品） |
| pt-osc | 影子表 + **三个触发器**同步增量 | 老牌成熟；高写入下触发器写放大明显 |

**标准动作**：变更评审（影响行数/空间翻倍/时长预估）→ 从库灰度验证 → 低峰执行+限速 → 切换 → 观察主从延迟 → 预案（失败回退旧表，rename 是原子可逆的）。

**⚠️ 坑位**
- ❌ "Online DDL 完全不锁表" → ✅ **首尾各有一次 MDL 短锁**；长事务/慢查询会把队列堵死，DDL 前先杀长事务（`information_schema.innodb_trx`）
- ❌ gh-ost 一定比 pt-osc 好 → ✅ gh-ost 依赖 binlog 格式（ROW）且要额外 binlog 带宽；触发器方案在高写入表上反而更差——**看表的写入画像选**

**📎 口诀**：*8.0 加列 INSTANT，索引 INPLACE 防 MDL 堵；改不动的 gh-ost，低峰限速留退路。*

### Q14 · 分库分表：时机、分片键、扩容（⭐⭐⭐⭐⭐）

> 🎨 **30 秒脚本**：时机——阿里手册建议**单表超 500 万行或 2GB 才推荐分库分表**（已核实），但先确认索引和归档救不救得了，拆表是不可逆的大动作。分片键选**最高频查询维度**（订单表选 user_id）；非分片键的查询靠**基因法**（orderId 里揉进 user_id 尾数，两个维度都能路由）、异构索引 ES、或宽表冗余。扩容走成倍扩 + 双写迁移；主键用雪花。

**🔧 弹药库**

| 问题 | 要点 |
|---|---|
| 垂直 vs 水平 | 垂直按业务拆库（订单库/用户库）；水平按分片键拆行（order_0..order_63） |
| 分片键怎么选 | 查询最集中的维度；避免热点（大买家加盐、订单按 user_id 不按时间） |
| 非分片键查询 | ① 基因法：orderId = 雪花 + user_id 后 6 位（两种路由）② ES 二级索引异构 ③ 冗余宽表/广播表（字典类小表每库一份） |
| 扩容 | 64→128 成倍扩，翻倍时旧数据一半不用动；ShardingSphere 支持迁移；**上线前就按 2 的幂设计** |
| 分布式 ID | 雪花：1+41(时间戳)+10(机器)+12(序列)，趋势递增利索 B+ 树；时钟回拨→等待/漂移号，或用 Leaf/UidGenerator |
| 跨片难题 | 跨片分页：各片取 top-N 汇聚重排（深页成本高，业务改 ES）；跨片事务：尽量同键落同库，跨了走最终一致（本地消息表/Seata AT |
| 中间件 | ShardingSphere-JDBC（客户端层，无代理）为主流；代理层（MyCat/ShardingSphere-Proxy）适合异构语言 |

**⚠️ 坑位**
- ❌ 数据到千万就赶紧拆 → ✅ **B+ 树千万级配合好索引完全能打**，先 explain、先归档；拆表带来的跨片查询/事务成本是长期的
- ❌ 先用自增主键上 AB 分片 → ✅ 自增 ID 和分片路由耦合后扩容极难；**先定 ID 策略再定分片**
- 追问"为什么雪花 ID 比 UUID 好"→ 趋势递增，B+ 树顺序追加不分裂；UUID 无序，插入页分裂+索引膨胀

**📎 口诀**：*五百万两 GB 才动刀；键选最高频，基因揉两可，成倍扩不搬家。*

### Q15 · 亿级数据平滑迁移（⭐⭐⭐⭐⭐）

> 🎨 **30 秒脚本**：五步走——**存量搬迁 → 增量双写 → 对账 → 灰度切读 → 切写收尾**，全程业务无感。关键次序：**先双写再搬存量**（反过来中间增量会丢）。存量按 id 区间分片限速搬；增量用 binlog（Canal）双写零侵入；对账做全量 checksum+增量实时校验，差异按片修复；读流量 1%→100% 灰度，双写一直保留到观察期满，回滚就是把开关拨回去。

**🔧 弹药库**

| 步骤 | 做法 | 坑位提示 |
|---|---|---|
| ① 存量搬迁 | id 区间切片（如每 1 万一批）、限速（盯主从延迟/IO util）、断点续跑（水位表） | 大字段单独处理，避免单行过大 |
| ② 增量双写 | 首选 Canal 伪装从库收 binlog→写新库（零侵入）；或业务代码双写（改造侵入但可控） | 双写失败要有补偿队列，不能静默丢 |
| ③ 对账 | 全量：分片 checksum 比对；增量：实时抽样比对+差异修复任务 | ❌ 只比行数——**内容 checksum 才算数** |
| ④ 灰度切读 | 配置中心开关，按用户/机器维度 1%→10%→100% | 每档观察 RT/错误率/对账差异 |
| ⑤ 收尾 | 切写（新库主写、旧库停写）→ 双写再留一个业务周期 → 旧库降级归档 | 切写前**预案演练**必须做过一次 |

**⚠️ 坑位**
- ❌ "先搬完数据再开始双写" → ✅ 搬迁耗时段内的增量会漏；**binlog 位点先记好（甚至先启双写），再搬存量**，对账兜漏网
- ❌ 迁移完成立刻下线旧库 → ✅ 至少留一个完整业务周期（月结/大促）双写观察
- 追问"Canal 原理"→ 伪装成 MySQL slave，走主从复制协议收 binlog，解析后投递 MQ，下游消费写新库

**📎 口诀**：*先记位点再搬家，binlog 双写零侵入，对账按内容不按数，灰度切读留退路。*

### Q16 · 大表冷热分离与归档（⭐⭐⭐⭐）

> 🎨 **30 秒脚本**：订单类表线性增长，但**热点数据只有最近 3 个月**——把冷数据搬走，热表永远年轻。三档：**分区表**（按月 range，`exchange partition` 秒级摘除整月数据）→ **归档表**（orders → orders_archive，job 按 id 水位 T+1 搬）→ 更冷进 **OLAP/OSS**（分析查询别碰交易库）。查询侧按时间路由：默认只查热表，跨年查询走归档库。

**🔧 弹药库**

| 方案 | 做法 | 注意 |
|---|---|---|
| MySQL 分区表 | range 按月分区；查询带分区键才**裁剪**，否则全分区扫 | 分区键必须进主键/唯一键；单机天花板仍在 |
| 归档表 + 搬运 job | 低峰限速 delete-limit-batch 循环：按 id 水位"读一批→写归档→删一批" | 删除**必须小批量**（大事务=主从延迟+锁）；幂等水位 |
| 冷数据 OLAP | 两年前的进 ClickHouse/TiDB/OSS | 归档格式对账工具要配套 |

**⚠️ 坑位**
- ❌ 分区表是万能药 → ✅ 不带分区键的查询扫全部分区比不分区还慢；且它不解决单机容量上限（那是分库分表的事）
- ❌ `delete from t where create_time < ?` 一把梭 → ✅ 千万级删除会打爆 undo 和主从延迟；**分批 + 限速 + 低峰**
- 追问"归档怎么保证不丢不重"→ 同事务"写归档+记水位"或先写后删+对账；重了靠唯一键幂等

**📎 口诀**：*热表滚三月，按月分区摘整月；删除小批量，冷数进仓不回库。*

### Q17 · 分布式任务分片：百万级批处理（⭐⭐⭐⭐）

> 🎨 **30 秒脚本**：百万账单日终处理，单机跑又慢又是单点。用 **XXL-Job 分片广播**：一次触发，所有执行器同时收到（各自带 `shardIndex/shardTotal`），数据按 **`id % shardTotal == shardIndex`** 认领自己的份，天然并行、天然分摊。配上**限速保护 DB、水位断点幂等重跑、失败转移**。更细粒度就换 MQ：把任务拆成子消息，消费者天然并行，代价是必须幂等。

**🔧 弹药库**

| 点 | 要点 |
|---|---|
| 分片广播 | 调度中心一次下发，全部执行器触发；`XxlJobHelper.getShardIndex()/getShardTotal()` |
| 数据切法 | `where id % #{shardTotal} = #{shardIndex}`；或按 id 区间分片（区间更好控流速） |
| 限速 | 每片内 sleep/令牌桶控制 QPS，别把 DB 打出主从延迟 |
| 幂等断点 | 任务水位表记 max_id；重跑从水位续，处理本身幂等（按业务单号 upsert） |
| 失败 | XXL-Job 失败重试+故障转移（换机重跑）；告警接钉钉/电话 |
| 对比 MQ 拆分 | 任务→N 条子消息→并发消费：粒度细、自动重试；要求消费幂等，且总量控制不如分片直观 |

**⚠️ 坑位**
- ❌ 一个大任务单机跑到底 → ✅ 长事务+长连接+单点+无法水平扩；**分片是水平扩的前提**
- ❌ 分片数写死 → ✅ 扩机器后 shardTotal 变化，`id%total` 的归属全变——**水位/幂等设计必须扛住重分配**（这正是为什么幂等不是可选项）
- 追问"某台机器中途挂了"→ 故障转移把该分片调度给别的机器重跑，幂等保证重跑不重复入账

**📎 口诀**：*一次广播全员到，id 取模认领活；限速断点加幂等，挂了换人重跑。*

### Q18 · 海量数据异步导出（⭐⭐⭐⭐）

> 🎨 **30 秒脚本**：几十万行导出，同步做必死（内存 OOM + HTTP 超时）。标准是**下载中心模式**：用户提交任务 → 后台异步生成 → 文件传 OSS → 站内信/通知下载。生成侧三件套：**游标续读**（`where id > ?` 分批，别一次 select *）、**流式写**（EasyExcel/POI SXSSF，内存只留滑动窗口）、**分文件**（单文件 10 万行，zip 打包——Excel 单 sheet 上限 104 万行）。

**🔧 弹药库**

| 点 | 要点 |
|---|---|
| 交互 | 提交返回任务号 → 任务表存进度（已处理行数/总行数）→ 完成通知 + 下载链接（带过期） |
| 读取 | 主键游标分批（Q11 书签法同款）；查只读从库或 ES；JDBC 流式：`fetchSize=Integer.MIN_VALUE`（MySQL）或 `useCursorFetch=true` |
| 写入 | EasyExcel（阿里开源，滑动窗口默认刷盘）或 POI SXSSFWorkbook；千万别 XSSFWorkbook 全量堆内存 |
| 分文件 | 单 CSV/xlsx 10w 行 → zip；列多时 CSV 比 xlsx 小一个量级 |
| 失败重跑 | 水位断点；生成失败的文件直接作废重做（部分文件不可用） |
| 治理 | 大导出限流/排队（别和批处理抢连接池）、任务保留 7 天自动清理 |

**⚠️ 坑位**
- ❌ `list = mapper.selectAll()` 一次拿全量 → ✅ 几十万行直接堆爆；**分批游标 + 边读边写边丢**
- ❌ "Excel 又不是数据库，行数没限制吧" → ✅ 单 sheet **1,048,576 行**硬上限，超了直接截断丢数据——所以分文件是必须项不是优化项
- 追问"导出期间数据在变怎么办"→ 导出带条件快照语义（如按 create_time 截止值过滤），或声明"数据截至导出开始时刻"

**📎 口诀**：*异步生成 OSS 存，游标分批流式写，十万一行打包走。*

# 第三篇 · 高可用底座（Q19-Q20）

### Q19 · 高可用：双活 / 单元化（⭐⭐⭐⭐）

> 🎨 **30 秒脚本**：先背数字：**99.9% = 一年停 8.8 小时，99.99% = 一年停 52.6 分钟**。演进路线：同机房主备 → **同城双活**（两机房近同步复制，延迟 1~2ms 没压力）→ **异地多活必须单元化**：跨地域延迟几十毫秒，没法做强双写，于是**按用户切单元**——每个单元服务自己的那批用户、读写在本单元闭环，只有全局数据（商品/库存）做跨单元同步。淘宝/支付宝的 RZone（用户单元）/GZone（全局单元）就是这个思路。

**🔧 弹药库**

| 层级 | 方案 | 核心 |
|---|---|---|
| 应用层 | 无状态 + 多副本 + 健康检查摘除 | 宕机自动踢掉 |
| 数据层 | 主从+哨兵/集群自动切换；同城双活近同步 | RPO≈0（不丢）、RTO 分钟级 |
| 机房层 | 同城双活 | 两机房都干活，爆炸切换分钟级 |
| 地域层 | 异地多活 = 单元化 | 按用户分片到单元；路由标识贯穿全链路；全局数据（GZone）集中+同步 |
| 演练 | 预案平台 + 混沌工程（ChaosBlade）+ 断机房演习 | 没演练过的高可用是纸面的 |

**⚠️ 坑位**
- ❌ "异地做个双活不就行了" → ✅ 跨地域 RT 几十 ms，同步双写每笔事务 RT 翻倍、吞吐腰斩——**不单元化做不到异地多活**
- ❌ 单元化只是部署问题 → ✅ 是**架构级**改造：路由标识要贯穿 RPC/消息/缓存/DB，全局数据要识别出来集中处理
- 实战锚点：核心系统底座项目做过单元化架构设计（物理机+全栈云双架构），这题直接引自己经历

**📎 口诀**：*同城双活随便做，异地必须切用户；RZone 干活 GZone 全局，演练过的才算数。*

---

### Q20 · 全链路压测（⭐⭐⭐⭐）

> 🎨 **30 秒脚本**：大促容量的唯一可信来源是**真题真做**：在生产的全链路（应用、DB、缓存、MQ 都是真的）注入 N 倍峰值流量，看哪里先断。三个关键设计：**流量染色**（压测标识贯穿全链路——RPC 上下文透传+trace baggage，任何组件都能认出这是压测流量）；**影子隔离**（影子表 `xxx_test` 同库同索引、影子 topic、Redis key 加前缀——压测数据和真实数据同环境不同表）；**出口拦截**（短信/支付/三方调用挡死）。小流量起步阶梯加压，同时保护真实用户。

**🔧 弹药库**

| 设计 | 做法 | 为什么 |
|---|---|---|
| 流量染色 | 施压入口打标 → RPC/ThreadLocal/trace 全链路透传 | 下游每个组件靠它分流压测/真实流量 |
| 影子表 | 同库建 `order_test` 等，表结构+索引+数据量级与真实一致 | **容量结论不失真**——这是和"测试环境压测"的本质区别 |
| 影子 topic / 缓存 | 压测消息发影子 topic；Redis key 前缀 `test_` | 消息/缓存不污染生产 |
| 出口拦截 | 短信/推送/支付/三方 HTTP 挡板 | 压测流量绝不产生真实副作用 |
| 施压策略 | 1x → 3x → 5x 阶梯；每档观察容量水位（CPU/RT/错误率/DB/主从延迟） | 找到"先断的那块板"，产出扩容/预案清单 |
| 生产保护 | 限流阈值兜底真实用户；压测窗口避峰；一键停止 | 压测不能把自己压挂 |

**⚠️ 坑位**
- ❌ "测试环境压一下就够了" → ✅ 数据量级、索引分布、硬件规格全不同，**容量结论失真**；全链路压测的核心价值就是"真"
- ❌ 只压入口 QPS → ✅ 要压**完整链路**（缓存 miss、DB 慢查询、MQ 堆积互相放大），单接口压测发现不了级联雪崩
- 追问"影子表怎么同步建"→ DDL 平台跟随真实表结构自动建影子表；压测后影子数据按规约清理

**📎 口诀**：*真题真做：染色贯穿、影子隔离、出口拦死、阶梯加压。*
