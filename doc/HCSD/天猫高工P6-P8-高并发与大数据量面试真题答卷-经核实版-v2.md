### Q1 · 高并发系统怎么设计（⭐⭐⭐⭐⭐）

**【一句话答】** 先量化目标（峰值 QPS、RT、可用性几个九），再分层削减流量：接入层 CDN 与动静分离、应用层无状态横向扩展加多级缓存加异步化、数据层读写分离与分库分表，最后用限流、熔断降级、全链路压测三道防线保证过载时的有序退化。

**【标准答】**
- **第一步永远是量化**：没有数字的设计没有讨论基础。给出估算方法：
  - 峰值 QPS = 日均请求量 ÷ 86400 × 峰值系数（电商大促通常 10~30，社交类 3~5）
  - 容量目标 = 峰值 QPS × 冗余系数（1.5~2）
  - 单机容量基线（量级参考，以压测为准）：Java 应用普通 CRUD 单机约 1~2k QPS；Redis 单机 10 万 QPS 量级；MySQL 单机写入数千 QPS
  - 参照系：2020 双 11 天猫订单创建峰值 **58.3 万笔/秒**（0 点 0 分 26 秒达成，已核实）——这个量级就是靠下面的分层削减做到的
- **接入层**：CDN 扛静态资源（大促页面 90%+ 流量是静态与图片）；动静分离让动态请求最小化；LVS/Nginx 负载均衡水平分发
- **应用层**：无状态（session 外置到 Redis）才能任意加机器；读多写少的数据上多级缓存；写路径异步化（一次 MQ 落盘替代同步长链）
- **数据层**：读写分离分摊读；分库分表突破单机写上限（阈值见 Q14）；热点数据独立缓存
- **三道防线**：
  - 限流——保命：流量超容量时按优先级拒绝，保护核心
  - 熔断降级——止损：下游故障时快速失败，防止级联雪崩
  - 全链路压测——验真：容量结论只能来自生产环境真题真做（见 Q20）

**【易错点】**
- ❌ 上来罗列技术栈（Redis、Kafka、K8s）→ ✅ 先给数字与容量推算，再谈每层选型。面试官考察的是"从需求推架构"的路径，不是名词量
- ❌ 高并发等于全面上中间件 → ✅ 高并发的第一原则是**减少到达数据库的流量**。缓存与异步的优先级高于任何存储升级

**【追问怎么接】**
- "你的系统现在 5000 QPS，要扛 5 万，怎么做？" → 先算差 10 倍从哪层补：静态化+CDN 挡掉几倍、缓存命中率从 80% 提到 95% 挡掉几倍、剩下的加机器横向扩；DB 若到瓶颈先读写分离再评估分库分表。给路径，不给单一方案
- "怎么验证你扛得住？" → 全链路压测（Q20），生产环境影子流量阶梯加压，观察 RT/错误率/DB 水位，找到最先到容量上限的组件

### Q2 · 缓存穿透 / 击穿 / 雪崩（⭐⭐⭐⭐⭐）

**【一句话答】** 穿透是查询不存在的数据、缓存永远无法命中；击穿是单个热点 key 过期瞬间高并发回源；雪崩是大批 key 同时过期或缓存实例整体故障——分别用空值缓存加布隆过滤器、互斥重建或逻辑过期、随机 TTL 加高可用加多级缓存应对。

**【标准答】**
- **穿透**（查"不存在"）：
  - 空值缓存：对确认不存在的 key 写入空值，TTL 30s~2min；新增该数据时必须主动删除空值，否则出现"数据已存在但缓存说不存在"
  - 布隆过滤器前置：位数组 + k 个哈希函数。特性是**有假阳性、无假阴性**——判"不存在"一定不存在（可拦截穿透），判"存在"有误判率（误判只是多查一次库）。误判率 1% 时空间开销约 9.6 bit/元素、最优哈希数约 7 个（由公式 p ≈ (1-e^(-kn/m))^k 推出）；工程上用 Redis 的 RBloomFilter 或 Guava BloomFilter，注意 Guava 版不支持删除、数据变更需重建
  - 入口层：参数合法性校验（id ≤ 0 直接拒绝）+ 高频维度限流
- **击穿**（单热 key 过期）：
  - 互斥锁重建：SETNX 抢锁，获得锁的线程查库回填，其余线程短暂等待重读缓存。注意锁要带 TTL 防死锁、等待要有上限防线程堆积
  - 逻辑过期：物理上不设 TTL，value 内嵌过期时间字段；读到已过期就异步触发刷新、当前请求返回旧值。用秒级旧值换取零等待
  - 极热数据直接不过期 + 主动更新
- **雪崩（批量过期或实例故障）**：
  - TTL 加随机数（基础值 ±10%~30%），把过期时间打散
  - 哨兵/集群保证缓存层高可用
  - 增加本地缓存作二次防护（见 Q5）
  - 缓存整体不可用时走限流+降级，保护 DB 不被打穿——这是最后防线

**【易错点】**
- ❌ 击穿和雪崩分不清 → ✅ **一个 vs 一片**：击穿是单个热点 key，雪崩是一批 key 同时失效或整个缓存层不可用
- ❌ 布隆过滤器判存在就一定存在 → ✅ 存在有误判率；它只能做"不存在"的快速排除，不能当数据索引
- ❌ 空值缓存不影响一致性 → ✅ 空值 TTL 内写入的新数据会读到"不存在"，必须短 TTL + 写路径主动清空值

**【追问怎么接】**
- "布隆过滤器误判率怎么定？" → 业务能接受多少无效回源。1% 是常见工程值；每降一个数量级，空间约增加 5 bit/元素左右（9.6→14.4→19.2），按数据量算内存后权衡
- "互斥锁方案会不会拖垮等待的线程？" → 会，所以等待要设上限 + 双重检查（拿到锁后先再查一次缓存）；高并发场景优先逻辑过期，把等待变成接受旧值

### Q3 · 缓存与数据库一致性（⭐⭐⭐⭐⭐）

**【一句话答】** 主流方案是 Cache Aside：读——miss 时查库回填；写——**先更新数据库，再删除缓存**；极端并发下的短窗口不一致用延迟双删或 binlog 订阅异步删除收敛，缓存这层天然只能做到最终一致。

**【标准答】**
- **为什么"删"不"更"**：并发写时"更新缓存"存在乱序覆盖（A 的旧值后到覆盖 B 的新值）；删除是幂等的懒加载，下次读自然回填最新值。且写多读少场景下更新缓存会产生大量无效计算
- **为什么 DB 先行**（时序分析，见配图）：
  - 先更 DB 后删缓存的不一致，需要"读请求 miss → 读到旧值 → 写请求完整执行完 → 读请求才回填"这个序列，即**读慢于写且恰逢缓存失效**，概率极低且窗口毫秒级
  - 先删缓存后更 DB 的不一致，只需"删完缓存 → 一个读请求 miss 查到旧值回填 → DB 才更新完"，普通业务节奏即可触发，窗口是整个写事务时长
  - 两个窗口的触发难度差一个数量级以上，所以选 DB 先行
- **延迟双删**：更 DB → 删缓存 → 等待（主从延迟 + buffer，通常几百 ms）→ 再删一次。消灭的是"从库旧数据被读请求回填"的窗口。读走主库可省掉这一步
- **binlog 订阅（Canal）**：Canal 伪装成 MySQL 从库接收 binlog，解析变更后删除/更新缓存。业务零侵入、不丢变更；代价是链路变长（准实时，秒级）
- **强一致的代价**：读写都上分布式锁串行化，吞吐倒退一个量级，只在资金类极小范围使用。**面试表述：缓存层给出的是最终一致的工程权衡，不是缺陷**

**【易错点】**
- ❌ 延迟双删保证 100% 一致 → ✅ 只能收敛窗口；说"100% 一致"在缓存语境下是错误表述
- ❌ 先删缓存再更 DB 更安全 → ✅ 时序分析恰好相反（见标准答），这是高频追问点

**【追问怎么接】**
- "删缓存失败了怎么办？" → 重试队列（删失败入 MQ 延迟重试）；binlog 方案天然兜底——删除失败会由下一条 binlog 重放补偿
- "为什么不用 TTL 兜底就够了？" → TTL 是最后兜底不是方案：不一致窗口 = TTL 全长。业务对窗口敏感就必须主动失效
- "读写分离架构下回填的是哪个库的数据？" → 读请求走从库，从库延迟期间回填的就是旧值——这正是延迟双删/走主库回填存在的理由

### Q4 · 热 key / 大 key（⭐⭐⭐⭐）

**【一句话答】** 热 key 是单个 key 承载极高流量导致单分片带宽与 CPU 打满，靠本地缓存、key 打碎、热点探测治理；大 key 是 value 过大拖慢单线程命令与主从同步，靠拆分、压缩、UNLINK 异步删除治理。

**【标准答】**
- **判定阈值**（行业治理惯例，说"行业一般按这个量级治理"而非"官方规定"）：string value > 10KB、集合类元素 > 5000 或总量 > 10MB；热 key 参考单 key QPS 数千以上且集中在单节点
- **热 key 治理**：
  - 本地缓存直接消化该 key 的读流量（Caffeine，纳秒级访问）
  - key 打碎：`key#1..#N` 写多份读随机一份，流量摊到 N 个分片；代价是写路径 N 倍放大与短窗口内 N 份不一致，只适合读极端热的场景
  - 热点探测：京东开源 hotkey 思路——客户端上报访问计数 → 计算集群聚合判定热点 → 推回客户端本地缓存，秒级发现
- **大 key 治理**：
  - 按业务维度拆成多个小 key（hash 拆 field 到多个 hash）
  - value 压缩（snappy/gzip，CPU 换带宽）
  - 删除用 `UNLINK`（4.0+）：DEL 是同步释放，百万级集合会阻塞主线程数百毫秒；UNLINK 只做引用摘除，内存释放交给 background 线程
  - 过期淘汰选 lazy-free（`lazyfree-lazy-expire yes`）
- **危害链路要能说全**：大 key → 单命令耗时长 → 阻塞 worker（单线程模型）→ 后续命令排队 → 客户端超时雪崩；同时主从同步该 value 产生延迟、集群迁移 slot 时卡顿

**【易错点】**
- ❌ 热 key 加 Redis 节点解决 → ✅ key 按 hash slot 固定落在某分片，加节点不改变单 key 归属；只能打碎或本地缓存
- ❌ DEL 大 key 无所谓 → ✅ 同步 DEL 是常见线上抖动根因，生产规约就是 UNLINK

**【追问怎么接】**
- "怎么系统性发现？" → `redis-cli --hotkeys`（需 maxmemory-policy 为 LFU）、`--bigkeys`（抽样扫描）、RDB 离线分析（redis-rdb-tools）给出精确分布；运行时靠客户端埋点上报
- "拆分后一致性怎么处理？" → 打碎的 N 份是同一数据的副本，写路径用版本号或全部重写+短 TTL 收敛，业务侧明确这是最终一致

### Q5 · 多级缓存：Caffeine + Redis（⭐⭐⭐⭐）

**【一句话答】** 请求先查本地 Caffeine（纳秒级、无网络往返），miss 再查 Redis（亚毫秒），最后回源 DB；代价是多实例本地缓存不一致，用广播失效、短 TTL、业务容忍窗口三者组合解决。

**【标准答】**
- **性能账**：一次 Redis 访问 = 本地内存访问的 10^3~10^4 倍延迟（网络 RT + 序列化）；最热的少量 key 消化在 JVM 内，Redis 与 DB 的 QPS 同步下降
- **Caffeine 为什么命中率高于 LRU**：W-TinyLFU 淘汰算法
  - 结构：小窗口（new entries，tiny LRU）+ 主区域（SLRU： probation 试用段 + protected 保护段）
  - 频率用 Count-Min Sketch 近似统计（空间远小于精确计数），周期性减半衰减，兼顾"防偶发扫描污染"与"热点随时间迁移"
  - 直白表述：LRU 谁 recently 谁留，一次全表扫描就能把真热点全挤掉；W-TinyLFU 新数据要先在窗口证明自己、进入主区要和已有元素的频率 sketch 比拼，偶发流量挤不掉真热点
- **一致性三招**：写后 MQ/Redis pub-sub 广播各实例失效；本地 TTL 压到秒级自然收敛；按业务评估容忍窗口（类目、配置、字典秒级旧值完全可接受）
- **选型边界**：只放**读多写少 + 容忍短暂旧值**的数据（类目/配置/字典/活动信息）；库存、订单状态等强时效数据禁止进本地缓存
- **实战表述模板**：核心链路 P99 优化，第一步是缓存（Redis 热点与本地字典），第二步才是异步化——顺序不可颠倒，缓存改造的风险面远小于异步化

**【易错点】**
- ❌ 所有读数据都上本地缓存 → ✅ 失效风暴与内存占用会让收益反转；本地缓存条目数要设上限（maximumSize）并监控命中率
- ❌ 广播失效后各实例立刻一致 → ✅ 广播本身可能丢失/延迟，秒级 TTL 才是最终兜底；两者是组合不是替代

**【追问怎么接】**
- "本地缓存上限怎么定？" → 按对象大小 × 条目数估算堆占用（例如 1KB × 10 万 = 100MB），结合 GC 压力与命中率曲线取拐点
- "Caffeine 的 expireAfterWrite 和 refreshAfterWrite 区别？" → 前者到期后请求阻塞回源（stampede 风险，配合 CacheLoader.asyncReload 缓解）；后者到期后先返回旧值、异步刷新，是逻辑过期思想在本地缓存的实现

### Q6 · 限流：四大算法 + 分布式限流（⭐⭐⭐⭐⭐）

**【一句话答】** 固定窗口有临界突刺，滑动窗口消突刺，漏桶恒速整形保护脆弱下游，令牌桶恒速补充且允许突发——通用场景首选令牌桶；分布式限流用 Redis + Lua 保证多实例共享同一计数的原子性。

**【标准答】**
- **四算法的进化关系**：
  - 固定窗口计数：实现最简；临界问题是上一窗口末尾 + 下一窗口开头可在瞬间通过 2 倍配额
  - 滑动窗口：窗口切格子滚动累加，精度与格子数成正比。Sentinel 默认 1 秒 2 格、每格 500ms（LeapArray 结构，已核实）
  - 漏桶：恒定速率放行，绝对平滑；代价是应对不了合理突发（业务天然有毛刺）
  - 令牌桶：恒定速率生成令牌、桶容量缓存令牌，平均速率受限的同时允许短时突发。Guava RateLimiter、网关通用方案
- **分布式限流**：Redis + Lua 把"读计数-判断-扣减"放进一个脚本原子执行，多实例共享一个桶。两个工程细节：
  - 脚本内不要依赖 `TIME` 命令取时间（集群模式下 Lua 的时间调用是受限/回写禁用的），用 key 的 TTL 差值推算窗口
  - 每次请求多一跳 Redis 是固定成本，上限受 Redis 容量约束；更高吞吐用 Sentinel 集群流控（Token Server 集中发放令牌）或本地预分配配额（每实例先领一段，用完再申请）
- **部署层次**：网关限总量 → 接口级限单资源 → 用户维度（userId 哈希分桶 + 布隆过滤器拦截伪造流量）
- **阈值怎么定**：压测得出的容量 × 安全系数（0.7~0.8）；低于容量的阈值是浪费，高于容量的阈值不具保护作用

**【易错点】**
- ❌ 漏桶比令牌桶先进 → ✅ 两者保护对象不同：漏桶保护脆弱下游（匀速放行），令牌桶兼顾用户体验（容忍突发）。没有绝对优劣
- ❌ 每个服务各自限流就安全了 → ✅ 各实例限额之和可能仍超下游容量；全局总量必须集中计数

**【追问怎么接】**
- "Sentinel 和 Guava RateLimiter 选哪个？" → 单机算法选 Guava；微服务选 Sentinel：规则中心动态推送、集群流控、熔断降级一体
- "限流被拒的请求怎么处理？" → 区分业务：交易类排队（MQ 缓冲）/ 返回友好降级页 / 直接 429。关键是"拒绝"也必须是设计过的行为，不是异常堆栈

### Q7 · 熔断、降级、隔离（⭐⭐⭐⭐）

**【一句话答】** 熔断器三态循环——关闭 → 失败率/慢调用比例超阈值 → 打开（请求不再打到下游、直接走 fallback）→ 熔断时长后 → 半开（放少量探测请求，达标恢复）；降级是有损服务的优先级取舍；隔离把故障域限制在单个下游内。

**【标准答】**
- **熔断**：
  - Sentinel 三种熔断策略：慢调用比例（RT 超阈值的请求占比）、异常比例、异常数
  - 打开后走 fallback 而不是抛异常——兜底逻辑（默认值/旧缓存/静态文案）才是熔断的完整形态
  - 半开探测：熔断时长（默认 10s 级）后放行少量请求验证下游恢复，成功则关闭、失败则继续打开
- **降级的优先级设计**：保交易主链路，砍外围——评价降级为静态文案、推荐降级为热门榜、搜索降级为默认结果。分自动（规则触发）与人工（大促预案开关）：**自动规则管波动，人工开关管极端场景**（例如主动关闭优惠券列表入口）
- **隔离两种模式**：
  - 线程池隔离：每个下游独立线程池，故障不扩散；代价是线程切换与排队开销（Hystrix 默认，也是它被淘汰的主因之一：线程开销大、停止维护）
  - 信号量隔离：只限并发数、不换线程，开销小（Sentinel 默认）
- **选型逻辑一句话**：同步调用走信号量够用；真正需要防火墙的场景（下游慢且调用方线程会被拖死）才上线程池隔离

**【易错点】**
- ❌ 熔断就是抛异常 → ✅ 熔断的设计目标是**有损但可用**：fallback 是熔断的组成部分
- ❌ 降级规则配好就不用人管 → ✅ 极端场景（资损风险、舆情风险）必须人工预案，自动规则无法判断业务止损边界

**【追问怎么接】**
- "Hystrix 为什么被淘汰？" → 线程池隔离开销大（排队 + 上下文切换）、项目停止维护；Sentinel 信号量 + 滑动窗口更轻，且提供流控/热点参数/系统自适应保护
- "熔断阈值怎么定？" → 依赖下游的正常失败率基线（例如正常 0.1%，阈值设 1%~10%），窗口内请求数要有最小值（如 20 次）防止低流量时误判

### Q8 · MQ 削峰与消息可靠性（⭐⭐⭐⭐⭐）

**【一句话答】** 削峰的本质是把同步长链替换为一次消息落盘——接口只写一条消息就返回，下游按自身消费能力追；消息不丢要生产、存储、消费三段分别设防，端到端语义在 at-least-once 之上通过消费端幂等实现 effect-once。

**【标准答】**
- **异步化的收益结构**：下单接口 RT 从"订单+库存+积分+通知串行"变为一次 MQ 写入（毫秒级）；各下游故障隔离（消费失败重试不影响下单成功）
- **不丢消息三段设防**：
  - 生产端：发送确认（acks/同步发送 + 失败重试）；本地消息表兜底"业务库与 broker 双写"的不一致（RocketMQ 另有事务消息方案，见 Q24）
  - Broker：同步刷盘 + 多副本（同步复制）；异步刷盘在机器断电时丢最后一批消息
  - 消费端：手动 ack（处理完成再确认）+ **幂等消费**（唯一业务单号去重表 / 数据库唯一键 / Redis setnx），因为重试必然带来重复投递
- **积压处理**（先诊断瓶颈再动手）：
  1. 消费并行度上限 = 队列/分区数（Kafka 一个分区最多被消费组内一个消费者消费）——消费者数没到顶先加消费者
  2. 到顶了扩分区/队列 + 把堆积数据搬运到新 topic
  3. 提批量 + 消费侧并发
  4. 旁路非核心订阅
  5. 极端场景：新 topic + 临时消费者只落盘，事后离线补处理
- **顺序消息**：同一业务 key（orderId）哈希到同一队列，队列内单线程消费——局部有序满足绝大多数业务，全局有序代价（单队列）不值得

**【易错点】**
- ❌ 积压就无脑加消费者 → ✅ 并行度上限是队列数；加满之后再加只是空转。先看并行度瓶颈还是单条耗时瓶颈
- ❌ MQ 配置好了消息就不会丢 → ✅ 三段各自都可能丢/重，任何一段没设防整体就不设防

**【追问怎么接】**
- "为什么不用线程池做异步？" → 线程池是内存态：机器重启任务即丢失，也无法跨服务解耦；MQ 提供持久化、重放、削峰跨服务三个不可替代能力
- "消息重复投递怎么彻底避免？" → 避免不了（网络重试的必然结果），只能在消费端幂等。说"追求 exactly-once 传输"是错误表述，正确目标是"effect-once 处理"
- "RocketMQ 的事务消息具体怎么实现的？" → 见 Q24（本题的标准延伸）

### Q9 · 秒杀库存热点行（⭐⭐⭐⭐⭐）

**【一句话答】** 流量漏斗下每层削一个数量级，真正到达库存系统的流量已大幅收敛；防超卖三层防线——Redis+Lua 原子预扣（性能层）、MQ 异步落单（吞吐层）、DB 条件更新行锁兜底（正确性层）；爆款商品再叠加库存分片对抗热点行。

**【标准答】**
> 系统全景（前端到履约）见飞猪篇 Q25，本题只深挖库存扣减链路——两卷刻意分工。

- **流量漏斗（见配图）**：亿级曝光 → 数千万点击 → 数百万提交 → 数十万有效扣减。58.3 万笔/秒的订单创建峰值背后，单商品库存热点行是 QPS 数万级的 `update` 打在同一行——这才是技术难点
- **三层防线**：
  - **性能层：Redis + Lua 原子预扣**。`if stock > 0 then decr stock` 在一个脚本内原子执行。为什么不用分布式锁：锁 = 加锁/解锁两次网络往返 + 其他线程自旋等待；Lua = 一次往返 + 单线程串行，单 key 天然串行化。单 Redis 节点即可支撑 10 万 QPS 级别的原子扣减
  - **吞吐层：预扣成功发 MQ**，订单服务异步落库，前端轮询/推送"排队中"结果。同步链路只剩一次 Redis 写 + 一次 MQ 写
  - **正确性层：DB 条件更新**。`update stock set n = n - 1 where sku_id = ? and n > 0`，影响行数为 0 即售罄。即使缓存层全灭，DB 行锁保证物理上不超卖——**宁可卖慢，不可卖超**
- **热点行深挖（P7/P8 加分层）**：
  - InnoDB 行锁语义：同一行的 update 在锁队列串行等待，单行吞吐受"锁等待 + 语句执行"耗时约束，约千级 QPS 上限
  - 对策一：**库存分片**——100 件拆 10 个 key/行（`stock_1..stock_10`），扣完一个切下一个；热点分散为 10 份
  - 对策二：**热点更新排队/合并**（阿里 inventory hint、Statement Queue 思路）——同一行的更新在内存排队、按序批量提交，减少锁竞争与 redo 刷盘次数
  - 对策三：极端热点走内存价签/令牌预分配（先到先得的资格发放，再异步兑换库存）
- **闭环补数**：预扣后下单失败的库存必须回滚（延迟消息回补 + 对账 job 兜底差异）；下单去重靠唯一业务单号

**【易错点】**
- ❌ 只答"用分布式锁" → ✅ 锁是三者中最贵的方案；能原子（Lua）、能异步（MQ+DB 兜底）就不用锁
- ❌ 忘记回滚链路 → ✅ 扣减成功 + 订单失败 = 少卖，是资损对称的另一面；延迟回补与对账是必答题不是加分题

**【追问怎么接】**
- "Redis 挂了怎么办？" → 降级 DB 行锁 + 入口限流：正确性由 DB 条件更新保证，吞吐由限流保护——按层次退化的思路回答
- "Redis 预扣和 DB 不一致怎么办？" → Redis 是"资格判定"不是账本：最终账以 DB 为准，差异由对账 job 修正；表述上把它定位成性能层组件，一致性问题就转化为对账问题
- "为什么 Lua 脚本能保证原子？" → Redis 单线程执行命令，脚本执行期间不插入其他命令；注意脚本要短（长脚本阻塞所有请求），且集群模式 key 必须同 slot（hash tag）

### Q10 · 线程池 / 连接池调优（⭐⭐⭐⭐）

**【一句话答】** 池化的本质是复用昂贵资源（线程创建、TCP 握手、DB 认证），把单次使用的开销摊平为复用成本；线程池参数不背公式靠压测，参考公式 N×U×(1+W/C) 给初值；连接池宁小勿大——HikariCP 默认 10 是有道理的。

**【标准答】**
- **线程池**（7 参数 4 策略的机制见飞猪篇 Q7，本题讲工程实践）：
  - 初值公式：N = CPU 数 × 目标利用率 × (1 + W/C)（出处《Java Concurrency in Practice》）——IO 密集型 W/C 大、线程数远超核数；但公式只给起点，**最终值以压测拐点为准**
  - 生产三件套：监控（active/queue/reject 指标暴露 Prometheus）、有界队列（无界队列会将过载转化为内存耗尽）、拒绝策略分级（核心链路 Abort + 告警快速失败；非核心 Discard）
  - 动态化：Nacos 推送 corePoolSize/maximumPoolSize/queue 容量实时生效（美团 dynamic-tp 思路）——大促前调参不发版
  - CallerRunsPolicy 的正确理解：它是把压力推回调用方的背压机制；网关类服务用它等于让上游一起慢，慎用
- **DB 连接池**：
  - HikariCP 默认 maximumPoolSize = 10；官方公式 connections = core_count × 2 + effective_spindle_count
  - 连接不是越大越好：MySQL 每连接消耗内存（sort/join buffer）、连接间上下文切换、锁竞争加剧——超配的连接池让吞吐**下降**
  - 关键参数：connectionTimeout（拿不到连接快速失败）、maxLifetime（略小于 DB 侧 wait_timeout，避免被服务端断连）
- **调优路径**：先监控拿到真实水位（活跃数、等待数、获取耗时）→ 判断瓶颈在线程数还是下游容量 → 调参 → 压测验证

**【易错点】**
- ❌ IO 密集就设 2×CPU → ✅ 2N 是无依据的老经验值；W/C 比值 + 压测才是方法论
- ❌ 队列无界防止任务被拒 → ✅ 无界队列把过载转换为内存膨胀与 RT 恶化；拒绝 + 快速失败才是过载的正确语义

**【追问怎么接】**
- "HikariCP 为什么快？" → 字节码级精简（用 javassist 代替反射代理）、FastList/ConcurrentBag 定制数据结构、无锁设计取向；答出方向与取舍即可
- "怎么发现线程池配错了？" → reject 计数 > 0 且上游 RT 抬升 = 配小了或下游慢；active 长期 = max 且队列空 = 可以扩；队列持续增长 = 下游容量不足，扩池子没用，先查下游

### Q11 · 深分页：limit 1000000,10 为什么慢（⭐⭐⭐⭐⭐）

**【一句话答】** MySQL 必须真实取出并回表前 100 万行、完成排序后丢弃，只返回 10 行——offset 越大无效功越多；四招：书签续读（`where id > ?`）、延迟关联（覆盖索引先取 id）、ES search_after、业务上限制跳页。

**【标准答】**
- **代价结构**：`limit 1000000, 10` 的执行 = 扫描 1000010 个索引条目 + 约 100 万次回表（随机 IO）+ 服务层丢弃前 100 万行。索引救不了 offset：优化器必须"数过"才能偏移
- **方案对比**：

| 方案 | 写法 | 代价 | 适用 |
|---|---|---|---|
| 书签续读 | `where id > #{lastMaxId} order by id limit 10` | O(10)，最优 | 交互可改为"下一页"的信息流/导出 |
| 延迟关联 | `select t.* from t join (select id from t where c=? order by id limit 1000000,10) x on t.id=x.id` | 仍扫 offset 个条目，但**只扫窄索引不回表**，快一个量级 | 必须支持跳页的 C 端列表 |
| ES search_after | 用上一页排序值续读 | 每页固定代价 | 检索类列表；scroll 用于离线导出 |
| 业务限制 | 只开放前 N 页 | 无 | 大厂真实做法（淘宝订单默认只查近 3 个月） |

- **ES 深分页同理**：from+size 需要每个分片取 from+size 条到协调节点归并排序，代价随 from 线性放大，故默认上限 max_result_window = 10000；search_after 无状态续读，代价每页恒定

**【易错点】**
- ❌ 加个索引就好了 → ✅ 索引不改变"必须数过 offset 行"的事实；索引优化的是回表与排序，不是 offset 本身
- ❌ 延迟关联是 O(1) → ✅ 子查询仍扫描 offset+limit 个索引条目，只是把"扫宽行+回表"降为"扫窄索引"；量级改善，不是免费

**【追问怎么接】**
- "书签法怎么处理带过滤条件的翻页？" → lastMaxId 换成"上一页最后一行的完整排序键元组"（(create_time, id) 复合游标），排序键不唯一时必须补 id 做 tie-breaker
- "为什么 ES 也设 10000 上限？" → 协调节点要维护 from+size 的优先队列 × 分片数，深翻页内存与 CPU 都失控；上限是自我保护

### Q12 · 百万级批量插入优化（⭐⭐⭐⭐⭐）

**【一句话答】** 第一优先级是启用 `rewriteBatchedStatements=true`——MySQL JDBC 驱动默认逐条发送 batch，加参数后才真正改写为 multi-values 单条 SQL，通常带来一个数量级的提升；第二优先级是每批 500~1000 条分段提交事务；第三步按主键区间多线程并行，再大规模换 DataX / load data。

**【标准答】**
- **参数是开关不是优化项**：`rewriteBatchedStatements=true`（Connector/J 5.1.7+）在驱动层把 `insert` 批量改写为 `insert into t values (...),(...),...`，网络往返从 N 次降为 1 次；对 update/delete 改写为 multi-statement，收益小一些。**不加这个参数，saveBatch 就是逐条发送**——这是最高频的认知错误
- **批大小**：500~1000 起步实测调优。上限约束是 `max_allowed_packet`（5.7 默认 4MB、8.0 默认 64MB）与 SQL 解析内存；收益递减，压测找拐点
- **事务粒度**：一条一提交 = 每条 fsync；百万行单事务 = undo 膨胀 + 主从延迟失控。正确粒度是**每 N 批一提交**（如每 5000 行）
- **并行化**：按主键区间切 20 片 × 10 线程，每线程独立连接；监控主从延迟与磁盘 util 动态调速
- **更大规模换工具**：DataX、`load data infile`（文本导入最快路径）、Canal 同步——数据搬运是成熟工具的领地，不要手写
- **可重跑**：作业表记录批次水位；或 staging 表写完校验后原子 rename/merge——百万级任务必须有断点与幂等

**【易错点】**
- ❌ MyBatis-Plus 的 saveBatch 就是批量插入 → ✅ 不加 rewriteBatchedStatements 它仍是逐条发送；参数才是决定性变量
- ❌ 批越大越快 → ✅ 收益递减 + 风险递增（包上限、解析开销、锁持有时间）；拐点靠压测不靠直觉

**【追问怎么接】**
- "为什么不用 insert ... select？" → 同库纯搬运 SQL 最快；跨库或需要业务转换（字段映射/清洗）时走应用层批量
- "怎么验证参数生效了？" → 抓包或开 MySQL general_log 观察是否合并为 multi-values；吞吐 10 倍级变化本身就是信号

### Q13 · 千万级大表在线 DDL（⭐⭐⭐⭐）

**【一句话答】** 先看 MySQL 原生能力——8.0 加列 INSTANT 秒级、5.7 加索引 INPLACE 全程允许并发 DML；收尾瞬间的 MDL 排他锁是最大风险点，长事务会堵死它导致全表读写挂起；改列类型等重操作用 gh-ost（binlog 回放）或 pt-osc（触发器）。

**【标准答】**
- **原生 Online DDL 的真实语义**：INPLACE 允许并发 DML，但**开始与结束各有一次 MDL（元数据锁）升级到排他**。正常毫秒级无感；危险在于 MDL 队列是公平的——一个长事务/慢查询先拿到共享 MDL，DDL 的排他请求排队，之后**所有新读写全部排在 DDL 后面**，表现为整表 hang。DDL 前必查 `information_schema.innodb_trx` 杀长事务
- **INSTANT（8.0）**：只改元数据，加列秒级完成；8.0.12 支持末尾加列，8.0.29 起支持任意位置。能 INSTANT 绝不 INPLACE
- **gh-ost vs pt-osc**：
  - pt-osc：影子表 + 三个触发器（insert/update/delete）同步增量——成熟，但高写入表上触发器写放大显著
  - gh-ost（GitHub）：影子表 + **解析 binlog 回放增量**——无触发器、可限速/暂停/随时终止、对主库侵入小；依赖 ROW 格式 binlog 与额外 binlog 带宽
  - 选型依据是表的写入画像：高写入选 gh-ost，触发器可接受且 binlog 受限时 pt-osc
- **标准流程**：变更评审（影响行数/空间翻倍/时长预估）→ 从库灰度验证 → 低峰执行 + 限速（盯主从延迟）→ 原子 rename 切换 → 观察 → 预案（rename 可逆，失败回退旧表）

**【易错点】**
- ❌ Online DDL 完全不锁表 → ✅ 首尾各一次 MDL 排他；锁本身不致命，**被长事务堵住的锁队列**才致命
- ❌ gh-ost 一定优于 pt-osc → ✅ gh-ost 依赖 ROW 格式 binlog 并增加 binlog 带宽消耗；按表写入画像选型

**【追问怎么接】**
- "执行中主从延迟涨了怎么办？" → gh-ost 自带 `max-lag-millis` 限速（延迟超阈值自动暂停拷贝）；没有自动限速的手段就人工分批+观察
- "为什么 DDL 会把整表读写堵死？" → MDL 队列公平排队 + 写锁优先：DDL 等共享锁释放，后续全部 DML 排在 DDL 之后——一环堵环环堵

### Q14 · 分库分表：时机、分片键、扩容（⭐⭐⭐⭐⭐）

**【一句话答】** 阿里手册建议单表超 500 万行或 2GB 才考虑分库分表（已核实），且拆前先确认索引优化与归档已无空间——拆表不可逆；分片键选最高频查询维度，非分片键查询靠基因法、异构索引或冗余解决；扩容按 2 的幂成倍扩，主键用雪花 ID。

**【标准答】**
- **时机判断**：B+ 树在良好索引下千万级仍可工作（经典估算：16KB 页 × 三层 B+ 树 ≈ 两千万行寻址能力），阿里 500 万阈值是给行宽与缓冲留余量的保守值。**先 explain、先归档，拆表是最后手段**——它带来的跨片查询/事务/运维复杂度是永久性的
- **分片键选择**：查询最集中的维度（订单表选 user_id，买家视角占绝对多数）；避免热点（大买家加盐、不按时间分片）
- **非分片键查询三解**：
  - **基因法**：orderId = 雪花主体 + user_id 后若干位——生成时把路由信息揉进 ID，按 user_id 或 orderId 都能定位分片，免广播
  - **异构索引**：按另一维度再存一份到 ES 或冗余表（空间换查询）
  - **广播表**：字典类小表每个库全量一份（冗余换 join）
- **扩容设计**：64 → 128 成倍扩，翻倍时旧数据按 hash 新分布恰好一半不动；**上线前按 2 的幂规划**，非倍数扩容几乎等于全量重分布。ShardingSphere 自带迁移能力
- **分布式 ID**：雪花 = 1 符号 + 41 时间戳 + 10 机器 + 12 序列（可调整配比），趋势递增对 B+ 树友好；时钟回拨对策：回拨小于阈值等待、大于阈值漂移备用号段，或用 Leaf（号段模式）/UidGenerator
- **跨片难题**：跨片分页=各片 top-N 归并重排（深页成本高，业务上转 ES）；跨片事务=同键尽量落同库，跨了走最终一致（本地消息表 / Seata AT）
- **中间件**：ShardingSphere-JDBC（客户端层、无代理损耗）为主流；Proxy 层适合异构语言团队

**【易错点】**
- ❌ 数据到千万就赶紧拆 → ✅ 先确认索引与归档已到极限；拆的触发条件是**写入容量**与运维成本，不是行数本身
- ❌ 先用自增主键再上分片 → ✅ 自增 ID 与分片路由耦合后扩容极难；**先定 ID 策略与分片键，再动手**

**【追问怎么接】**
- "雪花 ID 比 UUID 好在哪？" → 趋势递增：B+ 树顺序追加、页分裂少、缓存局部性好；UUID 无序导致随机插入、页分裂与索引膨胀
- "双 11 你的订单表怎么扛的？" → 按买家维度分片 + 写入高峰 MQ 削峰 + 热点买家检测；回答要落到分片键选择理由上

### Q15 · 亿级数据平滑迁移（⭐⭐⭐⭐⭐）

**【一句话答】** 五步：存量搬迁 → 增量双写 → 对账 → 灰度切读 → 切写收尾；关键次序是**先记录 binlog 位点（或先启动双写/Canal）再搬存量**，反过来搬迁时段的增量会漏；对账按内容 checksum 不按行数。

**【标准答】**
- **步骤与要点**（时间线见配图）：
  1. **位点先行**：启动 Canal（伪装从库收 binlog）或业务双写，先承接增量变更——这是不丢数据的先决条件
  2. **存量搬迁**：按 id 区间切片（每批 ~1 万）、限速（盯主从延迟与 IO util）、断点续跑（水位表）；大字段单独处理避免单行过大
  3. **对账**：全量按分片 CRC/checksum 聚合比对，增量实时抽样 + 差异修复任务。**只比行数不算对账**——内容一致才是迁移完成的标准
  4. **灰度切读**：配置中心开关按用户/机器维度 1% → 10% → 100%，每档观察 RT、错误率、对账差异
  5. **收尾**：切写（新库主写、旧库停写）→ 双写保留一个完整业务周期（月结/大促）→ 旧库降级归档；切写前必须完成一次回滚演练
- **双写失败处理**：写新库失败进补偿队列重试，禁止静默丢弃；binlog 方案天然有重放能力
- **回滚设计**：切读阶段回滚 = 开关拨回（秒级）；切写后回滚 = 反向双写重建旧库——所以切写是唯一不可轻易回退的点，演练必须在切写前

**【易错点】**
- ❌ 先搬存量再开始双写 → ✅ 搬迁耗时数小时，期间增量全部漏掉；位点/双写必须前置于存量搬迁
- ❌ 迁移完成立刻下线旧库 → ✅ 至少保留一个完整业务周期的双写观察期，周期性 bug（月结、对账日）只有真实周期才能暴露

**【追问怎么接】**
- "Canal 的原理？" → 伪装成 MySQL slave，走主从复制协议拉 binlog（ROW 格式），解析变更投递 MQ，下游消费写新库——对业务代码零侵入
- "对账 checksum 怎么做高效？" → 按主键区间分段聚合（sum(crc32(concat(所有列)))），段级比根因定位，避免单行全表扫描；增量部分按 binlog 序号窗口比对

### Q16 · 大表冷热分离与归档（⭐⭐⭐⭐）

**【一句话答】** 订单类数据的热点集中在最近约 3 个月，把冷数据搬走让热表保持小体量；三档手段：按月 range 分区（`exchange partition` 秒级摘除整月）、归档表（job 按水位小批量搬运）、更冷的数据进 OLAP/OSS；删除必须小批量分批。

**【标准答】**
- **分区表**：range 按月分区，查询带分区键触发**分区裁剪**（只扫目标分区）；`alter table ... exchange partition` 用段交换实现整月数据秒级摘除。两个硬约束：分区键必须包含在主键/唯一键里（InnoDB 唯一性只能保证分区内部局部唯一）；分区表不解决单机容量上限（那是分库分表的职责）
- **归档表 + 搬运 job**：低峰期"读一批（id 水位）→ 写归档库 → 删一批"循环；删除**必须小批量**（delete limit 1000 循环）——千万级单条删除会导致 undo log 急剧膨胀与主从延迟；幂等靠水位表 + 归档表唯一键
- **冷数据进仓**：两年外的数据进 ClickHouse/TiDB/OSS，分析查询不再碰交易库；归档格式与对账工具要配套
- **查询侧路由**：默认只查热表，跨年查询走归档库（应用层路由或 union 视图）；这个边界要在产品设计阶段就定好（参考：淘宝订单默认只展示近 3 个月）

**【易错点】**
- ❌ 分区表是万能方案 → ✅ 不带分区键的查询扫全部分区，比无分区还差；且单机天花板仍在
- ❌ `delete from t where create_time < ?` 单条全量执行 → ✅ 大删除 = 大事务 = undo 膨胀 + 锁持有 + 主从延迟；分批 + 限速 + 低峰是生产规约

**【追问怎么接】**
- "归档怎么保证不丢不重？" → 先写后删 + 水位记录，或同事务"写归档 + 推水位"；重了靠归档表唯一键幂等覆盖；兜底对账 job 定期比对两边行数与 checksum
- "为什么不直接归档到另一个 MySQL 而是进 OLAP？" → 归档 MySQL 只解决"热表变小"；分析查询（多维聚合）对行存的扫描成本仍高，OLAP 列存的压缩与向量化才是分析场景的正解

### Q17 · 分布式任务分片：百万级批处理（⭐⭐⭐⭐）

**【一句话答】** XXL-Job 分片广播一次触发全部执行器、各自携带 shardIndex/shardTotal，数据按 `id % shardTotal == shardIndex` 认领，天然并行分摊；配套限速保护 DB、水位断点幂等重跑、故障转移；更细粒度拆分用 MQ 子消息。

**【标准答】**
- **分片广播**：调度中心一次下发，所有执行器同时收到；`XxlJobHelper.getShardIndex()/getShardTotal()` 获取身份；数据切法 `where id % #{shardTotal} = #{shardIndex}` 或按 id 区间（区间更易控流速）
- **限速**：每片内 sleep/令牌桶控制 QPS，指标是**主从延迟与磁盘 util 不越界**——批处理导致数据库过载是常见事故
- **幂等断点**：任务水位表记录 max_id，重跑从水位续；处理逻辑本身幂等（按业务单号 upsert）。幂等不是可选项的原因：**扩机器后 shardTotal 变化，id 取模归属全变**，重分配必然带来重复处理
- **故障处理**：XXL-Job 失败重试 + 故障转移（换机重跑该分片）+ 告警（钉钉/电话）；重跑的正确性完全依赖幂等设计
- **与 MQ 拆分的取舍**：任务拆成 N 条子消息并发消费——粒度细、自动重试，但总量控制不如分片直观、且必须消费幂等。定时批处理选分片广播，实时流转选 MQ

**【易错点】**
- ❌ 一个大任务单机跑 → ✅ 长事务 + 长连接 + 单点 + 无法水平扩；分片是水平扩的前提
- ❌ 分片数写死一劳永逸 → ✅ shardTotal 变化即归属重分配，水位 + 幂等必须扛得住重复处理

**【追问怎么接】**
- "某台执行器中途宕机？" → 故障转移把该分片调度给其他机器重跑，从上次水位续跑 + 幂等保证不重复入账
- "怎么保证任务不重叠执行？"（上一轮没跑完下一轮又触发）→ 调度侧阻塞处理策略（丢弃后续/覆盖之前）+ 分布式锁抢任务 + 水位判断增量

### Q18 · 海量数据异步导出（⭐⭐⭐⭐）

**【一句话答】** 几十万行同步导出必然 OOM 或 HTTP 超时，标准架构是下载中心：提交任务 → 异步生成 → 传 OSS → 通知下载；生成侧三件套：主键游标分批读、EasyExcel/POI SXSSF 流式写、单文件 10 万行分片打 zip。

**【标准答】**
- **交互模型**：提交返回任务号 → 任务表记录进度（已处理/总行数）→ 完成后站内信 + 带过期的下载链接
- **读取**：主键游标分批（`where id > ? order by id limit N`，同 Q11 书签法）；查只读从库或 ES；JDBC 流式读取：MySQL 驱动 `fetchSize=Integer.MIN_VALUE`（逐行拉取）或 `useCursorFetch=true`（服务端游标）——否则驱动默认全量载入内存
- **写入**：EasyExcel（滑动窗口默认刷盘）或 POI `SXSSFWorkbook`（滑动窗口行模型）；禁止 XSSFWorkbook（全量驻留内存）。CSV 在列多时比 xlsx 小一个量级
- **分文件**：单 sheet 上限 1,048,576 行是 Excel 硬约束，超限静默截断丢数据——所以**分文件是必须项不是优化项**；单文件 10 万行 + zip 打包是惯例
- **失败重跑**：水位断点；生成失败的文件整体作废重做（部分文件不可用）
- **治理**：大导出限流/排队（避免与在线业务抢连接池）、任务产物 7 天自动清理、导出行为审计

**【易错点】**
- ❌ `selectList()` 一次取全量再写文件 → ✅ 几十万行对象图直接耗尽堆内存；游标分批 + 边读边写边丢才是流式
- ❌ Excel 行数"应该没限制" → ✅ 单 sheet 1,048,576 行硬上限，超限截断是**静默数据丢失**

**【追问怎么接】**
- "导出期间数据在变怎么办？" → 快照语义：按 create_time 截止值（或导出开始时刻的 binlog 位点）过滤，并在文件注明数据截止时间
- "用户等不及怎么办？" → 进度可查（任务表已处理/总数）+ 完成通知；体验问题用交互解决，不应由同步接口承担

### Q19 · 高可用：双活 / 单元化（⭐⭐⭐⭐）

**【一句话答】** 可用性先背数字——99.9% = 年停机 8.8 小时、99.99% = 52.6 分钟；演进路径是同机房主备 → 同城双活（近同步复制，延迟 1~2ms）→ 异地多活必须单元化：跨地域延迟几十毫秒做不了强双写，只能按用户切分单元、读写在本单元闭环，全局数据集中同步。

**【标准答】**
- **分层可用性设计**：
  - 应用层：无状态 + 多副本 + 健康检查自动摘除
  - 数据层：主从 + 哨兵/集群自动切换；同城双活近同步复制，RPO ≈ 0、RTO 分钟级
  - 机房层：同城双活两机房都承载流量，单机房故障分钟级切换
  - 地域层：异地多活 = 单元化
- **单元化核心**：
  - 按用户维度分片到单元（RZone），每个单元服务自己的用户群，RPC、缓存、DB 读写全在本单元闭环——跨地域 RT 不进入交易主链路
  - 全局数据（商品、库存等所有单元共用的，GZone）集中部署 + 向各单元同步；同城只读单元（CZone）承接就近读
  - 路由标识（如 uid 尾号）必须贯穿全链路：RPC 上下文、消息队列、缓存分片、DB 路由都要能识别"这个用户属于哪个单元"
- **为什么异地不能简单双活**：跨地域 RT 几十 ms，同步双写使每笔事务 RT 翻倍、吞吐减半，且网络抖动直接放大为可用性事故——**不单元化就没有异地多活**
- **演练**：预案平台 + 混沌工程（ChaosBlade）+ 断机房演习。未经真实演练验证的高可用方案不可信

**【易错点】**
- ❌ "异地再建一套双活就行" → ✅ 跨地域物理延迟不可消除，强双写不可行；单元化是唯一路径，且是架构级改造不是部署问题
- ❌ 单元化只是流量路由 → ✅ 路由标识要贯穿 RPC/消息/缓存/DB 全组件，全局数据的识别与集中处理是数据架构改造

**【追问怎么接】**
- "单元间数据要不要同步？" → 用户维度的数据各自闭环不同步；全局数据（商品/库存）GZone 集中 + 同步至各单元只读副本；跨境数据要识别出来特殊处理
- "某个单元整体故障？" → 用户流量切换到其他单元（容量预留 ×1.5 以上），该单元未完成数据靠同步链路追平后再切回——切流与追平的顺序就是 RTO 的构成

### Q20 · 全链路压测（⭐⭐⭐⭐）

**【一句话答】** 大促容量的唯一可信来源是生产环境真题真做：全链路注入 N 倍峰值流量找最短板；三个关键设计——流量染色（压测标识全链路透传）、影子隔离（影子表/影子 topic/缓存前缀，与真实数据同环境不同存储）、出口拦截（短信/支付/三方调用挡板）。

**【标准答】**
- **为什么必须生产环境**：测试环境的数据量级、索引分布、硬件规格、连接池与真实差异巨大，容量结论失真。全链路压测的核心价值就是"真"——真实数据体量（影子表同构）、真实链路（跨服务依赖互相放大）、真实资源
- **三个关键设计**（见配图）：
  - **流量染色**：施压入口打标 → 标识经 RPC 上下文 / trace baggage / ThreadLocal 全链路透传，任何组件都能判定"这是压测流量"——下游分流的依据
  - **影子隔离**：同库建影子表（`order_test`，结构、索引、数据量级与真实一致——这是容量结论不失真的前提）；消息发影子 topic；Redis key 加前缀。压测数据与生产数据同环境、不同存储
  - **出口拦截**：短信、推送、支付、三方 HTTP 全部挡板——压测流量绝不产生真实副作用（资损与合规红线）
- **施压策略**：1x → 3x → 5x 阶梯加压，每档观察 CPU、RT、错误率、DB 慢查询、主从延迟、MQ 堆积；产出是"最先到容量上限的组件清单 + 扩容/预案清单"
- **生产保护**：限流阈值兜底真实用户、压测窗口避峰、一键停止；压测导致生产系统过载属于方案设计失败
- **组织面**：全链路压测是跨团队工程——链路梳理、影子表 DDL 平台自动化、压测数据规约清理，都需要平台化沉淀

**【易错点】**
- ❌ 测试环境压一下就够了 → ✅ 容量结论的失真主要来自数据分布与规格差异，环境相似性决定结论可信度
- ❌ 只压入口 QPS → ✅ 级联效应（缓存 miss 风暴、DB 慢查询拖垮连接池、MQ 堆积反压）只有全链路才能暴露；单接口压测发现不了系统性雪崩

**【追问怎么接】**
- "影子表怎么跟着真实表结构变？" → DDL 平台在真实表变更时自动对影子表执行同步 DDL；结构漂移的影子表会让压测结论失真
- "压测期间真实用户受影响怎么办？" → 限流优先保真实流量、压测流量可被一键丢弃；错峰执行；核心指标（真实用户 RT/错误率）越界立即停止

### Q21 · 索引优化与执行计划 explain（⭐⭐⭐⭐⭐）

**【一句话答】** 索引优化的方法论是"explain 看 type/key/rows/Extra → 确认查询走了预期索引、回表最少"；设计侧围绕最左前缀、区分度、覆盖索引三个原则；失效场景有明确清单（函数、隐式转换、左模糊、破坏最左前缀等）。

**【标准答】**
- **explain 关键字段**：
  - **type（访问类型，差到好）**：ALL（全表扫）→ index（扫全索引）→ range（范围扫）→ ref（非唯一索引等值）→ eq_ref（join 时主键/唯一键匹配）→ const（主键等值，最多一行）。生产底线：range 以上；ALL 出现在大表上就是事故候选
  - **key / key_len**：实际使用的索引与使用长度——key_len 短于联合索引总长说明只用前几列
  - **rows / filtered**：预估扫描行数 × 过滤后比例，是代价估算的直接依据
  - **Extra 高频值**：`Using index`（覆盖索引免回表，最优）；`Using index condition`（ICP 索引条件下推，5.6+，把 where 条件下推到存储引擎层在索引里过滤，减少回表）；`Using filesort`（额外排序，需优化）；`Using temporary`（临时表，group by/distinct 常见，高危）
- **联合索引设计三原则**：
  - **最左前缀**：(a,b,c) 索引支持 a / a,b / a,b,c 查询；跳过 a 直接查 b 用不上（或只走 index skip scan——8.0 有限支持）
  - **区分度**：count(distinct col) / count(*) 越接近 1 越有利；低区分度（性别）单独建索引无意义，但可作为复合索引的后缀参与过滤
  - **等值在前、范围在后**：(status, create_time) 而非反过来——范围条件之后的列无法参与索引定位
- **索引失效清单**（高频考点，要能逐条给原因）：
  - 对索引列做函数/运算：`where date(create_time) = '2026-10-15'` → 改 `create_time >= '2026-10-15' and < '2026-10-16'`（索引存的是原始值，函数结果不可知）
  - 隐式类型转换：字符串列用数字查（`where phone = 13800000000`）——MySQL 把**列**转成数字比较，等价于对列套函数，索引失效；反过来数字列用字符串查不失效（转的是常量）
  - 左模糊 `like '%xx'`：B+ 树按最左有序，前缀未知无法定位；`like 'xx%'` 可以走 range
  - or 两侧任一无索引 → 整体无法走索引（可用 union all 改写）
  - `!=` / `not in`：视优化器成本估算与数据分布，通常放弃索引（结果集占比大时全表更划算）
  - 优化器统计信息过期选错索引：`analyze table` 重收集；必要时 `force index` 临时纠偏（留注释与回归计划）
- **覆盖索引**：查询列全部包含在索引中，`Using index` 免回表——高频查询把 select 的列做进联合索引是常考的优化手段（与大 key 取舍：索引变宽写入变贵）

**【易错点】**
- ❌ explain 里 rows 越小说明一定越快 → ✅ rows 是估算值，还要看访问类型与是否回表；`Using index` 的略大 rows 可能快于回表的略小 rows
- ❌ 建了索引就生效 → ✅ 失效清单 + 优化器成本估算都可能绕开索引；优化要以 explain 结果为准，不以"建过"为准

**【追问怎么接】**
- "select * 一定不好吗？" → 会破坏覆盖索引可能性、拉宽网络与内存占用；但索引能走还是走。表述为"放弃了一个优化维度"而非"索引失效"（飞猪篇 Q11 有此考点，这里给工程视角）
- "count(\*) / count(1) / count(col)？" → InnoDB 下 count(\*) 与 count(1) 等价且已被优化器特化（选最小可用索引）；count(col) 要判 NULL 且不走该列为 NULL 的行。MyISAM 的 O(1) count 不适用于 InnoDB（MVCC 下不同事务看到的行数不同）
- "索引是不是越多越好？" → 每个索引是一棵独立 B+ 树：写入放大、优化器选择空间变大、内存占用上升。核心表控制在个位数

### Q22 · 慢 SQL 排查方法论（⭐⭐⭐⭐）

**【一句话答】** 标准路径：慢查询日志定位（slow_query_log + long_query_time，默认 10s、生产建议调到 0.1~0.5s）→ pt-query-digest 聚合找 TOP → explain 分析执行计划 → 按索引层 / SQL 写法层 / 表结构层 / 架构层四层下药 → 验证与回归。

**【标准答】**
- **定位**：
  - 慢查询日志：`slow_query_log = on`，`long_query_time` 生产建议 0.1~0.5s（默认 10s 等于没开）；配合 `log_queries_not_using_indexes` 捕捉无索引查询
  - `pt-query-digest` 把日志按指纹聚合（同一模板的 SQL 归并统计），按总耗时排序——优化总耗时第一的模板，不是单条最慢的
  - 实时救火：`show processlist` 看当前在跑的语句与状态（Sending data / Waiting for lock）；`information_schema.innodb_trx` 找长事务；`sys.innodb_lock_waits` 看锁等待链
- **分析**：explain（见 Q21）+ `show table status` / `analyze table` 校准统计信息
- **四层优化手段**（由轻到重）：
  - 索引层：补索引、改联合索引顺序、覆盖索引消灭回表
  - SQL 写法层：深分页改写（Q11）、子查询拆 join、join 驱动表控制（小表驱动大表，join_buffer 放不下驱动表就分批）、批量改写（Q12）
  - 表结构层：字段类型收窄、大字段拆表（vertical split）、冷热分离（Q16）
  - 架构层：读写分离（Q23）、缓存、ES 接管检索、数据异构——SQL 优化到头就该动架构
- **常见慢因清单**：无索引/索引失效、深分页、大事务（锁持有久 + undo 大）、锁等待（热点行见 Q9）、Buffer Pool 命中率低（内存不足，脏页刷盘抖动）
- **Buffer Pool**：InnoDB 数据页缓存，默认仅 128MB，生产通常设物理内存的 50%~60%；命中率（innodb_buffer_pool_read_requests vs reads）低于 99% 说明热数据装不下

**【易错点】**
- ❌ 慢 SQL 优化 = 加索引 → ✅ 索引只是四层之一；数据量与访问模式问题（深分页、检索、分析）动架构才是正解
- ❌ 优化单条最慢的 SQL → ✅ 聚合视角：总耗时 = 次数 × 单次耗时，TOP 模板优先；单次 5s 日跑 10 次的没有单次 500ms 日跑百万次的重要

**【追问怎么接】**
- "线上正在慢，用户在报障，怎么办？" → 先止血：processlist 找到罪魁 → kill 异常 SQL / 限流降级入口 / 必要时摘除节点；再根因：日志 + explain 复盘。顺序是可用性优先于根因
- "怎么防复发？" → 慢日志常态化 + digest 报表周会、上线前 SQL 评审（explain 卡点）、DDL 与大查询的工单审批

### Q23 · 主从复制与读写分离（⭐⭐⭐⭐⭐）

**【一句话答】** 复制链路三线程：主库 log dump 线程推 binlog → 从库 IO 线程接收写入 relay log → SQL 线程重放；默认异步（性能最好、可能丢），半同步（AFTER_SYNC 等从库 ACK）保 RPO，组复制解决自愈选主；读写分离的最大敌人是复制延迟，对策是并行复制、关键读强制走主、写后读一致性方案。

**【标准答】**
- **复制链路**（见配图）：
  - 主库事务提交写 binlog → log dump 线程把变更推给从库
  - 从库 IO 线程接收，写入 relay log（中继日志）
  - 从库 SQL 线程（可并行）重放 relay log 产生数据变更，同时写自己的 binlog（log_slave_updates 级联必需）
- **binlog 三格式**：STATEMENT（记 SQL，量小但非确定函数 now()/uuid() 造成主从不一致）、ROW（记行变更，一致性最强、量最大，**MySQL 8.0 起默认**，已核实）、MIXED（自动切换）。Canal/gh-ost 依赖 ROW
- **三种复制模式与一致性梯度**：
  - 异步（默认）：主库提交即返回——宕机时未传出的 binlog 丢失，RPO > 0
  - 半同步：至少一个从库确认收到 binlog 才向客户端返回。两个等待点：**AFTER_SYNC**（5.7+ 无损半同步，主库 binlog 落盘并等从库 ACK 后才提交事务——推荐）vs **AFTER_COMMIT**（主库先提交再等 ACK，崩溃切换时已提交事务在从库不可见，存在幻读窗口）。超时（rpl_semi_sync_master_timeout 默认 10s）自动退化为异步
  - 组复制 MGR：基于 Paxos 变体认证多数派，自动选主与成员管理——云原生时代的主流方向
- **GTID**：server_uuid:transaction_id 全局标识事务，从库自动定位复制位点， failover 不再手工对比 binlog 文件名与位置——5.7+ 新建集群的默认选择
- **并行复制**（降低延迟的核心）：
  - 5.6 库级并行（schema 级，单库业务无效）
  - 5.7 `LOGICAL_CLOCK`：同一组提交内的事务可并行（组提交粒度）
  - 8.0 `WRITESET`：按修改行集合判断无冲突即并行，单库热点下效果最好
- **复制延迟成因与对策**：
  - 成因：大事务（SQL 线程必须串行重放单事务）、从库单线程重放瓶颈、从库机器规格差、锁等待
  - 对策：拆大事务（批量写分批提交，同 Q12）、开 WRITESET 并行复制、大查询隔离到更多从库或 OLAP（Q16）、规格对齐
- **读写分离落地**：
  - 实现层：客户端框架（ShardingSphere-JDBC 读写分离规则）或代理（ProxySQL/ShardingSphere-Proxy/云 RDS 代理）
  - **写后读一致性**（最难也最常被追问）：① 写后 N 秒内同用户读强制走主（业务标记 + 网关路由）② 主键单调递增 + 读从库发现版本旧则重读主库 ③ 会话粘性（同一用户请求路由到固定从库——治标）④ 从库 GTID 等待（读请求带期望位点，从库追平才执行——MySQL 5.7 `WAIT_FOR_EXECUTED_GTID_SET`）
  - 强一致读直接走主库并控制比例（10% 量级），不要为了分离率牺牲正确性

**【易错点】**
- ❌ 半同步=不丢数据 → ✅ AFTER_SYNC 下已 ACK 的事务不丢（RPO=0），但超时会**自动退化异步**；且只保证"收到"不保证"已重放完成"，从库提升时未重放部分需靠崩溃恢复补齐
- ❌ 延迟看 Seconds_Behind_Master 就够 → ✅ 它只反映 SQL/IO 线程当前时间差，长事务期间显示 0 切换后瞬间跳变；可靠观测是 binlog 位点差 / GTID 差 + 心跳表
- ❌ 读写分离自动提升性能 → ✅ 读延迟与写后读不一致处理不当，业务正确性先出问题；分离的是读流量，复杂度转移到了一致性层

**【追问怎么接】**
- "主库宕机怎么切？" → 哨兵/MHA/Orchestrator/云高可用版检测 → 选数据最新的从库提升（GTID 集合比较）→ 其余从库重指向 → VIP/代理切流量；脑裂防护靠仲裁（多数派/第三方节点）。关键指标：RTO（分钟级目标）与 RPO（半同步 0、异步可能丢）
- "为什么从库重放会慢于主库执行？" → 主库提交是组提交并行（多事务并发落盘），从库传统上是单 SQL 线程串行重放——并行度天然不对称，这就是 WRITESET 并行复制存在的理由

### Q24 · RocketMQ 深度（⭐⭐⭐⭐，JD 点名）

**【一句话答】** 架构 = 无状态 NameServer 集群做路由 + Broker 主从存储 + 客户端；存储 = 单一 CommitLog 顺序写（所有 Topic 混写一个文件）+ ConsumeQueue 逻辑队列索引；电商选它因为事务消息、延迟消息、重试队列、消息轨迹是原生能力——这些 Kafka 都要自己造。

**【标准答】**
- **架构与路由**：NameServer 无状态、节点间不通信（AP），Broker 每 30s 向全部 NameServer 注册路由；客户端定期拉取路由，NameServer 部分宕机不影响可用性（路由短暂陈旧）
- **存储模型**（对比 Kafka 的关键差异）：
  - RocketMQ：所有 Topic/Queue 的消息**混写单一 CommitLog**（1GB 文件顺序写，写放大最小）；每个队列一个 ConsumeQueue（消费位点索引，定长 20B：offset+size+tag hash）；IndexFile 支持按 key/时间查询
  - Kafka：每个 Partition 独立日志段文件——Partition 数量大时磁盘写入从纯顺序退化为多文件顺序写，页缓存竞争加剧；RocketMQ 的单 CommitLog 在多 Topic 场景写入吞吐更稳，代价是读需要索引跳转（读扩散）
- **可靠性与刷盘**：
  - 刷盘：`SYNC_FLUSH`（每条消息落盘才返回，可靠、慢）vs `ASYNC_FLUSH`（默认，批量刷盘，宕机丢最后一批）
  - 复制：`SYNC_MASTER`（主从同步复制才返回）vs `ASYNC_MASTER`（默认）；**SYNC_FLUSH + SYNC_MASTER 才是金融级配置**，默认配置是性能取向
  - 主从切换：传统主从不会自动切（需 Dledger/云厂商能力）；Dledger 模式用 Raft 自动选主，代价是写入多数派确认
- **事务消息**（见配图状态机）：
  1. 生产者发 **half 消息**（对消费者不可见，存于系统内部 topic）
  2. 执行本地事务
  3. 按本地事务结果 commit（消息转正投递）或 rollback（删除 half 消息）
  4. 生产者宕机/未确认 → Broker **回查**：transactionCheckInterval 默认 60s、transactionCheckMax 默认 15 次，超限默认回滚（已核实）；回查实现 `checkLocalTransaction` 返回事务状态
  - 本质是**最终一致**：解决"业务库与 MQ 双写"的原子性，不是分布式事务的强一致替代品；本地事务必须幂等且回查要能查到事务执行记录（事务日志表）
- **与 Kafka 选型**（给出明确判断）：
  - 选 RocketMQ：电商交易链路——事务消息、延迟级别消息（18 个级别 1s~2h）、消费重试与死信队列、消息轨迹按 key 查询是原生能力；万级 Topic/队列支撑好
  - 选 Kafka：日志/埋点/流计算——超高吞吐（批量 + 零拷贝 + 页缓存优化取向）、与 Flink 生态原生集成
  - 表述模板："业务消息选 RocketMQ，数据管道选 Kafka；量级不到时选团队熟的"

**【易错点】**
- ❌ RocketMQ 事务消息 = 分布式事务 → ✅ 它只保证"本地事务与消息发送的原子性"（先本地后消息的最终一致）；跨服务强一致不存在通用方案，需按业务逐案权衡
- ❌ 默认配置就可靠 → ✅ 默认 ASYNC_FLUSH + ASYNC_MASTER 是性能取向，宕机可丢消息；可靠性要显式配置同步刷盘 + 同步复制
- ❌ Kafka 也"有"事务 → ✅ Kafka 事务是**生产端跨分区原子写**（读-处理-写流的 exactly-once），不是"本地事务与消息一致"语义，两者名字相同语义不同

**【追问怎么接】**
- "CommitLog 混写怎么按 Topic 读？" → 写入时生成全局 offset；ConsumeQueue 按队列存 (CommitLog offset, size)，读路径先扫 ConsumeQueue 定位再到 CommitLog 取消息——写优化读妥协的设计取舍
- "延迟消息怎么实现的？" → 按 18 个延迟级别各建 SCHEDULE_TOPIC_XXXX，定时任务扫描到期消息转回原 Topic；只支持级别不支持任意时间（任意延迟要用时间轮或云厂商增强版）
- "消费失败怎么办？" → 重试队列（%RETRY% 消费组命名空间，默认 16 次间隔递增）→ 死信队列（%DLQ%）人工处理；前提是消费端幂等
