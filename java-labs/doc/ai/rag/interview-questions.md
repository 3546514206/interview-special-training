## 第一篇 · 链路与切分

### RAG01 · 完整讲一遍 RAG 的工作流程？⭐⭐⭐⭐⭐

**【一句话答】** 离线把文档解析 → 切块 → 向量化 → 连同元数据入库；在线把问题向量化 → 召回 → 重排 → 拼 Prompt → LLM 生成并给引用。四步里只有第一步是离线的，其余三步都在用户提问时实时发生。

**【展开】**

| 阶段 | 做什么 | 我们怎么做的 |
|---|---|---|
| 解析 | PDF/HTML/Markdown → 纯文本 + 结构 | 规则解析为主（`tagging_method=rule_engine` 覆盖 92,347 条），LLM 只在规则判不准时兜底（`rule_llm_hybrid` 14,828 条） |
| 切块 | 按语义边界切成 chunk | 保留 h1/h2/h3 标题层级作为 payload，切块不丢层级 |
| 向量化 | chunk → 向量 | bge-m3，1024 维，Cosine，**必须归一化**（`modules.json` 里第三段就是 `Normalize`） |
| 入库 | 向量 + payload + id | id 用 uuid5 派生 → 同内容幂等；payload 里带 topic/difficulty/quality 等 19 个字段 |
| 召回 | 问题向量化 → ANN 检索 | HNSW，top20，带元数据过滤 |
| 重排 | 粗排 → 精排 | 当前是同源内容去重 + 阈值过滤，**独立 cross-encoder 重排还没上**（已排期） |
| 生成 | 拼上下文 → LLM | 带引用标注（h2/h3 + source_url） |

**【我们的实践】** 我们这套索引链路是**「离线批处理 + 规则优先」**：有标注的 136,098 条里，`rule_engine` 92,347 + `rule_specialist` 23,172 + `rule_junk_short_circuit` 5,641 = **121,160 条走规则（89.0%）**，LLM 参与的只有 `rule_llm_hybrid` 14,828 条（**10.9%**）——也就是说 **近九成的块没花 LLM 钱**。如果面试官问「标注/解析怎么控成本」，这组数就是答案：先规则后模型，LLM 只处理规则拿不准的。

**【追问】**
- 为什么在线只做「召回 + 生成」，不在线做解析？→ 解析是 CPU/IO 密集且确定性的，放线上会把 P99 拖垮。
- 索引什么时候重建？→ 见 RAG18。

**【易错】**
- 说成「RAG = 向量库 + LLM」。检索只是 RAG 的一个环节，**切分、元数据、重排、引用**才是决定效果的地方。

### RAG02 · 为什么需要 RAG？直接塞给大模型不行吗？和微调怎么选？⭐⭐⭐⭐⭐

**【一句话答】** 长上下文塞不下（成本 + 注意力衰减 + 无法溯源），微调改不了「知识」只能改「行为」，所以知识频繁变、要溯源、要权限隔离的场景必须走 RAG。

**【展开】**

| 方案 | 解决什么 | 不解决什么 |
|---|---|---|
| 长上下文 | 单次任务要读的材料少而全 | 成本随 token 线性涨；长文本中间位置注意力衰减；无法做权限过滤 |
| 微调 | 改输出**风格/格式/领域术语习惯** | 改不了会过期的知识；改完还是黑盒，无法溯源；每次知识更新都要重训 |
| RAG | 知识**外置**，可更新、可溯源、可按权限过滤 | 依赖检索质量；多一跳的关联推理弱 |

常见组合：**微调改行为 + RAG 供知识**（让模型先熟悉领域术语，再用 RAG 补最新事实）。

**【我们的实践】** 我们的知识库 **90% 的块来自离线批处理**，一次构建长期服务；对比微调方案，改一条知识要重训模型、灰度、回归。我们选 RAG 的核心理由是**知识更新频率**：`tagged_at` 字段让我们能按时间做增量更新与时间衰减过滤，RAG 改一条只是 upsert 一个点。

**【追问】**
- RAG 能不能完全替代微调？→ 不能。输出格式不稳定、领域黑话不熟，还是要微调兜底。
- 什么时候不该用 RAG？→ 答案高度依赖固定模板、需要 100% 确定性输出的场景，直接用规则/代码。

**【易错】**
- 说「RAG 省钱」。RAG 一次检索 + 拼接 + 生成的 token 常常比长上下文**更**贵，省的是「不用反复全量重训」和「不用把所有文档常驻上下文」。

### RAG03 · 文档分块策略怎么设计？chunk 怎么定？语义被切断了怎么办？⭐⭐⭐⭐⭐

**【一句话答】** chunk 的大小没有银弹，按「检索单元」而不是「排版单元」切：先按结构（标题/段落/表格）切，块太大再递归细切；保留 10%~20% 重叠，并在 payload 里存标题层级，让召回后能还原上下文。

**【展开】**

- **切分顺序**：结构优先（h1/h2/h3 → 段落 → 句子），语义边界（句号、标点）兜底。
- **块大小**：太小 → 语义不完整，模型拿到半句话；太大 → 一块里混多个主题，embedding 被稀释，召回精度掉。我们的实测能看出来：一条查询 top10 的分数从 0.7992 一路衰减到 0.5966（top50），后段基本是噪声块。
- **重叠**：相邻块留 10%~20% 重叠，防止答案正好卡在切点上。
- **保留层级**：把标题路径写进 payload，召回后拼上下文时能带上「这是哪一章」，模型能利用章节做消歧。
- **特殊块**：表格、代码块、公式尽量**整块不切**（跨块切割会让表格语义彻底损坏）。

**【我们的实践】** 我们把 `h1 / h2 / h3` 三级标题做成了独立 payload 字段，一块内容同时带 h1（书名）、h2（章节）、h3（小节）。这带来两个直接好处：
1. 召回后能拼出「《AI Agent 面试 288 题合集》→ 04、RAG知识库（40 题）→ 109. 如何构建和使用向量索引」这样的引用，溯源链完整（见 RAG21）。
2. 想按章节过滤时才发现 `h2` **没有建 payload 索引**（见 RAG09）——这是我们踩过的坑。

**【追问】**
- 块大小怎么调？→ 用评测集跑 Recall@K vs 平均块 token 数曲线，取拐点。我们目前还没系统扫过，是明确的待办。
- 代码文件怎么切？→ 按类/方法切，不要按行切。

**【易错】**
- 固定 500 字一刀切，然后说「重叠 20% 就够了」。块大小、重叠、层级三件事必须一起设计。

### RAG04 · Embedding 模型怎么选型？维度越高越好吗？⭐⭐⭐⭐

**【一句话答】** 维度高不等于效果好；选型主要看语言、领域、是否需要稀疏通道，然后才是维度。维度直接乘进存储和计算成本。

**【展开】**

| 判据 | 说明 |
|---|---|
| 语言 | 中文场景优选 BGE / GTE 系 |
| 领域 | 通用模型在垂直领域掉点明显，医疗/法律要专门训过 |
| 通道能力 | 稠密（dense）管语义、稀疏（sparse）管关键词。bge-m3 同时给 dense + sparse + ColBERT multi-vector |
| 维度 | 存储 ≈ 点数 × 维度 × 4B（float32）；1024 维 × 13.6 万点 ≈ 557 MB，检索时的距离计算也随维度线性涨 |
| 检索方式 | dense-only 的库，**连加 sparse 通道的资格都没有** |

**【我们的实践】** 我们用 **bge-m3**（1024 维）。关键细节是：模型目录里 `sparse_linear.pt` 和 `colbert_linear.pt` **都在**，但当前加载链路是 `sentence-transformers`（`modules.json` 只有 Transformer → Pooling → Normalize 三段），**只走 dense 通道**。所以面试时要说清楚：

> 「我们选了 bge-m3 就是为了留 sparse/ColBERT 的口子，但目前**只用了 dense**。要上混合检索，得换成 FlagEmbedding 或自己写 sparse 编码头，这是我们排在最前面的待办。」

这比硬说「我们做了混合检索」诚实，也显得真的摸过模型。

**【追问】**
- 换 embedding 模型要重建全部索引吗？→ 要，维度/语义空间都变了。Qdrant 支持 named vectors 一个集合挂多套向量，可以灰度，但存储翻倍。
- 量化能省多少？→ int8 约 4 倍压缩、召回率掉 1~3 个点，靠 rescore 补回；我们没开。

**【易错】**
- 说「维度越高语义越细腻」。维度高通常是**语料和训练目标**堆出来的，不是精度的保证。

### RAG05 · 常见的向量相似度度量：余弦、内积、L2 有什么区别？⭐⭐⭐⭐

**【一句话答】** 余弦只看方向（夹角），内积同时看方向和长度，L2 看欧氏距离。**用归一化向量时，三者单调等价**，所以关键是「有没有归一化」而不是「选哪个度量」。

**【展开】**

- 余弦相似度 = 点积 / (|a||b|)，范围 [-1, 1]，与向量长度无关。
- 内积 = a·b：向量越长值越大，**未归一化时会被高范数文档主导召回**。
- L2 = ||a-b||：距离越小越近。
- 归一化后：cos(a,b) = a·b，且 ||a-b||² = 2 - 2·a·b，三者严格单调对应，检索结果一致。
- 我们的集合 `distance=Cosine`，且 bge-m3 的 `modules.json` 第三段是 `Normalize` —— **模型侧归一化 + 库侧 Cosine**，这是标准搭配。

**【我们的实践】** 有个可验证的证据：把一条已入库的原文截断后重新向量化再检索，**score 恰好 = 1.0000**。这只有在「归一化 + Cosine」下才成立（内积会因为截断改变范数而不再是 1）。这条实测也是我们做写前查重的基础（见 RAG16）。

**【追问】**
- 内积什么时候更好？→ 想让「长文档更可能被召回」时；也常用在 CLIP 这类已经训练好内积空间的模型上。
- 为什么很多库默认 Dot？→ 配合归一化向量与余弦等价，同时少一次开方。

**【易错】**
- 说「余弦比内积准」。在**已归一化**的前提下两者结果完全一样，不存在准不准的差别。

### RAG06 · 什么是 ANN？为什么必须用近似检索？⭐⭐⭐⭐⭐

**【一句话答】** ANN（Approximate Nearest Neighbor）用「牺牲一点召回精度，换数量级的速度」；13.6 万点 × 1024 维的暴力扫描是 O(N×d)，而 HNSW 只需要访问图上少数节点。

**【展开】**

- 暴力检索（Exact）：每次查询算 N 次距离。13.6 万 × 1024 维 ≈ 1.4 亿次乘加，单核几十毫秒到几百毫秒；再乘并发就不够了。
- ANN 的代价是**召回率**：返回的 Top-K 里可能漏掉真正的最近邻，所以才有 `hnsw_ef` 这个「搜索宽度」旋钮来换召回。
- Qdrant 有个开关 `full_scan_threshold`（默认 10000）：集合小于这个规模时**直接暴力扫**，不建 HNSW 图。我们的集合 13.6 万点，已经超过阈值，所以走 HNSW。

**【我们的实践】** 同一个集合两种取数方式的实测：

| 操作 | 数据量 | 耗时 |
|---|---|---|
| ANN 检索 top20 | 1 次查询 | **114 ms**（p50，含网络往返） |
| 全量 scroll（不带 payload） | 5,000 点 | 143 ms |
| 全量 scroll（带 payload） | 5,000 点 | **14,396 ms**（**101 倍**） |

结论有两层：
1. **在线检索绝不能退化成扫全量**——那是 13.6 万点 × 1024 维的暴力距离计算。
2. **离线批量搬运才是真正的雷区**：同样 5,000 个点，带 payload 比不带慢 101 倍，因为 payload 里有 19 个字段、content 平均上百字。我们的导入管道如果图省事用 `scroll` 拉全量再在客户端过滤，会比在服务端过滤慢两个数量级。

**【追问】**
- 什么时候该用 exact？→ 集合小（< 1 万）、要求零召回损失、或者做离线评测基准时。
- ANN 的召回率怎么量？→ 拿 exact 结果当 ground truth，比 Recall@K。

**【易错】**
- 把 ANN 说成「近似所以不准」。ANN 的召回率通常 >95%，**用速度换的**，而且 Qdrant 支持用 `exact=True` 或把 `full_scan_threshold` 调大来对照。

### RAG07 · HNSW 的原理？m、ef_construct、hnsw_ef 三个参数各管什么？⭐⭐⭐⭐⭐

**【一句话答】** HNSW 是分层可导航小世界图：查询从最稀疏的顶层图贪心下降到底层，途中维护候选集。`m` 控制图的连通度（建索引时每个节点的出边数），`ef_construct` 控制建图时的候选队列大小（召回/内存/建索引耗时的权衡），`hnsw_ef` 控制**查询时**的候选队列大小（召回/延迟的权衡）。

**【展开】**

- **m**：每个节点最多连多少个邻居（默认 16）。m 大 → 图更密 → 召回高、内存大、建索引慢。
- **ef_construct**（`m` 的孪生，默认 100）：建索引时每个节点的候选队列。调大 → 图质量高、构建慢。
- **hnsw_ef**（查询参数，默认与 `m` 相关）：查询时保留多少候选。调大 → 召回高、延迟高。**它只影响查询，不影响索引，是唯一能在线调的旋钮。**
- `full_scan_threshold`：小于它直接暴力扫。

**【我们的实践】** 我们的集合用**全是默认值**（m=16 / ef_construct=100 / full_scan_threshold=10000），实测 `hnsw_ef` 从 32 调到 512：

| hnsw_ef | 32 | 64 | 128 | 256 | 512 |
|---|---|---|---|---|---|
| top20 延迟 p50 | 117.3 ms | 115.4 ms | 115.4 ms | 121.6 ms | 128.3 ms |

**在 13.6 万点这个量级，ef 几乎不花钱**（32→512 只差 11 ms）。这说明瓶颈根本不在 HNSW 的搜索，而在网络往返和序列化。所以我们**没有为了延迟去调 ef**——这是有数据支撑的「不优化」。

⚠️ 提醒自己：这是我们这个规模 + 这个硬件的结论。**到百万级、或者 ef 已经调到 512 仍然召回不够时，再往上加才有意义**；不要背「ef 越大越慢所以要调小」这种空结论。

**【追问】**
- ef 调多大？→ 先用默认值，在评测集上比 Recall@K 与延迟的曲线，找拐点。
- HNSW 内存怎么估？→ 每个点存向量 + 邻居 id，m=16 时约 16×2（双向）×4B ≈ 128 B/点 的额外开销。

**【易错】**
- 说「m 越大越准所以设 64」。m 是**建索引**参数，改它要重建全量索引，代价远大于调 hnsw_ef。

## 第二篇 · 检索与排序

### RAG08 · Qdrant 的 payload 是什么？为什么过滤字段必须建索引？⭐⭐⭐⭐⭐

**【一句话答】** payload 是挂在每个向量点上的 JSON 附加信息（Qdrant 里既是业务元数据也是过滤依据）；**过滤字段不建索引时，服务端会退化成扫全量点做过滤**，我们的实测是 12.5 倍延迟。

**【展开】**

- Qdrant 的过滤发生在 HNSW 搜索过程中：先用 payload 索引把候选集缩小，再在候选集里跑图搜索。
- 建了索引（keyword / integer / float / bool / geo / datetime / array）→ 服务端能用倒排/有序结构定位候选。
- 没建索引 → 服务端必须把所有点拉出来逐个比对 payload，**HNSW 完全失效**。
- 索引是**按字段**建的，且**建索引时会跳过没有该字段的点**——这一点有真实后果（见 RAG09）。

**【我们的实践】** 同一个查询（top20），只改过滤条件：

| 过滤条件 | 字段有索引？ | 延迟 p50 | 对比 |
|---|---|---|---|
| 不过滤 | — | 116.7 ms | 1.0x |
| `topic = 数据库` | ✅ | 115.7 ms | 1.0x |
| `topic = 数据库` + `difficulty = intermediate` | ✅ | 115.2 ms | 1.0x |
| `h2 = 04、RAG知识库（40 题）` | ❌ | **1,456 ms** | **12.5x** |

面试可以直接说：**「我们踩过一次：想按章节过滤，发现 h2 没建索引，延迟从 116 ms 飙到 1,456 ms。payload 索引是 RAG 里性价比最高的一次优化——建索引是一次性成本。」**

**【追问】**
- 索引能删吗？→ 能，`delete_field_index`。
- 动态字段值很多怎么办？→ 用数组类型索引，别开成千上万个不同 key。

**【易错】**
- 说「过滤是免费的」。过滤免费**的前提是字段建了索引**。

### RAG09 · 元数据过滤怎么设计才能真正提升精度？（我们踩过的坑）⭐⭐⭐⭐⭐

**【一句话答】** 过滤字段要**按检索意图设计**，不是把能想到的都塞进去；而且必须保证「要过滤的字段在所有点上都有值」，否则过滤会**静默丢点**。

**【展开】**

一个可用的元数据体系通常包含四类：

| 类别 | 字段 | 作用 |
|---|---|---|
| 主题/域 | `topic`、`family` | 把检索限定在相关领域 |
| 难度/类型 | `difficulty`、`content_type` | 面向不同人群给不同深度内容 |
| 质量 | `quality` | 过滤低质块（解析乱码、重复片段） |
| 权限/来源 | `source`、租户字段 | 多租户隔离、限定可信来源 |

**【我们的实践 —— 两个真实的坑】**

**坑 1：过滤字段有缺失值会静默丢点。**
我们的 10 个 payload 索引里，`quality` 字段**只有 83,406 个点有值**（61.3%），其余 52,720 个点没有这个字段。而 `topic` 有 136,116 个点（几乎全覆盖）。含义很具体：

> 如果线上按 `quality = good` 过滤，**那 38.7% 没有 quality 字段的点会被一起滤掉**——它们不是「质量差」，是「没打过这个标」。缺失值和低质是两件事，混在一个过滤条件里就是事故。

我们的处理方式是：过滤用**覆盖率高**的字段（topic/difficulty/use_case），质量用**召回后过滤**而不是召回前过滤（见 RAG12 的去重逻辑）。

**坑 2：过滤不是「排序完再筛」，是「换候选集」。**
实测：同一条查询 `RAG 检索不到相关文档怎么办`，不加过滤的 top10 与加 `topic=数据库` 过滤的 top10 **只有 5 个重合**。过滤会改变召回结果本身，所以过滤条件写错会直接毁掉结果，而不是「少几条」。

**【追问】**
- 过滤和 Rerank 谁先？→ **先过滤后召回**（缩小候选集），Rerank 在召回之后做精排。
- 过滤太严召回空了怎么办？→ 降级策略：过滤后不足 K 条时，用宽条件兜底再补。

**【易错】**
- 把所有过滤条件都加上求「精准」。过滤越严越可能空召回，得有降级链路。

### RAG10 · 多租户场景下 RAG 的权限隔离怎么做？⭐⭐⭐⭐⭐

**【一句话答】** 隔离分三层：集合级（一租户一集合，最强最贵）、分区级（一个集合 + 租户字段 + payload 索引）、应用级（先按租户过滤再检索）。绝大多数 ToB 场景用第二层。

**【展开】**

| 隔离级别 | 做法 | 优点 | 代价 |
|---|---|---|---|
| 集合级 | 每租户一个 collection | 物理隔离，最简单 | 集合数量爆炸，小集合吃 HNSW 内存 |
| 分区级 | 一个 collection + `tenant_id` 字段 + 索引 | 共享索引资源，运维简单 | 依赖过滤正确性；大租户会拖累小租户 |
| 应用级 | 检索层强制注入过滤条件 | 最灵活 | 一旦漏加过滤条件就是越权事故 |

无论哪种，**过滤条件必须由服务端从会话身份推导，绝不能由前端传**。

**【我们的实践】** 我们这套知识库是**单租户的个人/团队知识库**，没有做租户字段——但架构上预留了：`source` 字段已建索引，语义上就是「数据来源域」，要做多租户时把它换成 `tenant_id` 即可，索引策略不用变。

想强调的是我们**实测过的那个反面教材**：既然「过滤字段没建索引 = 慢 12.5 倍」，那么**隔离字段必须和普通元数据一样建索引**——很多团队做多租户时把 tenant_id 存了却忘了建索引，结果隔离逻辑上线后延迟直接翻十几倍。

**【追问】**
- 大租户影响小租户怎么办？→ 分集合、分片，或者按租户分 HNSW 段。
- 怎么保证过滤一定生效？→ 在 DAO/检索服务的唯一入口收口，业务代码拿不到裸 collection；再加一条「越权用例」的自动化测试。

**【易错】**
- 说「用 prompt 告诉模型不要返回别的租户的内容」。**模型不是权限边界**，隔离必须在检索层做。

### RAG11 · 召回数量 K 怎么定？召回不够怎么办？⭐⭐⭐⭐⭐

**【一句话答】** K 是「召回预算」不是「答案条数」：先粗排 K₁ 个（比最终要喂给模型的多一个数量级），重排/去重/过滤后再截到 K₂ 个喂模型。召回不够要靠**换路**补，不是靠调 K。

**【展开】**

- 两段式：K₁（召回窗口，通常 50~200）→ 去重/重排 → K₂（进 Prompt，通常 3~8）。
- K₂ 决定 token 成本和「中间信息被忽略」的风险；K₁ 决定召回上限。
- 召回不够的排查顺序：
  1. **库里根本没有**（数据缺失）→ 补数据；
  2. **切分把答案切碎了** → 调整块大小/重叠；
  3. **embedding 不匹配**（问法与文档用词差异大）→ Query 改写 / 加 sparse 通道；
  4. **过滤太严** → 放宽或加降级；
  5. **确实需要多跳** → Agentic RAG / GraphRAG。

**【我们的实践】** 我们的 score 衰减曲线（查询 `RAG 检索不到相关文档怎么办`，bge-m3 + Cosine）：

| 排名 | top1 | top5 | top10 | top20 | top50 |
|---|---|---|---|---|---|
| 分数 | 0.7992 | 0.6774 | 0.6425 | 0.6251 | 0.5966 |

**top10 之后基本是平台期**（0.6425 → 0.5966 只降了 0.046），说明第 10 名之后的块大概率是噪声。所以我们当前 `top20` 召回 + 去重 + 阈值过滤的策略是够的，**再往上放 K 收益很小、token 成本线性涨**。

另一条真实数据：一次 `MySQL 间隙锁在什么场景下会加锁` 的 top20 召回里，**有 4 条是重复正文**（唯一内容只有 18 条）→ 20 个名额被白白占掉 2 个。这说明我们的 K₁ 定得太「信任召回」而没有做去重（见 RAG12）。

**【追问】**
- 为什么不直接把 K₁ = K₂？→ 因为粗排精度差，直接取 top20 前 5 喂模型，很可能第 1 条就不对。
- K₂ 怎么定？→ 跟 token 预算一起定。

**【易错】**
- 把 topK 调大当「召回兜底」。召回到 50 条但只喂 5 条，问题出在前半段排序，不在后半段数量。

### RAG12 · 为什么检索之后还要 Rerank？Bi-Encoder 和 Cross-Encoder 有什么区别？⭐⭐⭐⭐⭐

**【一句话答】** 向量检索是「粗筛」：bi-encoder 分别编码 query 和 doc，doc 向量可离线预计算，所以快但精度有限；cross-encoder 把 query+doc 拼起来送进模型算相关性，准但慢，所以只对粗筛出的几十条做精排。

**【展开】**

| | Bi-Encoder（召回） | Cross-Encoder（Rerank） |
|---|---|---|
| 输入 | query 单独编码、doc 单独编码 | query + doc 拼接一起编码 |
| 预计算 | doc 向量可离线算 | 不行，必须在线跑 |
| 速度 | 快（毫秒级，能扫全库） | 慢（几十~几百 ms/对） |
| 精度 | 中 | 高 |
| 位置 | 第一段，K₁=50~200 | 第二段，K₁→K₂=3~8 |

**【我们的实践】** 我们**目前没有独立的 cross-encoder 重排**，这一层的「精排」是用 **内容去重 + 相似度阈值**顶上去的。这是一个诚实的现状，也是我们下一步最想补的能力（模型目录里 bge-m3 的 `colbert_linear.pt` 已经在了，但走 ColBERT 路线意味着要上 multi-vector 索引，存储和查询复杂度都要重新评估）。

我们在召回侧能拿出来讲的**替代手段**是**混合打分**：dense 分数（语义）+ 关键词命中（精确词）。比如问「HNSW 和 IVF 索引有什么区别」，纯 dense 靠语义近邻，「IVF」这种专有名词的精确匹配反而是弱项——sparse 通道正是补这个的。

**【追问】**
- Rerank 放哪一层？→ 在「召回 → 过滤 → 去重」之后，「截断进 Prompt」之前。
- 一定要 rerank 模型吗？→ 不一定。BM25 rescore、关键词加权、规则去重都能当二阶段，核心是「粗排和精排用不同的信号」。

**【易错】**
- 说「rerank 让召回率变高」。**rerank 改的是排序，不改召回**——真正没被召回的文档，rerank 也救不回来。

### RAG13 · 混合检索（dense + sparse）怎么做？⭐⭐⭐⭐

**【一句话答】** dense 负责语义、sparse 负责关键词，两路各召回一批候选再融合（分数加权或 RRF）。专有名词、型号、报错码、人名这类精确匹配上，sparse 显著优于 dense。

**【展开】**

- **dense**：双塔，语义相似，擅长「意思相近但用词不同」。
- **sparse**：词权重稀疏向量（每个维度对应一个词表项），擅长精确词命中。BM25 是稀疏检索的经典实现。
- **融合方式**：
  - 分数归一化后加权：`score = α·dense + β·sparse`
  - **RRF（Reciprocal Rank Fusion）**：只看名次不看分数，`score = Σ 1/(k + rank)`，对两个通道的分数尺度不敏感，最常用。
- Qdrant 原生支持：集合可以同时挂 dense 和 sparse 两个 named vector，`query` 时用 `prefetch` + `fusion`（RRF/DBSF）。

**【我们的实践】** 我们**还没接 sparse 通道**，但选型时就是奔着它去的：

- 模型：bge-m3（原生输出 dense + sparse + multi-vector），目录里 `sparse_linear.pt` 在；
- 阻塞点：当前检索链路走 `sentence-transformers`，它只暴露 dense 向量（`modules.json` 三段：Transformer → Pooling → Normalize），要拿 sparse 得换 FlagEmbedding 或自己接 `sparse_linear`；
- 库侧：Qdrant 支持 sparse named vector，接入成本主要在模型侧。

这是很好的「有规划但诚实」的答题姿态：**「混合检索是我们下一步，模型选型时已经为它留了口子，现状是纯 dense。」**

**【追问】**
- 什么时候纯 dense 就够了？→ 语料和问法用词高度一致、术语少（如内部 FAQ）。
- sparse 的词表从哪来？→ bge-m3 自带词表；用 BM25 的话是引擎的分词词表。

**【易错】**
- 说「混合检索就是把两个分数加起来」。两个通道的分数尺度不同，必须归一化或用 RRF。

### RAG14 · 相似度阈值怎么定？检索不到相关内容怎么办？⭐⭐⭐⭐⭐

**【一句话答】** 阈值必须**用你自己的数据标定**，不能抄别人的 0.7。我们的做法是：取一批「库里肯定有」的查询和一批「库里肯定没有」的查询，看 top1 分数是否分得开，把阈值定在中间。

**【展开】**

标定流程：
1. 准备正例集（知识库覆盖的问题）和负例集（库外问题）；
2. 各跑一遍检索，记录 top1 分数；
3. 看两组分布是否可分（我们这里是可分的）；
4. 阈值取可分区间的中部，**偏保守**（宁可拒答也别幻觉）；
5. 线上再加「召回后按内容去重 + 低于阈值的丢弃」。

**【我们的实践 —— 一条可以直接讲的实验】**

我们用 7 条命中域查询和 6 条落空域查询实测（bge-m3 1024 维 / Cosine）：

| 类别 | top1 最低 | top1 平均 | top1 最高 | 例子 |
|---|---|---|---|---|
| 命中域 | **0.6913** | 0.7572 | 0.8052 | 「MySQL 间隙锁在什么场景下会加锁」0.8052；「Kafka 消费者 rebalance 是怎么触发的」0.6913 |
| 落空域 | 0.4902 | 0.5591 | **0.6126** | 「明天股市会涨吗」0.6126；「推荐几部好看的电影」0.4902 |

**两组不重叠，间隙是 [0.6126, 0.6913]，我们把阈值定在 0.65。** 落空域那条「明天股市会涨吗」之所以还能到 0.6126，是因为知识库里有美团那本实战年货，里面有「预测股票市场」的章节——**语料里真的出现了相关内容，模型没作弊**。

⚠️ 诚实说明：样本只有 13 条，这是**工程起点不是终点**。正式上线要用几百条标注样本扫 ROC，取业务可接受的漏召/误召平衡点。

**【追问】**
- 阈值和 topK 怎么配合？→ 阈值卡「有没有相关」，topK 卡「拿几条」。两者都要。
- 拒答的文案怎么写？→ 说清「知识库里没有」，而不是让模型编。

**【易错】**
- 直接用 0.7 / 0.8 这类拍脑袋的数。**阈值是标定出来的，不是抄来的**——这句本身就是加分点。

### RAG15 · 重复内容怎么治？幂等写入怎么做？⭐⭐⭐⭐

**【一句话答】** 三层：写入层用内容派生的确定性 id（幂等）→ 写前做语义查重（挡住改写重复）→ 召回后按内容哈希去重（挡住历史脏数据）。我们三层都做了前两层，第三层是体检后补的。

**【展开】**

1. **幂等 id**：`point_id = uuid5(NAMESPACE, "memory:" + 正文)`，同内容重跑只更新同一个点，不会产生重复。
2. **写前语义查重**：先用同一模型向量化，检索已有点，命中分数 ≥ 阈值就跳过（我们用 0.95）。
3. **召回后去重**：按 `content` 的哈希去重，防止历史脏数据挤占名额。

**【我们的实践】**

- **幂等与查重的实测**：把一条已入库的原文截断后重新向量化再检索，**score 恰好 1.0000** 且命中同一条 id（归一化 + Cosine 的必然结果）；**次相似只有 0.7508~0.7867**。所以 **0.95 的查重阈值留足了余量**：既能挡住重复，又不会误杀语义相近的不同段落。
- **但批量导入管道没有全局去重**。我们做过一次全量体检：136,126 个点里只有 120,961 份唯一正文，**6,295 组重复正文，21,460 个点（15.8%）落在重复组里**。抽样看到同一份教材的不同章节切片被重复入库，最大的一组有 169 个点。
- **代价是实测出来的**：一次 `MySQL 间隙锁在什么场景下会加锁` 的 top20 召回里，**4 条是重复正文**（唯一内容只有 18 条）。也就是说 20 个名额里有 2 个是白给的。

修复方向（按优先级）：
1. 召回后按 `content` 哈希去重（改动最小，立刻止损）；
2. 批量导入走幂等 id + 写前查重（治本，但需要重跑管道）；
3. 导入时按「来源 + 章节 + 块序号」派生 id，同时保留正文哈希做二次去重。

**【追问】**
- 为什么不用随机 id？→ 随机 id 下重跑就产生重复点（我们库里 68.4% 的 id 是 uuid4 随机生成的，正是这个后果）。
- 去重放在哪一层？→ 写入层治本，召回层兜底。

**【易错】**
- 只做写前查重就以为万事大吉。**历史脏数据不会自己消失**，召回后去重是必须的兜底。

### RAG16 · RAG 检索质量怎么评测？核心指标有哪些？⭐⭐⭐⭐⭐

**【一句话答】** 分两段评：检索段看 Recall@K / MRR / nDCG，生成段看忠实度（Faithfulness）和答案相关性（Relevancy）。评测集是人工标的一批「问题 → 应该命中的 chunk id」，没有评测集就等于没有 RAG。

**【展开】**

| 指标 | 定义 | 关心什么 |
|---|---|---|
| Recall@K | 前 K 条里命中的相关文档比例 | 召回够不够 |
| Precision@K | 前 K 条里相关的比例 | 精不精 |
| MRR | 相关文档排名的倒数的平均 | 好的排前面 |
| nDCG | 考虑多个相关文档的排名折扣 | 多级相关时最准 |
| Faithfulness | 答案是否都能在上下文里找到依据 | 幻觉 |
| Answer Relevancy | 答案是否切题 | 答非所问 |

- 工程化：**RAGAS** 把这些指标标准化（LLM-as-judge），但 LLM 判分本身有噪声，关键指标要有人工标注集对齐。
- 分段定位很重要：检索没召回 → 改检索；召回了但答案错 → 改 Prompt/模型/上下文组装。**用总分无法定位。**

**【我们的实践】** 我们目前**没有成体系的评测集**，只有上面那些单点体检（分数分布、阈值标定、重复率、过滤代价）。这是我们最大的短板，也是我下一步要补的：先人工标 100 条（问题 → 期望命中的 h2/h3），跑 Recall@10 / MRR 基线，再谈优化。

顺带一个**现成的半自动信号**：我们可以拿「命中域 vs 落空域」的 top1 分数分布当一个粗粒度的「检索是否分得开」指标——比人工评测便宜，能做回归监控。

**【追问】**
- 评测集怎么造？→ 从真实日志里采样问句，人工标相关 chunk；也可用 LLM 生成的问答对做冷启动。
- 线上怎么持续监控？→ 记录每次检索的 top1 分数分布、拒答率、空召回率、重复率——这些不需要标注就能看趋势。

**【易错】**
- 只看最终答案对不对。**答案对但检索错了**（模型靠自身知识答对）和**检索对了但答案错**，优化方向完全不同。

## 第三篇 · 生产与工程

### RAG17 · 索引怎么增量更新与删除？⭐⭐⭐⭐

**【一句话答】** 更新靠 upsert（id 固定 → 覆盖同一个点），删除靠按 filter 批量 delete；文档整体重解析时用「先删后建」并用 alias 切换，避免半成品被检索到。

**【展开】**

- **单块更新**：`upsert` 同一个 id → 整点替换。**注意 payload 也会被替换**，所以要先 `retrieve` 合并再写，否则会抹掉已有的标注字段。
- **删除**：`delete` 带 filter，删整个文档的所有块。
- **批量重建**：两种流派——
  - 就地更新：简单，但重建期间新旧混合，召回会拿到半成品；
  - **影子集合 + alias 切换**：建新集合 → 全量灌 → 灌完把 alias 指向新集合 → 删旧集合。Qdrant 的 alias 原生支持这个模式。

**【我们的实践】** 我们的写入工具就踩过 **upsert 整点替换抹 payload** 的坑，所以流程是固定的：**先 retrieve 出旧 payload → 合并新字段 → 再 upsert**。这条写在工具的注释里，因为很容易被后人一笔改掉。

我们还没做影子集合 + alias 切换——当前规模（13.6 万点）重建一次的成本还扛得住，但这是扩容到百万级之前必须补的。

**【追问】**
- 删文档时怎么保证不残留？→ 按 `doc_id` 过滤删除，别按文件名模糊匹配。
- 更新期间用户查到的还是旧版吗？→ 就地更新会短暂不一致；影子集合 + alias 可以做到原子切换。

**【易错】**
- 用随机 id 写入后想「更新」，只能删了重写——所以 id 必须由内容/文档键派生。

### RAG18 · 文档解析与数据清洗怎么做？⭐⭐⭐⭐⭐

**【一句话答】** 解析质量是 RAG 的天花板：PDF 抽出来的乱码、页眉页脚、目录、代码块被截断，embedding 再准也没用。所以要**在入库前把脏数据挡住**，并把质量作为元数据存下来。

**【展开】**

- 常见脏数据：PDF 乱码（尤其扫描件需要 OCR）、页眉页脚、目录页、跨页表格被切断、代码块被换行拆散、纯图片块（无文字）、超短块（噪声）、超长块（embedding 被截断）。
- 处理手段：版面解析（保留标题层级）、规则清洗（去页眉页脚、去目录）、短块短路丢弃、块级质量打分、**把清洗结果作为 payload 存下来**。

**【我们的实践】**

- 我们的标注管道有专门的 **`rule_junk_short_circuit`（5,641 条）** 这一档——就是「规则判定为垃圾块直接短路丢弃」，说明清洗是入库流程里的一等公民，不是事后补救。
- 质量字段分布：`good 40,677 / ok 30,405 / low 12,324`。**故意保留 low 而不是全删**——因为实测发现落空域查询的 top1 会被乱码块占据（见下），保留并打标，才好过滤。
- **乱码实锤**：我们查「我家猫不吃饭怎么办」时，top1 命中的是一段 PDF 抽取的乱码（`sa皿;J, …`），score 0.5546；查「今天天气怎么样」时 top1 也是乱码（score 0.5947）。**乱码文本在向量空间里不是噪声，是「一段看不懂但统计上像文本」的向量**，纯 dense 检索会把它召回来。
- 我们的解法方向：解析阶段做质量判定 + 乱码检测（如可打印字符比例），把这类块的 `quality` 标成 low 并在召回后过滤；**根治要靠 OCR 质量或换解析器**。

**【追问】**
- 乱码怎么自动检测？→ 字符可打印率、字典命中率、非常规字符比例。
- 扫描版 PDF 怎么办？→ 必须 OCR，OCR 质量决定上限。

**【易错】**
- 以为「解析是数据工程师的事」。**解析质量直接决定召回上限**，而且脏数据在向量库里是隐形的——检索时你看不见它，只能看见它排在第一。

### RAG19 · 检索延迟从哪来？优化顺序是什么？⭐⭐⭐⭐⭐

**【一句话答】** 端到端延迟 = 向量化 + 网络往返 + 服务端检索 + payload 传输 + LLM 生成。**优化前先分段量**，我们量出来的结论是：13.6 万点规模下，检索侧几乎没有优化空间，瓶颈在网络和模型。

**【我们的实践 —— 分段实测】**

| 环节 | 实测 | 说明 |
|---|---|---|
| 本地向量化 1 条 | **≈14 ms**（p50，实测 13~15 ms） | bge-m3，XLM-RoBERTa 24 层，CPU |
| 批量向量化 8 条 | 15.2 ms | 批处理摊薄后约 1.9 ms/条 |
| 服务端检索 top20 | **114 ms**（p50） | 含网络往返 |
| 检索 top5 / top10 / top50 | 119 / 118 / 139 ms | **K 从 5 到 50，延迟只涨 20 ms** |
| `hnsw_ef` 32→512 | 117→128 ms | 调 ef 收益极小 |
| 带索引过滤 | 115.7 ms | 与不过滤持平 |
| 无索引字段过滤 | 1,456 ms | **12.5x，唯一真正的大坑** |
| scroll 5,000 点（带 payload） | 14,396 ms | **比不带 payload 慢 101 倍** |

由此得到的**优化优先级**（不是通用理论，是我们的实测排序）：

1. **payload 索引**——一次性的成本换 12.5 倍的延迟，收益最高；
2. **批量搬运时只取需要的字段**——101 倍差距；
3. **向量化批处理**——13 ms/条 → 1.9 ms/条；
4. **调 hnsw_ef**——13.6 万点规模下几乎无收益，**不调**；
5. **上量化**——当前没开；int8 能省 4 倍内存，代价是召回掉 1~3 个点，要配 rescore。

**我们的结论**：这个规模下，**检索侧优化的天花板就是「别用错字段过滤」**。真正的大头在 LLM 生成那一步（秒级），而我们把 114 ms 花在检索上是划算的。

**【追问】**
- 向量化能不能更快？→ 上 GPU、换更小的模型、或对高频 query 做**查询缓存**（同一 query 直接复用向量）。
- 端到端怎么做缓存？→ query 向量缓存 + 结果缓存，注意权限维度的缓存键。

**【易错】**
- 上来就调 ef / 加机器。先分段量，找占比最大的那一段。

### RAG20 · 生产环境怎么控制成本？⭐⭐⭐⭐

**【一句话答】** 成本从三处来：**token（上下文拼接 + 生成）、索引（存储 + 构建算力）、算力（向量化 / 重排）**。对应三个杠杆：控制进 Prompt 的条数、量化与降维、把规则/小模型放在链路前面。

**【展开】**

| 成本项 | 手段 |
|---|---|
| 生成 token | K₂ 压到 3~5；历史消息摘要/截断；Prompt 缓存；简单问题走小模型 |
| 索引存储 | 量化（int8/scalar）；维度压缩；冷数据下沉 |
| 构建算力 | 规则优先，LLM 只处理拿不准的；批量向量化；增量更新而非全量重建 |
| 检索算力 | payload 索引；查询向量缓存；批处理 |

**【我们的实践】**
- **标注成本**：我们的 `tagging_method` 分布就是成本策略的证据——`rule_engine` 92,347 + `rule_specialist` 23,172 + `rule_junk_short_circuit` 5,641 = **121,160 条走规则（89.0%）**，LLM 参与的只有 `rule_llm_hybrid` 14,828 条（**10.9%**）。粗算：把标注全交给 LLM，成本是这个数的 **9 倍以上**。
- **构建成本**：全量重跑一次索引 = 13.6 万次向量化 + 13.6 万次 upsert。我们的对策是**增量**：按 `tagged_at` 只处理变更的部分。
- **存储成本**：1024 维 × 136,126 点 × 4B ≈ **557 MB**（未量化）。上 int8 量化能压到约 140 MB。
- **生成成本**：我们目前 K₂ 取 3~5，正好卡在「够回答」和「不多花」之间。

**【追问】**
- 什么时候该上量化？→ 内存吃紧或数据量过百万时；召回掉点可以用 rescore 补。
- 缓存的 key 怎么设计？→ query 文本 + 权限维度 + 索引版本号；索引版本变了缓存要失效。

**【易错】**
- 只盯着 LLM 的 token 单价。**构建成本和索引存储经常是被忽略的大头**。

### RAG21 · 引用与溯源怎么做？⭐⭐⭐⭐

**【一句话答】** 每个 chunk 入库时就带「可回溯的坐标」（文档 id + 标题路径 + 原文位置 + URL），召回后把这个坐标和正文一起返回，生成时要求模型给引用编号，前端把编号映射回原文位置做跳转。

**【展开】**

- 入库时存：`doc_id`、`h1/h2/h3`、`page_no`（PDF 页码）、`chunk_idx`、`source_url`。
- 召回结果里带回这些坐标 → 拼 Prompt 时给每块编号（`[1] [2] [3]`）。
- Prompt 里要求模型在句末标 `[1]`，并禁止编造编号。
- 后处理：校验模型引用的编号是否在候选集合内，非法编号丢弃。
- 关键：**原文位置必须由入库管道写，不靠模型推断**。

**【我们的实践】** 我们已经在做了：`source_url`、`h1/h2/h3`、`chunk_idx` 全是 payload 字段，召回后能拼出完整引用链：

> 《AI Agent 面试 288 题合集》 → 04、RAG知识库（40 题） → 109. 如何构建和使用向量索引？HNSW 和 IVF 有什么区别？

而且 `source_url` 直接可点（我们库里存的是 `https://javabetter.cn/ai/video/` 这类原始地址）。`cs_books` 那部分还带 `book_name` + `page_no`（PDF 页码），是天然的定位坐标。

**【追问】**
- 怎么防模型编引用？→ 只给合法编号集合 + 后置校验，编号不在集合内的句子判为幻觉。
- 引用精度怎么评？→ 逐句核对「这句话的依据在不在引用的那一块里」。

**【易错】**
- 让模型自己写「根据文档 X」。模型不知道文档 X 是谁，**坐标必须由系统拼进 Prompt**。

### RAG22 · 幻觉怎么压？⭐⭐⭐⭐⭐

**【一句话答】** 四个杠杆一起上：**只喂检索到的内容**（不许模型靠参数知识补）、**给出引用并校验**、**低于阈值就拒答**、**检索不到时明说**。核心是让「没有依据」变成一个可表达的状态。

**【展开】**

1. **Prompt 层**：明确「只能依据 <context> 回答，context 里没有就说不知道，不要用你自己的知识补」。
2. **阈值层**：top1 分数低于阈值 → 直接返回「知识库里没有相关内容」，不进生成。这是最有效的一条，因为幻觉的根因是「模型被逼着回答」。
3. **引用层**：要求标引用编号 + 后置校验编号合法性。
4. **温度层**：事实性问答用低温度（甚至 greedy）。

**【我们的实践】** 我们把**拒答阈值**做成了硬闸门而不是提示词里的软建议：

- 阈值标定见 RAG14（命中域最低 0.6913 / 落空域最高 0.6126 → 阈值 0.65）；
- 落空域的典型例子：问「我家猫不吃饭怎么办」，库里的 top1 是乱码块（score 0.5546）——**低于阈值，直接拒答**，不把乱码喂给模型；
- 这一条同时挡住了「乱码被当答案」和「模型用参数知识编答案」两种幻觉。

另外我们的 `quality` 字段（good/ok/low）是**第二道防线**：召回后把 low 质量的块剔掉，减少「依据本身有问题」的幻觉。

**【追问】**
- 拒答太多用户会烦怎么办？→ 分档：低置信度给「相关文档链接 + 建议换个问法」，而不是干巴巴一句「不知道」。
- 模型还是编怎么办？→ 上 groundedness 评测（ faithfulness 指标）持续监控，低于阈值就降级到「只返回检索结果」。

**【易错】**
- 只在 Prompt 里写「不要编」。**Prompt 是请求，不是保证**；阈值闸门才是保证。

### RAG23 · Agentic RAG 和传统 RAG 有什么区别？⭐⭐⭐⭐

**【一句话答】** 传统 RAG 是「一次检索 → 一次生成」的固定流水线；Agentic RAG 把检索变成**模型可调用的工具**，由模型决定查几次、查什么、要不要换关键词重查、要不要先查 A 再查 B。

**【展开】**

| | 传统 RAG | Agentic RAG |
|---|---|---|
| 检索次数 | 固定 1 次 | 不定，由模型决定 |
| 查询改写 | 固定预处理 | 模型自己重写/拆解 |
| 多跳 | 难 | 天然支持（多轮工具调用） |
| 成本 | 可预测 | 不定，可能爆炸 |
| 延迟 | 稳定 | 波动大 |

关键能力：**自我批判**（发现结果不够好就换词再查）、**查询分解**（复杂问题拆成多个子查询）、**多源聚合**。

**【我们的实践】** 我们的知识库检索目前是一个**受控的工具调用**（有明确的 query → 召回 → 阈值判断流程），还没做成让模型自由多轮检索。理由是成本与延迟不可控——我们的单次检索 114 ms 不贵，但模型自由多轮意味着几十次调用，延迟和 token 都会失控。

我们的过渡方案是**在检索侧做确定性增强**：阈值不够就换一路（dense → sparse → 加过滤放宽）再试一次，而不是把决策权完全交给模型。这叫「受控的多路召回」，比 Agentic 便宜且可预测。

**【追问】**
- Agentic RAG 什么时候值得？→ 问题本身需要多跳推理（跨文档、跨时间、跨实体），且单轮召回确实不够。
- 怎么防止无限循环？→ 工具层限制最大调用次数 + 总 token 预算。

**【易错】**
- 说「Agentic RAG 更好」。多轮检索的收益要用评测集证明，成本也要算进去。

### RAG24 · 什么时候需要 GraphRAG？⭐⭐⭐⭐

**【一句话答】** 当问题需要**实体关系上的多跳推理**（A 收购了 B，B 的 CEO 是 C）时，图检索比向量检索合适；但图谱的构建和维护成本高，绝大多数问答场景用不上。

**【展开】**

- 向量检索擅长「这段话和我的问题像不像」；不擅长「B 和 C 之间是什么关系」，因为关系是**结构**不是**语义**。
- GraphRAG：先抽实体和关系建图，再在图上做路径查询，最后把子图转成文本喂给模型。
- 代价：实体消歧、图谱增量维护、schema 设计，复杂度远高于切块 + 向量。
- 轻量替代：**结构化字段当关系用**——把「作者/章节/版本/引用」这类关系直接做成 payload 字段，用过滤和字段组合代替图遍历。

**【我们的实践】** 我们的 `h1/h2/h3` 层级、`source`、`family` 实际上已经是一棵**浅层树**，可以用它做「限定在某本书的某章里搜」这类弱关系查询——靠 payload 过滤实现，零额外成本。这也说明：**很多「要不要上图」的问题，用字段化的层级结构就能覆盖一大半**。

我们对 GraphRAG 的判断是：**知识库里有大量实体关系型问题之前，不做**。目前的替代路线是「Agentic 多轮 + 受控多路召回」。

**【追问】**
- 实体关系问题长什么样？→ 「A 公司和 B 公司是什么关系」「这个人参与过哪些项目」。
- 成本量级？→ 实体抽取 + 关系抽取（LLM 批量跑）+ 图存储，通常是纯向量方案的几倍到几十倍成本。

**【易错】**
- 把 GraphRAG 当 RAG 的「高级版」默认上。**它是另一类问题域**，不是升级。

## 附：面试速记 10 条

1. RAG 的效果瓶颈在**解析、切分、召回**三处，不在模型；答案出不来先查这三处，别先换模型。
2. 阈值是**标定**出来的：命中域 top1 最低 0.6913、落空域最高 0.6126 → 阈值 0.65，落在这个空隙里。
3. **payload 索引**是性价比最高的优化：建索引前 1,456 ms，建完 115.7 ms（12.5 倍）。
4. 归一化 + Cosine 下，余弦/内积/L2 **等价**；真正要问的是「归一化了没有」。
5. `hnsw_ef` 是唯一能在线调的旋钮，但在 13.6 万点规模上收益 <10%，**不值得调**。
6. 13.6 万点 × 1024 维的暴力扫描不可行；但**批量搬运 payload**（scroll 5,000 点带 payload 慢 101 倍）比 ANN 检索更容易出事。
7. 幂等靠**内容派生的确定性 id**；写前查重 0.95 是安全的（同内容 score=1.0，次相似仅 0.75~0.79）。
8. 库里 15.8% 的点正文重复（6,295 组），一次 top20 召回能被重复内容占掉 2 个名额 → **召回后必须去重**。
9. **过滤是「换候选集」不是「排序后筛」**：加过滤后 top10 与不过滤的 top10 只重合 5 个。
10. 幻觉最有效的防线是**阈值闸门 + 拒答**，不是 Prompt 里写「不要编」。
