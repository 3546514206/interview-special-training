Cache Aside · 写路径并发时序对比

先更新 DB 再删缓存（推荐） vs 先删缓存再更新 DB（反例） · 时序决定不一致窗口的大小

为什么"删缓存"而不是"更新缓存"

  • 乱序覆盖：并发写时 A 的旧值后到，覆盖 B 的新值
  • 懒加载：删除幂等，下次读自然回填最新值
  • 写多读少场景下，更新缓存产生大量无效计算

延迟双删

  • 更 DB → 删缓存 → 等待 → 再删一次
  • 间隔 = 主从延迟 + buffer（通常几百 ms）
  • 消灭"从库旧数据被读请求回填"的窗口；读走主库可省略

binlog 订阅（Canal）

  • 伪装 MySQL 从库收 binlog → 解析 → 删缓存
  • 业务零侵入、不丢变更，准实时（秒级）
  • 删除失败由下一条 binlog 重放补偿

一致性的准确定位

  • 缓存层给出的是最终一致的工程权衡
  • 面试中声称"100% 一致"是错误表述
  • 强一致需读写分布式锁串行化，吞吐倒退一个量级，仅资金类极小范围使用
