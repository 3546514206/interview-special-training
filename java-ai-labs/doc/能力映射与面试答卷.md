# 能力映射与面试答卷

> 面向「蚂蚁集团 · 财富黑卡 / 蚂蚁财富 · Java AI 岗」JD。
> 左边是 JD 原话，右边是本模块里**已经能跑起来**的代码，以及面试时该怎么讲。

## 一、JD 条款 → 代码映射总表

| JD 条款 | 代码位置 | 面试怎么讲（一句话） |
|---|---|---|
| 熟悉 RAG 的**知识接入** | `rag/CorpusLoader`、`rag/Chunker`、`rag/Document` | 接入不是「读文件」，是归一化 + 分块 + 保留可追溯的元数据；分块要按语义边界切、带 overlap，否则答案被切在中间 |
| RAG 的**索引构建** | `rag/IndexBuilder`、`rag/Bm25Index`、`rag/InMemoryVectorStore`、`rag/QdrantVectorStore` | 索引有两套：稠密向量（语义）+ BM25（精确词），两者互补；向量库集合维度与 embedding 模型强绑定 |
| RAG 的**召回** | `rag/DenseRetriever`、`rag/SparseRetriever`、`rag/HybridRetriever`（RRF）、`rag/QueryRewriter` | 召回是「宁可多召」，重排才是「精选」；RRF 融合只比排名不比分数，避免两路分数不可比 |
| RAG 的**重排** | `rag/FeatureReranker`（+ MMR） | 重排用多特征加权并**输出分数拆解**，可解释才能定位问题；MMR 解决「十条都来自同一篇文档」 |
| RAG 的**上下文组装** | `rag/ContextAssembler` | 组装要同时管：token 预算、去重、来源限额、引用编号、以及「不可信内容边界」 |
| RAG 的**效果评测** | `rag/RagEvaluator`、`rag/RagExperiment`、`resources/golden` | 评测先定口径再调参：Recall@k 看召回、nDCG 看排序、引用正确率看可信度；多组配置对比而不是拍脑袋 |
| **工具调用** | `agent/ToolRegistry`、`agent/AgentLoop`、`agent/tools/*` | 工具是能力边界；参数校验、失败结构化返回、副作用声明，缺一不可 |
| **状态与记忆** | `agent/ConversationState`、`agent/MemoryCompactor`、`agent/Scratchpad`、`agent/MemoryStore` | 三类记忆：会话轮次、长期笔记、事实 KV；超预算时压缩而不是硬截断 |
| **权限控制** | `core/ToolAuthorizer` + `harness/PermissionPolicy`、`harness/PathSandbox` | 授权发生在执行之前，**拒绝理由要回灌给模型**，模型才知道换路 |
| **工作流编排** | `agent/Workflow`、`agent/WorkflowRunner` | 能用工作流确定的就别交给模型决策；工作流管确定性的分支与重试，模型只做需要判断的节点 |
| **Agent 运行时 / 多 Agent** | `agent/AgentLoop`、`agent/SupervisorAgent`、`agent/SpecialistAgent` | 多 Agent 的价值是**工具集与上下文隔离**，不是把一个模型拆成几个角色 |
| **Harness Engineering** | 整个 `harness` 包 | 把模型关进笼子：能力边界、权限、预算、可观测、降级、安全，六件事同时成立才算工程化 |
| **可观测性** | `harness/Tracer`、`harness/JsonlTraceSink`、`harness/TraceReport` | 一次请求扇出成 N 次模型调用 + M 次工具调用，不画 span 树就不知道慢在哪、花在哪 |
| **成本控制** | `harness/CostMeter`、`harness/BudgetPolicy` | 成本是运行时约束不是事后报表：软阈值降级模型、硬阈值拒绝调用 |
| **安全** | `harness/SecretRedactor`、`harness/PromptInjectionGuard`、`harness/PathSandbox` | 注入的根因是「不可信内容」和「指令」混在一个通道里；解法是分层 + 标注 + 权限收窄 |
| **稳定性** | `harness/RetryPolicy`、`harness/CircuitBreaker`、`harness/FallbackChatModel` | 模型调用不稳定是常态：超时/限流/5xx 要能重试，连续失败要熔断，主模型挂了要能降级 |
| **AI Coding / 无人化交付** | `harness/coding/CodingDeliveryPipeline` | 生成代码的质量只能靠**编译 + 断言**判定，不能靠「看起来对」 |
| **借助 AI Coding 快速上手新语言** | 本仓库 `java-labs` / `spring-labs` / `java-ai-labs` 的演进记录 | 用 AI 生成初稿，人负责定契约、验边界、写断言——这正是「判断和验证生成代码质量」 |

## 二、六个最可能被追问的问题

### Q1：RAG 回答不准，你怎么定位？

**分层归因，不要一上来就调 prompt。**按「检索 → 重排 → 组装 → 生成」四层逐个看：

1. **检索层**：正确文档在不在 top-k 里？在 → 不是检索问题；不在 → 换分块策略 / 加 BM25 / 加查询改写。
2. **重排层**：在 top-k 里但没排进 top-3？→ 调重排特征权重（`FeatureReranker` 的权重就是为这个准备的）。
3. **组装层**：排进去了但被预算裁掉了？→ 看 `AssembledContext` 的截断记录。
4. **生成层**：上下文里明明有答案却答错 → 才是 prompt / 模型的问题。

> 工程抓手：`rag/RagExperiment` 同一批问题上跑多组配置出对比表，
> **用数字说话**（Recall@5 +18pt，代价是平均上下文 token +320）。

### Q2：召回和重排的边界在哪？为什么不能一步到位？

召回追求「别漏」，重排追求「别冗」。如果只做一次向量检索 top-5，
既可能漏（用户问法的词面不匹配）也可能冗（五条来自同一篇文档）。
所以是**漏斗式**：向量 + BM25 各召回 50 → RRF 融合去重 → 重排取 top-5 → 组装。

RRF（Reciprocal Rank Fusion）用 `1/(k+rank)` 而不是直接加分数，
原因是两路检索的分数尺度完全不同（余弦相似度 0~1，BM25 无上界），只有排名可比。

### Q3：上下文组装最容易踩什么坑？

四个坑，按踩到频率排序：

1. **预算超了硬截断** → 截掉的可能正是答案。做法是按预算**按分数贪心挑选**，并记录被丢弃了什么。
2. **丢失中间（lost in the middle）** → 长上下文里模型对开头结尾更敏感，中间容易被忽略。
   做法：高相关片段放两端（`ContextAssembler` 的排序策略）。
3. **重复内容挤占预算** → 同一文档的相邻 chunk 高度相似，必须去重/合并。
4. **指令与资料混淆** → 检索到的文档里如果写着「忽略以上指令」，模型可能照做。
   做法：资料统一包在 `<context>` 里（`core/PromptBlocks`），并在授权层收窄工具权限。

### Q4：效果怎么评测？指标口径是什么？

先说口径再说数字：

- **Recall@k**：黄金集里期望命中的文档，有多少出现在 top-k。衡量「漏没漏」。
- **MRR@10 / nDCG@10**：第一个正确结果的位置 / 排序质量。衡量「排得准不准」。
- **引用正确率**：答案里的 `[n]` 是否真的支撑结论。衡量「有没有编」。
- **上下文 token 均值**：效果的代价。召回率提升通常伴随 token 成本上升，必须一起报。

黄金集（`resources/golden`）要覆盖**可回答 / 需多跳 / 不可回答（应拒答）**三类。
只有可回答的问题会让系统显得比实际更好——拒答能力必须单独评测。

> 回归门禁：测试里断言 Recall@5 不低于阈值，效果掉了 CI 就红。

### Q5：Agent Loop 怎么防止跑飞？

四件套终止条件，缺一个就可能失控：

1. **步数上限**：单次请求最多 N 步。
2. **预算上限**：token / 金额超阈值就停（`BudgetPolicy`）。
3. **重复检测**：同一工具 + 同一参数连续出现 N 次 → 判定死循环，直接终止并报错。
   （模型很容易陷入「改一个字再试一次」的死循环。）
4. **连续失败熔断**：工具连续报错 → 判定环境或方案有问题，停止重试。

另外每个工具的失败都要**结构化回灌**给模型（`ToolResult.error`），
让模型自己决定换参数、换工具还是收尾——而不是把异常抛出去让整条链路挂掉。

### Q6：什么是 Harness Engineering？

一句话：**把模型关进笼子里**。

模型不可靠是既定事实，Harness 的目标不是让模型变可靠，而是**让模型不可靠这件事不伤到系统**。六件事同时成立才算工程化：

| 维度 | 手段 | 代码 |
|---|---|---|
| 能力边界 | 工具白名单 + 参数 schema 校验 | `ToolRegistry`、`ToolSpec` |
| 权限 | 执行前授权，拒绝理由回灌 | `PermissionPolicy`、`ToolAuthorizer` |
| 预算 | 软阈值降级 / 硬阈值拒绝 | `BudgetPolicy` |
| 可观测 | span 树 + 成本归因 | `Tracer`、`CostMeter` |
| 降级 | 重试、熔断、备用模型 | `RetryPolicy`、`CircuitBreaker`、`FallbackChatModel` |
| 安全 | 脱敏、注入检测、路径沙箱 | `SecretRedactor`、`PromptInjectionGuard`、`PathSandbox` |

这六件事的共同点：**都在模型之外**。这也回答了「Harness 和写 prompt 有什么区别」。

## 三、技术选型的答辩要点

**为什么选 Qdrant？**
- 部署简单（单容器）、REST 与 gRPC 双协议、payload 过滤 + 全文索引一体；
- Java 侧官方有 `spring-ai-qdrant`，实验里我用 REST 直连，是为了把协议细节显式写出来；
- 实验用**独立集合** `java_ai_labs_knowledge`，与生产/记忆库隔离，避免实验污染真实数据。

**向量维度怎么管？**
维度是集合的**建表契约**，不是运行时参数。工程约束：

1. 维度写进配置（`QDRANT_DIM`），启动时与 `EmbeddingModel.dimensions()` 校验，不一致直接拒绝启动；
2. 换 embedding 模型 = 新维度 = **必须重建集合**（可以双写灰度，但不能原地改）；
3. 维度不匹配是 RAG 里最难查的故障之一：检索返回空 / 报 400 / 静默全零分数，表现完全不像「维度问题」。

**为什么 embedding 用哈希向量？**
因为实验要**离线可回归**：真实 embedding 模型要么要 API Key、要么要 GPU 推理。
哈希向量（signed hashing trick）保证确定性，缺点是语义泛化能力弱。
工程上正确的做法是把它放在 `EmbeddingModel` 接口后面，换模型只改实现 + 重建集合——
**这正是接口抽象的价值所在**，也是面试里可以主动展开的点。

## 四、一分钟讲清这个项目

> 我做了一个 Java AI 工程实验模块，把蚂蚁财富这个岗位要求的 RAG 全链路、Agent Loop 和
> Harness Engineering 三块能力，都做成了可运行、可断言的 Java 代码。
>
> 架构上是端口-适配器：模型、向量库、检索、工具、Trace、成本全部抽象成接口，
> 所以没有 API Key 也能跑完整链路和回归测试，真实依赖作为可选适配器接进来——
> 向量库接的是 Qdrant，模型侧写了 OpenAI 兼容协议的适配器。
>
> RAG 侧我实现了知识接入、索引、混合召回、重排、上下文组装和效果评测，
> 重排会输出每个候选的特征分拆解，评测有 Recall@k、MRR、nDCG 和引用正确率，
> 并且支持多组配置对比，指标退化会直接让测试挂掉。
>
> Agent 侧是完整的 Loop 状态机：工具注册与参数校验、工具结果结构化回灌、
> 死循环检测、预算熔断、状态与三类记忆、工作流编排和多 Agent 委派。
>
> Harness 侧我把可观测、成本预算、权限安全、降级熔断都做成了运行时约束，
> 还做了一个 AI Coding 流水线：需求 → 方案 → 代码 → 测试 → 真实编译执行 → 交付报告，
> 用编译和断言来判定生成代码的质量，而不是靠看起来对。

## 五、诚实边界（面试时主动说，反而加分）

- 哈希 embedding **不是**语义模型，召回质量上限受此限制；真实场景应换 bge-m3 / text-embedding-v3 一类的模型，
  换模型必须重建集合（本模块已把这个约束显式化）。
- 评测集是自建的小规模中文黄金集（十几条），**不是**线上分布；
  真正的评测集应该来自线上日志采样 + 人工标注，且要按业务线分层。
- 重排是特征加权 + MMR，**不是** cross-encoder 精排；生产上应在特征重排之后再叠一层 cross-encoder。
- 多 Agent 目前是「Supervisor + 专家」的两层结构，真实业务里还需要考虑共享记忆的污染与委派成本的收益比。
